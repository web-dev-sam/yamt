Owner skills: `skill://ts-conventions`, `skill://ipc-contract`. yamt's own language-server client (plan §2 #67, #70): speaks the protocol to programs an `ipc/ServerHost` starts; owns each server's lifecycle and state, the documents open on it, its problems (pushed and pulled into one slot per server: `DocProblems` never shows an answer older than the last one it showed), formatting, and its log. Framework-free: no `vue`, `@vueuse`, `@tauri-apps`, and never imports `editor/`, `ui/`, `model/`, `connectors/` (oxlint + `scripts/fences.ts`); only `ipc/index.ts` types. Public surface is `index.ts` (`LanguageServers`, `isDocVersion`, `detect`, `addedSpecs`, `presetChoices` and the types); everything else in `internal/`. Every message from a server is external data, parsed once with valibot (`messages.ts` envelope, `protocol.ts` payloads); a malformed one is logged and dropped.

A server's run is one sum type, `Run` in `internal/run.ts` (idle, launching, starting, running, halting), held by `internal/server.ts` (the lifecycle); its `state` and `running` (the documents, the capabilities, the attempt) are derived from it. `internal/attempt.ts` is one process run: it starts and stops the process and routes its messages.

Which specs exist (plan §2 #70 "Detection", "Not installed", #72): `internal/detect.ts` `detect(paths, lookups, root)` is a pure function over the host's two generic lookups (`findProgram`, `projectFiles`; Rust never learns a server's name or an ecosystem). `internal/ecosystems.ts` is the one table of ecosystems (node, python, rust, go, php, clang): each one's project rule (manifests tried in order, nearest folder up to the repository root; rust prefers the nearest `Cargo.toml` with a `[workspace]` table, go `go.work` over `go.mod`, clang's `build/compile_commands.json` makes the folder holding `build/` the project) and its `ProgramFolders` (project folders such as `node_modules/.bin`, `.venv/bin`, `vendor/bin`; home folders such as `go/bin`, `.cargo/bin`, `.local/bin`); the folder walking lives there once, as do the TOML table-header rule (`tomlTable`) and its check (`fileHolds`). A path joins an ecosystem only when some detected preset of that ecosystem serves its file type. Each project folder is read in one `projectFiles` batch — the names come from `internal/candidates.ts` (each preset's signs and configs, Phpactor's integration files, the Vue packages, and the files the install hints read, `install.ts` `HINT_FILES`) — and run through the one preset table `internal/presets.ts` (vocabulary in `internal/tool.ts`; formatters first: oxfmt, Biome, oxlint, TypeScript, eslint, rust-analyzer, gopls, ruff, ty, basedpyright, pyright, Phpactor else Intelephense, clangd, then Deno and bash-language-server, which have `ecosystem: null`: Settings list only, never detected; `DETECTED_PRESETS` is the rest). A `used` look counts a config file, a `pyproject.toml` section or the ecosystem's manifest wherever `findProgram` finds the server (`Project`, `Path`, `Home`), else its spec carries an `InstallHint` (`internal/install.ts`: node's manager from `internal/packageManager.ts` — the `packageManager` field, else the nearest lock file; python's from the nearest `uv.lock`/`poetry.lock`/`pdm.lock`); a found preset server carries that same hint as `help` (null for oxfmt, Biome, oxlint, tsc/tsgo and Intelephense, which have none); a program-only sign (oxfmt, Biome, oxlint; ruff, ty, basedpyright without their config) counts only `place: "Project"`, so detected and can start agree. A tool's `fromProject` adds what only the project knows: Phpactor's integrations (`internal/integrations.ts`: PHPStan, Psalm, PHP-CS-Fixer, phpcs, each on with `vendor/bin/<tool>` and its config in the project folder; Phpactor formats only with a formatting one on), pyright's `python.pythonPath` (the project venv's `python`, `place: "Project"`). `internal/vue.ts`: in a TypeScript 5/6 project (typescript-language-server) with `vue` up the chain, `@vue/typescript-plugin` up the chain makes the TypeScript spec serve `vue` with the plugin loaded from the project folder; without it a never-started "Vue" spec carries the plugin's hint; TypeScript 7 or tsgo with `vue` gets the `vueNeedsTypeScript6` note. A changed spec (the plugin installed) is a new spec to `setSpecs`: the old run stops, the new one starts. `internal/project.ts` holds what one (ecosystem, folder) project reads: its files, its program lookups with the ecosystem's folders, the nearest of a set of files. A project's workspace URI is `handshake.ts` `projectUri`, the one the handshake sends. A rejecting lookup means "not found"; nothing throws. `internal/choices.ts` lists each preset's own server (`presetChoices` for Settings, in table order, PHP as Phpactor then Intelephense). `internal/added.ts` `addedSpecs(added, taken, root)` turns the settings file's added servers into specs served at the repository root; an entry whose program has no file name is skipped; one whose program file name (folder and `.exe`/`.cmd`/`.bat` dropped) and arguments equal a preset server's gets its name, settings, start options for the root, formats unless "never", and help. Every detected spec carries its ecosystem's folders as `ServerSpec.folders`; added specs carry `ecosystems.ts` `EVERY_ECOSYSTEM_FOLDERS`; the start command sends `spec.folders`.

Reading path of one message from a server: `ServerHost` event → `internal/attempt.ts` `#onEvent` → `connection.ts` `receive` (parse) → a response settles its request; a request goes to `answers.ts` (pure table) and back through `send`; a notification goes to `attempt.ts` `#notified` → `problems.ts` `pushProblems` → `DocProblems` → `ResultDocument.showProblems`. Outward: `index.ts` `open` → `documents.ts` (`DocEntry`: version, 300 ms sync) → `serverDocs.ts` (`didOpen`/`didChange`/`didClose`) → `connection.ts` → `ServerHost.send`; pulls go from `problems.ts` `DocProblems.pull`, the formatting request from `formatting.ts`.

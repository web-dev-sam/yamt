# Gate D — 2026-10-13: faster features, growth-first review triage

Approved by the owner (#740) after the settings feature took ~4¼ h (analysis in session 8: ~40 % in
repeat passes — 7 fix rounds for 2 blocking findings, re-reviews that found new small issues each
time, the mutation check only at the end, strictly sequential builds, one build over its request
budget). The owner's own rule (verbatim in #740): the app must scale without god components or
unclear data flow; time is bought for that, not for local polish; small findings are judged by
whether leaving them hurts the technical vision as the app grows, so many drop.

Apply each item exactly. "Orchestrator" items are applied by the orchestrator (outside the
curator's `.omp/**` scope or in `ORCHESTRATOR_EDITABLE`); everything else by the curator.

## W1 — Severity: user-visible bugs and growth harm block; the rest is judged, mostly dropped

- `skill://review-protocol` § Grading becomes:
  - `block` — (1) wrong behaviour a user or a caller would notice, a violated invariant, a changed
    contract, missing acceptance evidence, or a test that is the only evidence for an Acceptance
    line and would pass with the feature deleted; **(2) growth harm**: a change that makes the app
    harder to grow — a module or component taking on a second job (a god component in the making),
    state with two writers or a second source of truth, data reaching a place through a side
    channel or through layers that do not use it, a boundary bent (an edge against architecture §2
    or the state-ownership table §5.1), a rule or decision copied instead of shared, a rule other
    code relies on left untested. A user-visible bug is never a `should` (calibration: #689, #692,
    #710, #723 were reported as `should`).
  - `should` — local quality with no growth effect: naming, a clearer loop, comment wording, a test
    gap on a rule nothing else builds on, structure inside one function.
  - `nit` — taste.
  - New line: "For every `should` and `nit`, the `problem` sentence says what, if anything, gets
    harder as the app grows if it stays; 'nothing' is a valid answer."
- Boundary lens gains a **growth check**: for every touched module or component, count its jobs
  (does it now own data _and_ layout _and_ rules?); every new piece of state has one owner row in
  architecture §5.1 and is written only by that owner; every new import edge follows §2; a second
  copy of a decision is reported.
- `skill://orchestrate` §5 gains **[OR12] triage**: before any fix round, the orchestrator judges
  every `should`/`nit` (and every verifier survivor) with one question — _if this stays, does the
  app get harder to grow (a component with a second job, data with two writers or two sources, a
  copied rule, a bent boundary, an untested rule other code relies on)?_ Yes → promoted to `block`
  and fixed in this build's fix round. No → dropped, logged in `findings.jsonl` with
  `"triage": "dropped: <one-line reason>"` (or promoted: `"triage": "promoted: <reason>"`). No
  backlog of small items, no end-of-feature cleanup round.
- `skill://orchestrate` §6: a fix round runs only for blocks (including promoted ones). Max two
  rounds per build stays; beyond → Gate B.

## W2 — One scoped reviewer per fix round

- `skill://orchestrate` §5/§6 and `skill://review-protocol`: a fix round is re-checked by **one**
  reviewer — the lens that raised the blocks it fixes (both only when both lenses raised blocks).
  Scope: is each block fixed; did the fix break behaviour or cause growth harm (W1 (2))? New
  `should`/`nit` in a re-check are reported only if they meet the block bar; the orchestrator
  drops the rest without a round.

## W3 — The mutation run follows each build, not only the end

- `skill://verification` VF7 and registry SP5: after a build's patch is applied and committed, the
  **orchestrator** starts `just mutants <commit before the build>` as a background job. The boundary
  reviewer starts at once; the correctness reviewer starts when the run ends and gets its survivor
  list (`target/mutants/`, Stryker clear-text) as input, triaged with VF7 (a)/(b)/(c) and W1. The
  final check still runs `just mutants <commit before the feature>` once, as confirmation.
- `skill://review-protocol` correctness lens: "survivors come from the orchestrator's per-build
  `just mutants` run" (not "from the verifier").
- **Orchestrator**: `justfile` `mutants` recipe passes `--ignoreStatic` to Stryker (static mutants
  are not re-evaluated under the vitest runner; #732: 134 false survivors).

## W4 — Overlap independent work

- **Orchestrator**: `.omp/hooks/lib/policy.ts` `MAX_PARALLEL_AGENTS = 3`.
- Curator: `.omp/hooks/test/hooks.test.ts` task-fanout test asserts `MAX_PARALLEL_AGENTS` allowed
  and `MAX_PARALLEL_AGENTS + 1` blocked (not literal 2/3).
- `skill://orchestrate` OR10 becomes: at most `MAX_PARALLEL_AGENTS` agents live; at most two
  implementers; reviewers may run while an implementer runs (they read committed patches); a
  `just mutants` run may run beside reviewers and implementers; the verifier runs alone (no other
  agent and no mutation run beside it: it builds and drives the app). Registry OR10 row updated to
  match.
- `skill://orchestrate` §2/§3: builds form a dependency graph. Builds without shared files or
  contracts run in parallel (e.g. a desktop build and a palette build). A build that needs another
  build's code starts as soon as that build's round 1 is committed, not after its review and fix
  round; a fix round never touches the dependent build's owned files, and a fix that changes a
  contract the dependent build uses is sent to it (`write agent://<id>`) or becomes part of its
  own fix round.

## W5 — Builds sized to the budget; task descriptions do not re-derive sourced facts

- `skill://orchestrate` §2 and `skill://slice-protocol`: one build = one concern and fits well
  inside an implementer's 200-request budget — as a guide ≤ ~25 files and ≤ ~1,500 changed lines;
  larger → split (incident: SettingsWeb, 281 requests, stopped before its real-app check).
- A task description passes the design's sourced facts (values, source lines) as given and asks to
  re-check only what the design marked `[INFERENCE]` (incident: ~25 requests re-reading theme
  files the design had already read).

## W6 — A shared real-app helper (built as a task, not by the curator)

- **Orchestrator**: a build task adds a committed helper for driving the real app and the
  fixture page (start Xvfb + tauri-driver with a temporary config folder and a fresh conflict repo,
  or the fixture dev server + `just webdriver`; click and type by accessible name; read state;
  page/display screenshots; frame-colour sampling of a recording). Curator: once it lands,
  `skill://verification` recipes point to it and say "do not write throwaway WebDriver helpers".

## W7 — Fewer stops for questions

- `skill://orchestrate` §1 and Gate A: before asking the owner anything, start every build that
  does not depend on the answer (the question then waits while agents work). When the owner's
  request states the feature and the workflow, Gate A is not a question: the plan goes into the
  next report, and only real product choices (a WebStorm deviation, a tradeoff the owner must make)
  are asked.
- Gate B is asked at most once per feature; its answer stands for the rest of the feature.
- Talking to the human: the first word of an owner's answer is the answer ("No …" is no); a
  complaint about being asked again is not consent (#738/#739).

# M1 walkthrough — the window shows the engine's conflicts

## What was built

The browser window now works as a merge tool on the 10 real conflicts from `tests/golden/`:

- **Real data from the engine.** `just fixtures` runs the Rust engine on every golden case and
  writes `frontend/fixtures/golden/<case>.json`; `just fixtures-check` (in `just check`) fails
  if they drift from the engine. The TypeScript types for that data are generated from the Rust
  types (`frontend/src/ipc/bindings.ts`), then given line-space brands in `ipc/domain.ts`.
- **File list** of the 10 cases; clicking one opens it (a slower earlier load never replaces a
  newer click).
- **Colours** per change: green inserted, blue modified, grey deleted, red conflict, in all three
  panes; a thin line marks where lines were inserted or deleted.
- **Bands** in the two gaps join each change to its counterpart, and the three panes **scroll
  together**: the line in the middle of the pane you scroll lines up with its counterparts; across
  a change of different heights the other panes move proportionally, across inserted lines they
  wait.
- **Applying changes**: `»` / `«` next to each open change applies it into the middle pane, `×`
  ignores it; a conflict can take one side, then the other (appended). Undo/redo (keyboard or
  toolbar) restore text and state together. "Apply non-conflicting changes from the left/right"
  is one click and one undo step. The toolbar counts what is left. "Mark resolved" hands the
  middle text (CRLF kept for CRLF files) to the source; "Reset file" starts the file over.

Not yet: the desktop app and a live git merge (next milestone), `.vue`/`.tsx` highlighting,
word-level highlights, keyboard access to the arrows.

## Non-obvious constructs (TypeScript / CodeMirror)

- **Brands without casts** (`ipc/domain.ts`): `BaseLine = number & { readonly __brand: "BaseLine" }`
  is created by a type guard that checks for a non-negative integer, so a local line number can
  never be passed where a base line is expected, and no `as` is needed.
- **One owner for each change's position and state** (`editor/internal/chunkField.ts`): a
  CodeMirror `StateField` on the middle pane maps every change's range through each edit and keeps
  its state (`pending`, `applied-local`, …). The state changes only through an effect registered
  with `invertedEffects`, which is how undo restores the text and the state in one step. The side
  panes only show a copy pushed after each change.
- **Range ends** (cm6-rules CM1): a range runs from the start of its first line to the start of the
  line after. Both ends stick to the text before them when something is inserted exactly there, so
  typing on a change's lines stays inside and typing on the next line stays outside; when a change
  is applied, the next change is pushed down rather than the applied text being cut short.
- **Scroll mapping as one pure function** (`editor/internal/scrollSync.ts`): anchor pairs at every
  change's top and bottom plus the file ends, straight lines between them. Replacing this one
  function is how a different scrolling style would be tried later (plan §2 #12).
- **One repaint per frame**: scroll events only request an animation frame; all measuring and
  drawing of bands and arrows happens there, so the three panes never fight each other.

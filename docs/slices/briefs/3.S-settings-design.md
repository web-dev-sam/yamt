## The product rule (settled by the owner, #662/#663 — do not reopen)

1. **Theme.** A Light / Dark switch in the settings view; it recolours the whole window at once,
   every opened file included. Dark is today's Islands Dark (`docs/plan.md` §2 #24) and stays the
   default. Light is WebStorm 2026.2's "Islands Light", read from the owner's install (DR6, as #24
   did for dark):
   - window theme `ManyIslandsLight.theme.json` (parent `ExperimentalLightWithLightHeader` →
     `expUI/expUI_light_with_light_header.theme.json` → `expUI/expUI_light.theme.json`);
   - editor scheme "Light" = `expUI/expUI_lightScheme.xml` (parent "Default" in
     `DefaultColorSchemesManager.xml`: `DIFF_INSERTED` BEE6BE, `DIFF_MODIFIED` CAD9FA — the "Light"
     scheme overrides it to c2d8f2 —, `DIFF_DELETED` D6D6D6, `DIFF_CONFLICT` ffd5cc);
   - all extracted under `/tmp/yamt-islands-light/` (re-extract with `unzip` from
     `~/.local/share/JetBrains/WebStorm-262.10968.77/lib/intellij.platform.ide.impl.jar` if gone;
     the dark files are there too, for comparison).
     Conflicts stay **purple** in light, a light purple from the JetBrains light palette, not
     WebStorm's salmon: the owner's reason for purple (#32: red reads as "deleted") holds in both.
2. **Keys.** The view lists yamt's own keyboard actions — about 14 — each with its keys, today's
   keys as defaults:

   | action          | today                                 | where it acts                    |
   | --------------- | ------------------------------------- | -------------------------------- |
   | Apply           | Enter, Space                          | a side pane (#54)                |
   | Ignore          | Backspace, Delete, X                  | a side pane                      |
   | Next change     | Down                                  | a side pane                      |
   | Previous change | Up                                    | a side pane                      |
   | Left side       | Left                                  | a side pane                      |
   | Right side      | Right                                 | a side pane                      |
   | Undo            | Ctrl/Cmd+Z                            | anywhere in the shown file (#54) |
   | Redo            | Ctrl/Cmd+Shift+Z, Ctrl/Cmd+Y          | anywhere in the shown file       |
   | Find            | Ctrl/Cmd+F                            | any pane (#44)                   |
   | Find next       | F3 (and Enter in the find box)        | a pane or its find box           |
   | Find previous   | Shift+F3 (and Shift+Enter in the box) | a pane or its find box           |
   | Close find      | Escape                                | a pane or its find box           |
   | Indent          | Tab                                   | the middle pane (#35)            |
   | Outdent         | Shift+Tab                             | the middle pane                  |

   Verify this table against the tree; a key the code binds that is missing here, or one listed
   that the code does not bind, goes into your output. The middle pane's text-editing keys
   (cursor moves, select all, move line, …) are **not** listed and keep working as today.
   Per action, like WebStorm's Keymap settings (`KeymapPanel`: "Add Keyboard Shortcut", "Remove",
   "Reset Shortcuts"): change one key, add a key, remove a key, reset the action to its defaults.
   Recording a key follows WebStorm's `KeyboardShortcutDialog` / `ShortcutTextField` (DR6; source
   sparse-cloned at `/tmp/ij-diff/platform/platform-impl/src/com/intellij/openapi/keymap/impl/ui/`).
   A key another action already uses → a question naming that action, "Move" (the other action
   loses the key) or "Cancel" (nothing changes). WebStorm offers "Leave" too; yamt drops it because
   only one of the two would work. A changed key works at once in every opened file.

3. **Settings file.** Per user, not per repository. By default a file in the user's config folder.
   The view shows the file's location in a field prefilled with the default path; the user can
   point it elsewhere. A file that exists there → its settings take effect; a missing one → it is
   created with the current settings. yamt writes every change to the file at once, and picks up
   changes made outside (by hand, a dotfiles sync) while it runs. The chosen location must itself
   be remembered somewhere fixed.
4. **Toolbar.** The Undo and Redo buttons are hidden by one hardcoded switch in the code; their code
   stays (`frontend/src/ui/MergeToolbar.vue:66-78`).

Orchestrator defaults (keep unless you find a concrete problem; then say so in `open_questions` as
a user-visible consequence):

- No "follow the system" theme. The switch is two choices, Dark first.
- One stored form for "Ctrl on Linux, Cmd on macOS" (today's `Mod-` convention), shown as "Ctrl+F"
  on Linux and "⌘F" on macOS.
- Outside changes are picked up when the window gets focus — the moment the file list is re-read
  today (#49, `ui/App.vue:32-38` `useWindowFocus`), not by watching the file.
- A broken or unreadable settings file shows a problem in the window, the settings in use stay,
  and the file is not overwritten behind the user's back. Entries yamt does not know (a newer
  version's) survive a save.
- A light start never shows a dark frame: the native window background follows the theme from the
  moment the window is created.
- Fixture mode (`just dev-web`, the browser, no Rust) shows and applies settings too.

## What each option must answer

1. **Data.** The settings shape, data structures first: theme, key bindings, the file location.
   The JSON format of the file (readable and editable by hand; unknown entries; a later version).
   One source of truth (vision 2) for the action list, each action's name and its default keys:
   where it lives (`editor/`? Rust?), and how the IPC types stay generated (#19,
   `skill://ipc-contract`). Illegal states (vision 4): an unknown action id, a malformed key, an
   action with no keys left.
2. **File.** Default path per platform (Linux `XDG_CONFIG_HOME`, macOS), where the chosen location
   is remembered, read at start (before the window exists, for its background), written on every
   change (atomically?), re-read on focus; a missing folder, a broken file, a location that cannot
   be written, two yamt windows open at once (one per repository) writing the same file.
3. **Theme.** How the palette switches while staying in one place (style.css), CodeMirror's dark
   flag in every opened file, `color-scheme`, the native window background at start and on a
   switch, the colour of everything not drawn through the variables (icons, scrollbars, focus
   rings). No dark frame at a light start; no flash on a switch.
4. **Keys into the editor.** How `editor/` receives bindings (at creation and on a change, in every
   opened file — a CodeMirror `Compartment`?), side keys, find keys and the box's Enter,
   indent/outdent, window-wide undo/redo with the layout fallback; precedence against the middle
   pane's own `defaultKeymap`/`historyKeymap` (Indent re-bound to a key the default keymap uses;
   the default keymap's own Mod-z undo when Undo is re-bound away from it); keys that would break
   typing in the middle (Undo bound to a plain letter) — allowed or refused: a product consequence
   → `open_questions`. Follow `skill://cm6-rules`.
5. **The view.** Layout of the settings column (sections, headings), a key row (action name, its
   keys, add/remove/reset), recording a key as WebStorm does (what starts and ends a recording,
   Escape, a modifier pressed alone, the Mac), the clash question, the location field (how a new
   path is confirmed; reset to the default path). `skill://vue-conventions`; components and line
   budgets (`store.ts` and `index.ts` are within 4 lines of 300).
6. **Fixture mode.** Where settings live without Rust.
7. **Builds.** The cut into builds with disjoint owned files, their order, and the contract each
   one hands to the next (written out in full: types, commands, functions).
8. **Tests.** Rust tests for the file rules; unit tests that fail for each rule's plausible bug
   (`editor/` and `.vue` get no mutation testing); the real-app steps that prove it (theme at start
   and on a switch, a re-bound key in two opened files, a clash, a hand edit picked up, a broken
   file).

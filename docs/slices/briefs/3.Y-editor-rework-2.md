## Block

### #945 (correctness, block; `frontend/src/editor/internal/format.ts:62`)

**Problem:** #922 is fixed only when an edit keeps the same number of lines. When a formatter splits or joins a line next to an open block and also changes the block's first line, lineDiff gives one LineEdit. `lineChanges` then pairs its lines by position, so text moves across the block's edge. A probe ran the real `formatResult` and `chunkField` (tsx, read-only). (B) Old `function f(a,` / `b) {` / one-line block `B1` / `}`, formatted to `function f(a, b) {` / `  B1` / `}`: the block becomes `ignored ignored` with no arrows, even though `  B1` is still in the Result. This is the exact symptom #922 reported. (A) Old `foo(x, y)` / `B1` / `B2`, formatted to `foo(x,` / `  y)` / `  B1` / `B2`: the block becomes `"  y)\n  B1\nB2\n"`, so applying a side deletes `  y)` from the Result. (B2) With a two-line block the block loses its first line. (C, open risk 1) A blank line the formatter adds after a reindented last block line joins the block. The added tests only cover reindents that keep the line count. Each would still pass if pairing across block edges were wrong, so none of them catches this.

**Fix:** Inside each LineEdit, pair lines with a second `lineDiff` on whitespace-free keys (`line.replace(/\s+/g, "")`). Reindented lines then always pair with themselves, and positional pairing and the extra-line insert or delete happen only in the sub-edits left unmatched. An extra line with no pair goes at the start of the next line, as it does today. Add format tests for (A) split before the block and (B) a join before a one-line block: `pending pending`, the block's own text, and `replace` arrows.

## Settled behaviour (plan §2 #65, #66 — read both rows in full; owner #856 and answers of 2026-10-14)

1. **Save**: a new key action "Save", Ctrl/Cmd+S by default, rebindable in the keymap, working wherever the
   keyboard is in the shown file (any pane, like Undo/Redo's window-wide key, plan #54). It writes the Result
   into the conflicted file in place and **does not stage** it; git still lists the file as conflicted until
   "Mark resolved" (unchanged: writes and stages). Ctrl+S does nothing in the choice and deleted-side views.
2. **Waiting changes are written "what git wrote"**: decided parts as the Result shows them; a conflict still
   waiting is written as **conflict markers**; a one-sided change still waiting is written **applied**, as git
   wrote it. The file never silently loses a side, and when yamt opens the file later it finds those
   conflicts again as waiting.
3. **Own write**: a save is yamt's own write — no "changed on disk" notice for it. A change by anyone else keeps
   plan #52's rule (the disk is the truth, unsaved edits dropped with a notice); a disk change found at save
   time stops the save as it stops "Mark resolved" today.
4. **Dot**: a circle at the right end of the Result header (where "Result [Reset]" is, on the right) while the
   Result differs from what was last saved or opened; undoing back to that text clears it. "Mark resolved"
   also clears it.
5. **Close**: the close question asks only when some opened file has unsaved edits; saved work stays on disk
   after yamt closes, and the next run opens the file from disk (plan #52/#53).
6. **Reset** (#66): back to the file as it was when **this run** of yamt opened it — the index stages captured
   at open and the file's content on disk at open; saves from earlier runs stay. Within one run with no earlier
   saves this equals today's Reset (`restore_stages` + `checkout -m`).

## Sourced facts (given; re-check only [INFERENCE]; file:line in `agent://FormatLintFacts`)

- Only `MergeSession::finish` writes the Result today (`crates/session/src/writes.rs:21-52`): checks the disk
  (`changed_on_disk`, 104-127), `fs::write(root.join(path))`, `git add`, rolls back if staging fails, records
  `seen` (`read_back`). `reset` (88-102): `restore_stages` + `checkout_merge` when
  `stages.can_rebuild_markers()`, then `read_back`. `take` writes a side.
- Session memory per file: `FileState.stages` (captured at `open()`), `FileState.seen`
  (`Seen::GitOutput | ViewFromStages | ViewFromDisk`) and `settled` (last `DiskResult`, `DiskVersion`), written
  only by `session` (project map, state table). `start.rs` reconstructs what git wrote at start
  (`merge_file` through temp files in the system temp folder, `start.rs:308-321`).
- Opening a file whose disk differs from git's output (`Seen::ViewFromDisk`, `seed.rs:97-100`): settled text is
  kept; a marker block located exactly in the stages becomes a waiting change showing its base lines; an
  inexact block or a raw region keeps its lines verbatim, markers included (plan #53).
- Git's marker shape depends on `conflict-marker-size` (gitattributes, `attributes.rs:7-11`), `merge.conflictStyle`
  (merge / diff3 / zdiff3) and labels [INFERENCE: check what yamt already reads in `merge_config.rs:26-30` and
  `start.rs`].
- Window: the Result's text and every change's per-side status (`pending | applied | ignored`) live in the
  editor's `chunkField`; `resultText()` is the Result pane's text (`editor/index.ts:262-264`). A waiting change
  shows base text, possibly edited by the user (a pending block stays pending when edited, `apply.ts:60-63`).
  A conflict can be half decided (one side applied or ignored, the other waiting).
- Unsaved work exists today: a non-reactive baseline `let` in `useMergeController` set when the controller is
  built and replaced by `markSaved` after a successful finish; `closeGuard.ts` tracks `{ unsaved, markSaved }`
  per opened file; the close question is `question.ts:46-52` ("Cancel File Merge" / "Are you sure you want to
  exit without applying changes?" / Exit / Cancel).
- A disk change or reset rebuilds the file's view (`useMergeController.ts:113-126`): text, statuses and undo
  are dropped. Disk checks happen at start, on window focus, before each write and at close — no watcher
  (plan #49, #52).
- Adding a key action: `ipc/keys.ts` (`KeyAction`, `KEY_ACTIONS`, `DEFAULT_KEYS`), `ui/keyText.ts`
  (`ACTION_NAMES`, `ACTION_PLACES`, `KEYMAP_GROUPS`), no Rust change (keys are opaque in `yamt-settings`).
  Window-wide keys: `MergeView.vue:58` → `historyKey` (the pattern to copy).
- The Result header is in `MergeView.vue` (the "Reset" button, ~160-173).
- Commands are plain synchronous `fn`s over one `Mutex<MergeSession>`; command bodies ≤ 15 lines delegating to
  `session` (architecture §3.5); fixture mode (`ipc/fixture.ts`) must keep working.

## What to design (open)

1. **Composing "what git wrote"**: where the bytes to write are built (window from statuses + text, Rust from
   stages + statuses, or split), the IPC shape (what the window sends: text, per-change statuses, edited
   waiting text), and the rules for every case: both sides waiting; half-decided conflicts; a waiting block the
   user edited; a waiting one-sided change; line endings (`eol`) and encodings; marker size, style and labels.
   **Required property: round trip** — save, then open the file in a new session, shows the same waiting
   conflicts (state the cases where it cannot, and what the user sees then).
2. **Own write** in `session`: what `seen`/`settled`/`DiskVersion` become after a save, the reply type, and
   how the window updates its `disk_version` without rebuilding the view (the user keeps undo and statuses).
3. **Reset to this run's start**: what is captured at open (the bytes on disk), how Reset writes them back with
   the stages, and its all-or-nothing behaviour on failure (as `finish`/`reset` today).
4. **The dot and the baseline**: one owner for "saved text" (vision 2), cost per keystroke, how Vue learns of
   changes (no `EditorView`/text in Vue state); after Save the baseline is the text **written**, which differs
   from the Result where conflicts wait — define "unsaved" so the dot clears after a save.
5. **Close question** wording now that "unsaved" means "not saved to disk" (keep two buttons unless you argue
   otherwise; WebStorm's words are the source today).
6. **Save while a formatting step runs or fails**, a second Ctrl+S during a save, Save on a file not shown.
7. Tests that would catch a real bug: the round trip on goldens and the disk-mode cases; own write vs foreign
   write; reset after a save; reset in a second run.

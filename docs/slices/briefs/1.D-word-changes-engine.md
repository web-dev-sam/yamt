# Slice 1.D — word changes in the engine

The owner: on a conflict it is hard to see what exactly changed compared to base; WebStorm draws
the parts of each side that differ from base in a brighter tint, so left and right are easy to
compare. Today a conflict is one red block per side. Decision: plan §2 #30 (visions 2, 4, 5). This
slice computes the word-level changes in `merge-core` and carries them to the frontend's domain
types; the next slice (1.E, `briefs/1.E-word-highlights.md`) draws them. No visible change yet.

## Contract (fixed; you may add private items, never change these)

```rust
// merge-core, next to LineRange (serde::Serialize + specta::Type, like the other chunk types)
/// Changed text inside one line of one text: `len` UTF-16 code units from column `start`
/// (the unit of JavaScript strings and CodeMirror positions). Never contains a line break.
pub struct InlineRange<L> { pub line: L, pub start: u32, pub len: u32 }

/// Where one chunk's sides differ from base, word by word. `base` marks the base text that
/// either side changed (the union).
pub struct WordChanges {
    pub chunk: ChunkId,
    pub local: Vec<InlineRange<LocalLine>>,
    pub base: Vec<InlineRange<BaseLine>>,
    pub remote: Vec<InlineRange<RemoteLine>>,
}

/// One entry per chunk, in the order of `chunks`.
pub fn word_changes(base: &str, local: &str, remote: &str, chunks: &[Chunk]) -> Vec<WordChanges>;

// session
pub struct FileMergeData { /* …existing… */ pub chunks: Vec<Chunk>, pub word_changes: Vec<WordChanges> }
// merge_data fills it from the chunks it computed.
```

Generated TS (for reference): `InlineRange<L> = { line: L; start: number; len: number }`,
`WordChanges = { chunk: ChunkId; local: InlineRange<LocalLine>[]; base: …; remote: … }`,
`FileMergeData.word_changes: WordChanges[]`.

Frontend domain (`ipc/domain.ts`, used by 1.E — write exactly this):

```ts
type InlineRange<L> = { readonly line: L; readonly start: number; readonly len: number };
export type ChunkWords = {
  readonly local: readonly InlineRange<LocalLine>[];
  readonly base: readonly InlineRange<BaseLine>[];
  readonly remote: readonly InlineRange<RemoteLine>[];
};
export type Chunk = { /* …existing… */ readonly words: ChunkWords };
```

`toDomain` joins `word_changes[i]` onto `chunks[i]`: equal lengths and `word_changes[i].chunk ===
chunks[i].id`, else it throws (like a bad brand); lines branded with the existing guards; `start` a
non-negative integer, `len` a positive integer. The fixture schema gains `word_changes` and keeps
`satisfies SchemaOf<Generated.FileMergeData>`. Export `ChunkWords` from `ipc/index.ts` only if 1.E
needs the name (it may reach it as `Chunk["words"]`).

## Behaviour (rules the ranges follow)

- Tokens of a text: a maximal run of word characters (`char::is_alphanumeric()` or `_`); a maximal
  run of whitespace other than line breaks; a line break (`\n`, or `\r\n` as one token); any other
  character alone.
- Per chunk and side: when both the side's chunk lines and the base chunk lines are non-empty and
  differ, diff their tokens with imara-diff (histogram). Changed tokens of the side → that side's
  ranges; changed tokens of base → base ranges. Otherwise that side contributes no ranges
  (insertions and deletions of whole blocks are already shown by the block tint).
- `base` = union of the base ranges from the local diff and the remote diff, overlapping or touching
  ranges merged. `LocalOnly` → remote empty, `RemoteOnly` → local empty, `BothSame` → local and
  remote equal ranges.
- Ranges are split at line breaks; a line break is never inside a range; empty ranges are never
  emitted. On one line, two ranges separated only by whitespace become one range (one highlight
  for "two changed words", as WebStorm draws it). Ranges are sorted by line then start and do not
  overlap.
- Columns count UTF-16 code units of the line's text (a `😀` before a change moves `start` by 2).

## Tests

- Hand-written, each with its exact expected ranges: one changed word (`foo(a, b)` vs `foo(a, c)`);
  two changed words separated by a space become one range; a changed word on a later line of a
  multi-line chunk; a whole line added inside a modified chunk (full-line range, no line break);
  a non-ASCII prefix (`é`, `😀`) before a change; a CRLF chunk (no range covers `\r`); a conflict
  where local and remote change different words (local/remote ranges differ; base = union); a
  `LocalOnly` chunk (remote empty); `BothSame` (equal sides); an add/add chunk (no ranges);
  identical-but-for-whitespace lines (`a  b` vs `a b`: the whitespace run is the range).
- Proptests (`tests/invariants.rs` style, unicode text including multi-unit characters): for every
  generated triple, `word_changes` has one entry per chunk with matching ids; every range lies on a
  line inside its chunk's range on that side, `start + len` ≤ that line's UTF-16 length without its
  line break, `len > 0`, sorted, non-overlapping; for a two-text diff, removing each text's ranges
  and then all whitespace from both texts leaves equal strings; identical texts give no ranges.
- `session` / `cli`: `merge_data` and the `fixture` output carry one `word_changes` entry per chunk.
- `ipc/fixture.test.ts`: a record whose `word_changes` misaligns with `chunks` (length or id) is
  rejected; a real golden's conflict arrives with its words on the domain chunk.

`merge-core` and `ipc/` are mutation-tested (`just mutants`); write tests that a wrong offset, a
missed range or a dropped union would fail.

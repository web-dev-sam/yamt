## Findings to fix

### #927 (boundary, block; `frontend/src/editor/internal/savedPoint.ts:32`)

**Problem:** `typedWhileAllWait` decides on its own which Result text Save drops (`AsShown`, or no changed side decided, via `sideChanged`). `fileText.ts:24` `writtenLines` makes the same decision with a different formula (`isResolved`, then per kind; a half-decided `Markers` keeps the shown lines). The two agree today only because `status.ts` `markConflictSideOrChange` moves both changed sides of a non-conflict together. The dot is defined as "typing that is not written" (brief behaviour 4, plan #69). So any change to the write rules (design open question 1 (b), or a new `Waiting` kind) can clear the dot while the typing is still left out of the file. Growth: every later change to what Save writes has to be made twice, and no test ties the two together.

**Fix:** Put the rule once in `fileText.ts`, as an exported `dropsShownText(span)` built on `status.ts`'s `isSideOpen`/`isResolved`: true for `SideLines` while unresolved and for `Markers` while both sides are open. `writtenLines` should branch on it, and `savedPoint.ts` should call it instead of its own `SIDES.some(sideChanged …)` check.

### #928 (boundary, should; `frontend/src/ui/saving.ts:82`)

**Problem:** `written` (save) and `finish` (lines 55–80) repeat the same handling of a `WriteReply`: `files.value = reply.files`, then `ChangedOnDisk` → `changedOnDisk` → return, then `markSaved`. `store.ts` `reset` and `takeSide` repeat it as well. The brief's "ChangedOnDisk → exactly what finish does" is therefore held by copying, not by sharing. Growth: each new write action adds a fifth copy, and a change to disk-change handling has to find all of them.

**Fix:** Add one `afterWrite(target, path, reply): boolean` to `saving.ts` (it sets `files`, runs `changedOnDisk` and returns whether the write landed) and call it from `finish`, `written`, `reset` and `takeSide`.

### #929 (boundary, should; `frontend/src/ui/saving.ts:115`)

**Problem:** Two claim rules on the one `writing` Set sit in the same module. `whileWriting` (line 39) is named and shared (it takes the claim only if free and releases only its own). `save` writes its exclusive claim inline: it returns if the path is held, then adds and deletes. Growth: a later writer (a status-area "format now", a save-all) has to read both and guess which one to copy. The exclusive rule has no name and no direct test.

**Fix:** Next to `whileWriting`, add a named `claimWrite(target, path, write): Promise<void>` that returns at once when the path is held, and use it in `createSaving().save`.

### #930 (boundary, should; `frontend/src/editor/internal/fileText.ts:50`)

**Problem:** `lineChange` re-implements the final-line-break rule of `apply.ts:49` `wholeLines`: at an unterminated end, an empty replacement deletes from `from - 1`, and no trailing "" is added at the end. It also adds a mid-line case of its own (deviation 5). Two helpers now encode how a span's lines become a `ChangeSpec`, although the brief allowed exporting `wholeLines`. Growth: a fix to one, such as open risk 1's overlap at `from - 1`, misses the other.

**Fix:** Export `wholeLines` from `apply.ts` with the mid-line case moved into it, covered by an `apply.test.ts` case, and call it from `fileText`. If apply must not get the mid-line case, have both functions call one shared end-of-file helper.

### #931 (boundary, should; `frontend/src/ui/store.test.ts:2330`)

**Problem:** The tests for `ui/saving.ts` (`save`, `finish`, the claim) are in `store.test.ts`, not in the `saving.test.ts` the brief's Owned list asks for ("saving.ts (new, +test)", deviation 8). Growth: each module split out of `store.ts` leaves its tests in a 2400-line file, so someone reading `saving.ts` cannot find its rules.

**Fix:** Move the save, finish and claim tests to `ui/saving.test.ts` (they can import `store.test.ts`'s source helpers once those are in a shared test module, or build a `SaveTarget` from refs). Keep a single store wiring test in `store.test.ts`.

### #936 (correctness, block; `frontend/src/editor/internal/savedPoint.ts:61`)

**Problem:** A common case breaks: the user resolves a conflict by typing into the Result while both sides are still waiting, then clicks Mark resolved. `finish` writes `asShown()` (the typing included) and stages it. But `markSaved` re-checks `typedWhileAllWait`, which still returns true, so the dot stays on for good. The close question then lists a file that is fully written and staged, and Ctrl+S cannot clear the dot (a resolved file saves `asShown`, nothing changes). The same happens for any file git already lists as Resolved.

**Fix:** Have the saved point record which text was written (for example `markSaved(written: "asShown" | "fileText")`, with finish and the resolved branch of save passing "asShown"), and apply `typedWhileAllWait` only when the last write was `fileText`. Add a savedPoint test: type inside a fully waiting conflict, mark saved as asShown, and the dot clears.

### #937 (correctness, block; `frontend/src/editor/internal/fileText.ts:14`)

**Problem:** `spanLines` takes whole document lines at `from` and `to`, not only the text inside the span. When a line break at the edge of a half-decided conflict's decided section was deleted, the neighbouring line gets written twice. Checked with @codemirror/state: "a\nL\nz\n" with local applied, delete the break after "L" → span [2,3), `spanLines` = ["Lz"], so the file becomes "a\n<<<<<<< ours\nLz\n=======\nR1\nR2\n>>>>>>> theirs\nz\n" with "z" twice. Deleting the break before "L" writes "a" twice the same way. The edge-break test only covers a conflict with both sides waiting, where `spanLines` is never called.

**Fix:** Build the decided section from the span's own text only: split `doc.sliceString(from, to)` into lines and drop the final empty piece when `to` is at a line start. Add the half-decided case to the test "a line break deleted at a waiting change's edge…" (joined after and joined before).

### #938 (correctness, block; `frontend/src/ui/MergeView.vue:192`)

**Problem:** In a deleted-side view, Keep reloads the file and `keptSideToApply` runs `applyAllNonConflicting` on a controller that is not editable. That changes the text and the statuses, so `unsaved` turns true and the "Not saved" dot appears in the Result header. Yet `take` has just written the file, Ctrl+S does nothing there (plan #65), and the close guard does not track the file. The dot is false and can never be cleared.

**Fix:** Show the dot only for an editable Result (`v-if="editable && unsaved"`). Check it in the smoke: Keep on a deleted-side text file, and no dot appears.

### #939 (correctness, block; `frontend/src/ui/saving.ts:61`)

**Problem:** Surviving mutant `return false` → `true`: answering Back to the "unprocessed" question would make `finishThenMoveOn` switch to the next unresolved file without writing anything. The test "a finish with work left asks; Back writes nothing…" (store.test.ts:616) has no other unresolved file to move to, so it cannot tell. The `boolean` seam is new in this patch, and `finishThenMoveOn` depends on it.

**Fix:** In that test, list b.ts as unresolved and check after Back that `store.active` is still a.ts and no `loadFile b.ts` was called.

### #940 (correctness, block; `frontend/src/ui/saving.ts:45`)

**Problem:** Surviving mutant: `target.writing.add(path)` removed in `whileWriting`, so reset and finish no longer claim the path. The test "a save while a %s of the same file runs is ignored" (store.test.ts:2495) checks only the final `saves` list. That list is the same whether the save was ignored during the reset and sent afterwards, or sent during the reset and skipped afterwards. This test is the only evidence for "finish and reset register in it too" (Behaviour 2), and it passes with that registration deleted. Without the claim, a Save can overwrite Reset's restored bytes: Rust's reset leaves the disk version as it is (writes.rs:102-131).

**Fix:** Right after the in-flight `await store.save(...)` and before answering the reset or finish, add `expect(saves).toEqual([])`.

### #941 (correctness, block; `frontend/src/ui/saving.ts:90`)

**Problem:** Surviving mutants: `.some` → `.every` (line 90) and `file.path === path` → `true` (line 91). The resolved test (store.test.ts:2381) lists only a.ts. Under the second mutant, any resolved file elsewhere in the list makes an unresolved file write `asShown()`: its waiting conflicts go to disk as base text without markers, and the next start stages it. That is exactly the silent loss of a side that plan #65 rules out. Under `.every`, a resolved file in a list of several writes `fileText()` and puts markers back into it.

**Fix:** Add a store.save case with a.ts Unresolved and b.ts Resolved (expect the `fileText` text), and one with a.ts Resolved and b.ts Unresolved (expect `asShown`).

### #942 (correctness, block; `frontend/src/ui/saving.ts:44`)

**Problem:** Deviation 2 lets Reset run while an earlier Save still holds the claim. The window is the Save's wait on `handle.format()`: Reset can write the at-open bytes and start its reload, and then the Save resumes. `handle.snapshot()` still returns the old controller, so the Save sends the pre-reset text with a disk version Rust still accepts, because reset does not change it. The disk ends up undoing the Reset while the view reloads to the reset content with no dot. This is exactly what the design's claim was meant to prevent ("Save cannot slip between Reset's reply and its reload"). It is unreachable today only because MergeView passes `servers: null`, so `format()` returns at once. The status-area slice that wires servers will make it reachable without touching this file.

**Fix:** Make the claim exclusive both ways: reset and finish wait for, or refuse during, a save's claim. Or let save drop its write when another write to the path started during `format()` (for example a per-path counter that reset and finish increase, checked before `snapshot()`). Add a store test where format is still pending while a reset completes.

### #943 (correctness, should; `frontend/src/ui/store.ts:272`)

**Problem:** Surviving mutant in reset's `taken` filter (the line only moved into `whileWriting`; the gap existed before). Dropping every taken side on any reset passes, because "reset of a taken choice forgets only its side…" (store.test.ts:1214) has no second taken file. If this stays, any later change to how reset clears `taken` goes unnoticed.

**Fix:** In `takenChoice`, also take REMOVED, then check that after the reset of LOGO, `taken` still holds REMOVED.

## Blocks to fix (from the final run, verbatim)

1. **#1632 — "horizontal scroll leaves the box in place" fails:** `AssertionError: expected -253.59375 to be 46.40625`
   at `rangeThreads.browser.test.ts:280` (`expect(host.getBoundingClientRect().left).toBe(before)`) after
   `scrollDOM.scrollLeft = 300`. The box moved by the whole scroll. Plan §2 #116 and the original brief: "rows stay put
   under horizontal scroll" (`.cm-thread-row` is `position: sticky; left: var(--thread-left); width:
   var(--thread-width)`, the vars written by `ThreadHosts.#placeColumns`). First find out, with observed values, why
   the row does not stick in WebKit (the vars unset at that moment, the row as wide as `.cm-content`, a containing
   block or overflow in the way, the test's own setup…), **then decide whether the product or the test is wrong**:
   - Product wrong (a box in the real window also slides away sideways): fix it so the box stays put, the test unchanged.
   - Test wrong (the real window keeps the box still): fix the test so it fails when stickiness is removed and passes
     with it.
     Either way, show the box staying put in the **range window on the fixture page in MiniBrowser** (engine of record):
     a thread open on a file with a line longer than the column, the column scrolled sideways, the box's `left` before and
     after, and one screenshot.
2. **#1633 — "a removed line's row in a pure deletion is inside the band in both columns…" fails:** `AssertionError:
   expected undefined to be 200` (the `.cm-thread-row` query at :309 finds nothing). The failure screenshot shows the
   left column at line 196, not near line 301: [INFERENCE] `lineTop` (`view.lineBlockAt(...).top`) is read before
   CodeMirror has measured the lines, so the scroll target uses the estimated line height and the row at line 301 is
   never drawn. Confirm or refute with observed values, then fix (product or test, as in 1). The test must still fail
   under the round-1 mutation M4 ("`columnSpan` always uses `rangeSpan`": the right band collapses to a point).

## How to run the browser tests here

`pnpm -C frontend test:browser` cannot start Playwright's WebKit on this host (`libicudata.so.74`). The final run built
a private one at `/tmp/yamt-pw/webkit-2370` (Ubuntu noble's libicu74, libxml2 2.9.14, libflite1 in
`minibrowser-wpe/sys/lib`). Copy `/tmp/yamt-pw/vitest.probe.verify.config.mts` to your own scratch file with your
worktree's paths (it merges `frontend/vite.config.ts` and adds `/tmp` to `server.fs.allow`), then:
`PLAYWRIGHT_BROWSERS_PATH=/tmp/yamt-pw pnpm -C frontend exec vitest run --config <your copy> --project browser
src/editor/range.browser.test.ts src/editor/rangeThreads.browser.test.ts`. Do not change `/tmp/yamt-pw` itself.

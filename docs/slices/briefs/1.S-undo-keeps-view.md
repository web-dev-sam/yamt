# Slice 1.S — undo after applying a change keeps the view on that change

Bug (board row 8, finding #201, present since 1.4): after applying a change with an arrow (`»`/`«`),
ignoring it (`×`) or a bulk apply, Ctrl+Z or the toolbar Undo restores the text and status but
scrolls the middle pane to line 1. Cause (confirmed in `@codemirror/commands`): a history event
remembers the selection from **before** its transaction, and `undo`/`redo` dispatch that selection
with `scrollIntoView: true`. Arrow clicks never move the cursor (the strip keeps the middle pane's
focus on `mousedown`), so the remembered selection is usually wherever the cursor was, often
position 0.

## Behaviour (what the user sees)

- **Arrow or `×` on a block:** the middle pane's cursor moves to the start of that block's first
  line in the middle pane, without scrolling (the block is on screen — its arrow was just clicked).
  Then Ctrl+Z / toolbar Undo, and Ctrl+Shift+Z / toolbar Redo, restore text and status together
  and show that block: the view does not move while the block is on screen; if the user scrolled
  away meanwhile, the view scrolls to the block (IntelliJ shows what was undone).
- **Bulk apply (toolbar):** if the cursor is outside the visible part of the middle pane, it moves
  to the start of the first fully visible line before applying; otherwise it stays. Undo/redo then
  return to where the user was looking when they pressed the button (no move if still there).
- Never a jump to line 1 caused by an old cursor position.
- Unchanged: one undo step per action, bulk apply included (CM7); text and status restored
  together, status only through the `invertedEffects` path in `chunkField.ts` (CM2); the arrows
  keep the middle pane's focus (`keepEditorFocus` in `strips.ts`); typing after an arrow click
  types at the new cursor position.

## Contract

- `MergeController`'s public surface unchanged.
- The cursor move must be its own transaction dispatched **before** the action's transaction
  (history takes the remembered selection from the action transaction's start state), must not
  add an undo step, and must not scroll.
- Keep the decision testable without a DOM: `apply.ts` decides where the cursor goes (from the
  state, the block, and — for bulk — a visible line range the controller passes in);
  `MergeController` only measures the visible range and dispatches.

## Tests (`apply.test.ts`, `EditorState` with `history()`)

- Cursor at position 0, apply a block far below it, `undo`: the selection head lies inside that
  block's current span; `redo`: still inside it. Same for `×` (status-only) and for a
  `BothSame`/conflict block applied from either side.
- Bulk apply with the cursor outside a given visible range: after `undo` the head lies inside that
  range; with the cursor inside the range it is unchanged.
- `undoDepth` grows by exactly one per action; the existing undo/status tests stay green.

`editor/` is outside the mutation run: break each tested rule by hand once (skip the cursor
move; put the selection into the action transaction instead of a separate one; move the cursor
to the block's end line in the wrong pane's coordinates), paste each failing assertion, restore.

# Slice 3.X-probe — measure what makes yamt's code text softer than WebStorm's

Board "Crisp code text" row 1. An investigation: you change no repository file. Your measurements decide what the build
slices change, so every number must come from a run you did, with the command.

## Target

Owned: nothing in the repository. Scratch only: `/tmp/yamt-crisp/**` (scripts, screenshots, crops, the report).
Read-only: the whole repository. You may build the app (`cargo tauri build --debug --no-bundle`, writes `target/`) and
start dev servers on your own ports.

Non-goals: any product change; the owner's real screen (VF9: screenshots only from a private Xvfb display or a WebDriver
session; never the desktop); macOS (no Mac here).

## Given facts (sourced; use them, do not re-check)

- Owner's screen: Samsung 3840×2160 at KDE scale 1.45 on Wayland (`~/.config/kwinoutputconfig.json`). GTK3 has no
  fractional scale on Wayland: yamt draws at 2× and KWin scales the buffer to 1.45. WebStorm 2026.2 runs on its Wayland
  toolkit and logs `System scale factor: 2.0 (JRE-managed HiDPI)` (`~/.cache/JetBrains/WebStorm2026.2/log/idea.log`), so
  it is scaled down the same way.
- System font settings: `Xft.rgba: none`, `Xft.hintstyle: hintslight`, `XftSubPixel=none` (kdeglobals). WebStorm's
  editor font settings are its defaults (`options/editor-font.xml` has no entries): JetBrains Mono 13, line spacing 1.2.
- WebKitGTK 2.54.1 (`pkg-config --modversion webkit2gtk-4.1`). Its GTK3 port follows the system's font settings
  (`Source/WebCore/platform/graphics/FontRenderOptions.h`: `s_followSystemSettingsDefault = true` for GTK3;
  `FontRenderOptionsSkia.cpp` maps antialias `Subpixel` → `SkFont::Edging::kSubpixelAntiAlias` and the subpixel order to
  `SkPixelGeometry`, used by `createSurfaceProps`). Whether the GPU or the CPU painting path honours it is unknown: that
  is question 1.
- yamt's code text (`frontend/src/editor/internal/pane.ts:70-102`): `@fontsource/jetbrains-mono/400.css` (static 400
  woff2), `fontSize 13px`, `.cm-scroller` `lineHeight 1.4` (18.2 px), ligatures off, colour `--color-code` #bcbec4 on
  `--color-panel` #191a1c (`frontend/src/style.css:13,19`). `.cm-scroller` and `.cm-content` have no background of their
  own; gutters are sticky with an opaque background; the two strip wrappers (no text) have `will-change: transform`
  (`frontend/src/ui/MergeView.vue:181-193`).
- The app on a private display: `just app-session start-app …` (see `frontend/scripts/app-session/args.ts` USAGE; it
  starts Xvfb with `GDK_BACKEND=x11`, a private HOME/XDG_CONFIG_HOME, passes the parent environment through, `shot
  --display` grabs the X display = what was really composited). `src-tauri/src/graphics.rs` sets
  `WEBKIT_DISABLE_DMABUF_RENDERER=1` when `/sys/module/nvidia` exists, as on the owner's machine.
- Scroll timing harness: `.omp/run/scroll-timing.py` (read its header; trial repository in `~/yamt-trial/vue-merge-yamt`,
  clone it per the header, never modify it). A frame over 20 ms is late.
- WebStorm's rasterizer: the JetBrains Runtime at `~/.local/share/JetBrains/WebStorm-262.10968.77/jbr/bin/java`; find
  `JetBrainsMono-Regular.ttf` inside that WebStorm install.
- Playwright's Chromium is installed (`~/.cache/ms-playwright/chromium-1248`); the `playwright` package is reachable from
  `frontend/node_modules` [INFERENCE: check].

## Change (what to do)

1. **Reference crops (WebStorm).** A single-file Java program run with WebStorm's `java`: draw 20 lines of
   `tests/golden/<one .ts case>/local.ts` (pick lines that are unchanged on both sides, so yamt shows them without
   change tints) in JetBrains Mono 13 from WebStorm's own TTF, `KEY_TEXT_ANTIALIASING = VALUE_TEXT_ANTIALIAS_LCD_HRGB`,
   fractional metrics off, LCD contrast 140 (Java2D's default), #BCBEC4 on #191A1C, once at scale 1 and once with
   `g.scale(2, 2)`. Line height: print `FontMetrics` ascent/descent/leading/height at 13 and report `ceil(h × 1.2)` and
   `round(h × 1.2)` (what WebStorm's editor uses for line spacing 1.2 [INFERENCE]). Save PNGs.
2. **yamt crops.** Same 20 lines in the real app on Xvfb, the file open in the panes. For comparable crops, inject a
   style through `app-session read` that makes every code token #bcbec4 (`.cm-content, .cm-content * { color: #bcbec4
   !important }`) and pick the same lines. Configurations (each a fresh `start-app`):
   - C0 as today; C1 GTK settings `gtk-xft-antialias=1`, `gtk-xft-rgba=rgb`, `gtk-xft-hintstyle=hintslight` (a
     `gtk-3.0/settings.ini` in a directory you put first in `XDG_CONFIG_DIRS`; no XSETTINGS manager runs on Xvfb);
     C2 = C1 + `WEBKIT_SKIA_ENABLE_CPU_RENDERING=1`; C3 = C0 + `WEBKIT_SKIA_ENABLE_CPU_RENDERING=1`.
   - Each at scale 1 (1600×1000) and at `GDK_SCALE=2` (3200×2000).
   - For C1 and C2 also with an injected `.cm-scroller { background-color: var(--color-panel) }` (does a transparent
     scroller block subpixel text?).
   - Record which renderer each run used: the libraries mapped in the WebKit processes (`/proc/<pid>/maps`: NVIDIA EGL,
     Mesa llvmpipe/gallium, none) and whether `WEBKIT_DISABLE_DMABUF_RENDERER` was set.
3. **Owner's-screen simulation.** Scale every 2× crop (yamt and WebStorm) to 72.5 % with a linear filter (`magick
   -filter Triangle -resize 72.5%`; KWin's scale-down is linear [INFERENCE]).
4. **Metrics** per crop, one script for all: background = #191A1C; ink pixel = luminance differs from background by > 10;
   `fringe` = share of ink pixels whose per-channel difference from the background spreads (max − min) by > 24 (grey
   antialiasing stays < 6); `ink` = mean coverage (luminance step / full step to #BCBEC4) over the crop (stroke weight);
   `core` = share of ink pixels with coverage > 0.9 (stem contrast); `edge` = mean absolute horizontal coverage step on
   ink rows (sharpness). One table: config × scale × metric, WebStorm rows first.
5. **Side-by-side images** for the owner: per scale (1, 2, 2→1.45), one PNG of the same 6 lines × ~40 columns at 400 %
   nearest-neighbour, labelled columns: WebStorm | C0 | C1 | C2 (and the best opaque-scroller variant).
6. **Baselines.** At scale 1 and 2 under C0 and the best config: is the same glyph drawn with identical pixels on
   different lines (baseline snapped to device pixels) with `line-height: 1.4` vs an injected `20px`? Show one glyph's
   row profile on three lines for each.
7. **Live switch.** If an XSETTINGS manager (`xsettingsd`) is installed: start C0, then switch `Xft/RGBA` to `rgb` while
   the app runs: does the open window repaint with fringes without a restart? If none is installed, say so.
8. **Scroll timing** with the harness, "all opened", middle pane, `renderer.ts`, for C0, C1 and the best config, at
   scale 1 and at `GDK_SCALE=2` 3200×2000; three runs each, report the median row. Xvfb numbers are relative only.
9. **Chromium's layer rules (stand-in for Windows' WebView2).** The fixture page (`pnpm -C frontend dev --port <own>`)
   in Playwright's Chromium, headed on a private Xvfb, with `FONTCONFIG_FILE` pointing to a config that includes the
   system one and assigns `rgba=rgb`, `antialias=true`, `hintstyle=hintslight`; device scale factor 1 and 1.5. Measure
   `fringe` on code text in each pane and on the line numbers, with: (a) nothing injected, (b) `.cm-scroller {
   background-color: var(--color-panel) }`, (c) (b) + `.cm-line { isolation: auto }`, (d) (b) + the strip wrappers
   without `will-change`. Also after scrolling a pane 1000 px. Name the smallest variant that gives subpixel text in all
   three panes and the gutters. If Chromium's DevTools protocol reports LCD-text reasons per layer, include them.

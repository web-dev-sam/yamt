## Behaviour (what the user sees)

**Toolbar and Reset** (#48).

- "Mark resolved" is the first thing in the toolbar, at its left end next to the file list, before
  the apply/undo/redo icons and the status line.
- Its look follows the open file's summary: filled blue (today's primary style) when nothing is left
  ("All changes processed": no changes and no conflicts), outlined like Reset while changes or
  conflicts remain. Clicking it behaves as today (the "Unprocessed Changes" question when something is
  left).
- "Reset file" leaves the toolbar. A button "Reset" sits in the "Result" column header, next to the word
  "Result", same outlined style; it is the only reset button. It does what "Reset file" did.

**Next file** (#48, #421). After a successful "Mark resolved" (with or without the question), "Keep",
"Delete" or "Take left/right", the window opens the next file in list order after the current one whose
mark is unresolved, wrapping to the top; when none is left it stays on the current file (the "All files
are resolved" bar shows as today). A mark that changes for any other reason never switches files.

**Marks follow git** (#49). Whenever the window gets focus, it asks for the file list again and updates
the marks (and the "All files are resolved" bar) without switching files, touching open editors, or
clearing a problem about something else. A failure shows as today's "list" problem.

**Right header** (#50, #422). The left header stays "Local (yours)". The right header reads "Remote
(theirs): minor" for `RemoteName.Branch`, "Remote (theirs): 1a2b3c4 Fix parser crash" for
`RemoteName.Commit` (short id + subject; hovering shows the full message), "Remote (theirs)" when there
is no name or asking for it failed (no problem bar for that; log a warning). Long names cut off with an
ellipsis, the full text on hover. The name is asked for once at start. Same headers in every view.

**Deleted on one side, other side text** (#47, #408). A file whose `FileMergeData.deleted` is not
null opens in the three-pane view with the editor's read-only mode (`{ readOnly: true }`):

- the kept side's pane shows its text with its changes against base highlighted; "Keep" (outlined
  button) sits in that side's header next to its title;
- the middle shows base until a choice;
- the deleted side's column shows, instead of its pane, today's choice wording: "Deleted in this
  branch." and the "Delete" button under it;
- the toolbar shows no Mark resolved, apply, undo or redo (nothing to do there for this file).
- "Keep" → `takeSide(kept)`; on success the middle shows the kept text (the controller's
  `applyAllNonConflicting(kept)`), the buttons hide, the file's mark turns resolved, and the window
  moves on (above). "Delete" → `takeSide(deleted)`; on success the middle column shows "Resolved by
  deleting the file." instead of its pane, buttons hide, move on.
- "Reset" (Result header) is enabled once a side was taken and brings the file back as it was opened
  (base in the middle, both buttons).
- Coming back to such a file later shows it as it was left.

**Files the editor cannot show** (ChoiceView, #48): three columns like the other views — "Local
(yours)" | "Result" | right header — so "Reset" can sit in the "Result" header (enabled once a side was
taken). The side columns keep today's sentence and button under it. The Result column says "Keep the
file or delete it." / "Take the left or the right version." before a choice and today's "Resolved
with …" line after it. The bar above keeps its height (no jump when switching files) and holds nothing.

**File list width** (#48, #417). A thin handle on the file list's right edge; dragging it changes the
list's width between 10rem and half the window (col-resize cursor). The panes follow (their connectors
repaint on their own).

## Contract

- What 3.G gave (generated in `ipc/bindings.ts`, already regenerated; `pnpm typecheck` fails until this
  task adapts `ipc/`): `commands.listFiles` now returns a typed result (`FileEntry[]` or `IpcError`:
  it re-reads git, so it can fail); `commands.remoteName()` returns
  `{ kind: "Branch"; name } | { kind: "Commit"; short_id; subject; message } | null` (exported type
  `RemoteName`; it never fails, a git problem is already `null`); `FileMergeData.deleted: Side | null`
  (a deleted-on-one-side text file: that side's text is base, every chunk one-sided). Until this task
  lands, such a file (`docs/removed.md` in the smoke repo) opens in the normal editor.
- `ChunkSource.listFiles` becomes `Promise<SourceResult<FileEntry[]>>`; `ChunkSource` gains
  `remoteName(): Promise<RemoteName | null>`; `createTauriSource` maps both (string-error rule #305 as the
  others); the fixture source answers `null`. `RemoteName` reaches `ui/` through `ipc/index.ts`
  (IPC2). The fixture valibot schema accepts `deleted` (`"local" | "remote" | null`; the regenerated
  fixture JSON has `"deleted": null`).
- What 3.E gave: `new MergeController(data, hosts, { readOnly: true })` (`MergeOptions` from
  `editor/index.ts`): middle refuses user edits, no icons, no drag, no Ctrl/Cmd+click, find works,
  `applyAllNonConflicting(side)` works; `undo()`/`redo()` return false in read-only mode.
- Words: one pure function per concern in `ui/` with tests (header text + tooltip from a side and a
  `RemoteName | null`; the Result column's line for choices). `SIDE_HEADERS` goes if nothing else
  needs it.
- The next file: one pure function `(files, active) → path | null` with tests (wrap, none left, the
  current file is the only unresolved one, active not in the list).
- The side taken for a deleted-side text file lives in the store next to the choices' `taken` (one
  owner for "which side was taken", project-map state table); Vue state never holds document text or
  an `EditorView` (VU10).
- Window focus through `@vueuse/core` in `ui/` (VU12) or `ipc/window.ts` (the only
  `@tauri-apps/api/window` importer); check in the real app that it fires when the window comes back.
- Actions stay in `store.ts` (VU9), every non-test file ≤ 300 lines, every function ≤ 40 (oxlint).
  `store.ts` is at 289 lines: move pure logic out into tested modules; if actions alone do not fit,
  propose the split in `deviations_from_brief` instead of raising a limit. A new component needs a
  one-line reason (VU15). Name every new file in `deviations_from_brief` (the orchestrator updates the
  project map).

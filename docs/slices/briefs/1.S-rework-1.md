## Findings (verbatim) and decisions

### #219 block (correctness, CM2) — redo after an insert-only apply lands after the block

> After an apply that only inserts lines (chunk 4 in magic-keys: empty base range), redo maps the
> remembered cursor with assoc 1 and puts it at span.to, the start of the line after the block
> (probe: span [4,8), redo head 8). If the user undoes, scrolls below the block and redoes, the
> inserted lines stay just above the top edge, which breaks the brief's rule that redo shows the
> block. expectHeadInside (apply.test.ts:84, `toBeLessThanOrEqual(to)`) was widened to allow this,
> so it does not enforce the brief's 'redo: still inside it'.
>
> Fix: After the action, dispatch a selection-only step that history records, with the cursor at
> the block's new `from`. History stores it in the event's selectionsAfter[0], which `redo` uses
> before the mapped start selection; in the probe, redo head is 4 and undoDepth is unchanged. Then
> make expectHeadInside require `head < to` for non-empty spans. The brief's Contract only
> describes the cursor move before the action, so the orchestrator must approve this added step.

**Decision:** approved, for all three actions (arrow, `×`, bulk). The step order becomes:

1. cursor move, outside history;
2. the action;
3. a cursor step that history records, with no scroll.

The cursor in step 3 is where step 1 put it, mapped through the action so it stays at the block's
start; for bulk, the moved or unchanged cursor, mapped the same way. Contract addition to the
original brief:

- step 3 adds no undo step;
- step 3 must not scroll;
- `head < to` for non-empty spans after undo and after redo.

### #220 should (correctness, CM7) — typing right after an arrow click joins the apply's undo step

> The cursor now always sits next to the applied change, so typing within history's 500 ms
> newGroupDelay after an arrow click joins the 'input.type' change into the apply's undo event. In
> the probe, undoDepth stays 1 and one undo removes both the typed 'z' and the apply. That breaks
> 'one undo step per action'; before this patch the cursor was usually somewhere else.
>
> Fix: The post-action selection step from the first finding fixes this too, because addChanges
> only joins when lastEvent.selectionsAfter is empty (probe: depth 2). Alternatively, add
> `isolateHistory.of("after")` to the action spec. Either way, add a test: apply, then an adjacent
> `input.type` change ⇒ undoDepth +2.

**Decision:** fixed by step 3. Add the test, with the typed change at the same timestamp as the
apply, so the join would happen without step 3.

### #221 should (correctness) — nothing guards that steps are separate dispatches

> Nothing automated guards that the steps go out as separate dispatches. A refactor to
> `this.#views.center.dispatch(...steps)` still type-checks (Steps is a TransactionSpec[]) but
> merges the move into the action transaction, which brings back the jump to line 1. apply.test.ts
> would stay green because its run() has its own loop.
>
> Fix: Export one `dispatchSteps(dispatch: (spec: TransactionSpec) => void, steps: Steps)` from
> apply.ts. Have MergeController.#dispatch and the test's run() both call it, so the node tests
> exercise the production loop.

**Decision:** as proposed.

### #222 should (correctness) — bulk bounds untested

> The bulk test only puts the cursor on line 1 and line 120 for the visible range 100–130.
> Off-by-one changes to cursorInView's `>=`/`<=` bounds, or moving the cursor to a non-line-start
> on the first line, would still pass because only the line number is checked.
>
> Fix: Add cursors on lines 100 and 130 ⇒ unchanged after undo, and on lines 99 and 131 ⇒ head ===
> doc.line(100).from after undo.

**Decision:** as proposed.

### #214 should (boundary, principles §2) — `cursorInView` name

> `cursorInView` reads like a boolean check, but it returns the position to move the cursor to,
> and that is non-null exactly when the cursor is _not_ in view. A reader of `bulkApplySteps` has
> to open the function to learn what `null` means.
>
> Fix: Rename it to describe what it returns, e.g. `cursorIntoView` or `bulkCursorTarget`, so that
> `null` reads as 'no move needed'.

**Decision:** `bulkCursorTarget`.

### #215 should (boundary, principles §1/§2) — two independent nullables in `steps`

> `steps(cursor | null, action | null)` takes two independent nullables. As a result,
> `applySteps`/`dismissSteps` look up the span twice (once here, once inside applySpec/dismissSpec)
> and pass `?.from ?? null` for a combination that cannot happen: whenever the action is non-null
> the span exists. The `cursor === null` branch is reachable only from bulk.
>
> Fix: Resolve the span once in `applySteps`/`dismissSteps` and return `[]` or
> `[moveCursor(span.from), action]` directly (sharing a private `moveCursor(pos)` spec builder).
> Keep the `cursor === null ? [action] : [moveCursor(cursor), action]` choice only in
> `bulkApplySteps`.

**Decision:** as proposed, extended to the three-step shape from #219.

### #216 should (boundary, TS7) — three positional arguments on new exports

> The new exported `bulkApplySteps(target, side, visible)` and `applySteps(target, chunk, side)`
> take three positional arguments. apply.ts is not one of the per-frame paths TS7 exempts. They
> copy a TS7 breach already present in `applySpec`/`applyChange`.

**Decision:** object parameters for the exported step builders with three inputs:
`applySteps({ target, chunk, side })` and `bulkApplySteps({ target, side, visible })`.
`dismissSteps(target, chunk)` keeps two positional arguments. The private helpers may stay as they
are; once #217 lands, nothing outside apply.ts sees them.

### #217 nit (boundary) — two API pairs for the same actions — rides along

> apply.ts now exports two API pairs for the same actions: `applySpec`/`dismissSpec`, used only by
> words.test.ts, and `applySteps`/`dismissSteps`, used by the controller and apply.test.ts. A test
> written against the `*Spec` pair exercises a path that production code no longer dispatches on
> its own.

**Decision:** do it now. Switch `words.test.ts` to `applySteps`/`dismissSteps` through
`dispatchSteps`, and make `applySpec`/`dismissSpec` module-private.

Orchestrator item for the rules review; not in this round.

## Change

1. **`scripts/demo-repo.sh <dir>`** builds a git repository in an empty `<dir>`, stopped mid-merge with conflicts:
   - **A believable small TypeScript web project** in a domain any reader recognizes (the old screenshot used a shop's
     cart; pick freely): `package.json` with `typescript`, `oxlint` and `oxfmt` as devDependencies, `tsconfig.json`,
     `.oxlintrc.json`/`.oxfmtrc.json` as such a project would have them, `node_modules` linked from this checkout's
     `frontend/node_modules` the way `lsp-repo.sh` does it (package.json copies, git-ignored).
   - **A real-looking history:** a few base commits, `main` with the user's work, a colleague's `feature/<name>` branch,
     plausible author names and messages, then `git merge feature/<name>` stopping. No user or system git config (risk
     RK19, `git-sandbox.sh`). Prints the conflicted paths; `expected_conflicts` exact.
   - **The tree:** 6–8 conflicted files two or three folders deep (e.g. `src/<area>/…`, `docs/…`, `public/…`): mostly
     TypeScript, one Markdown doc, one image changed on both sides, one file deleted on one side and changed on the
     other (these two keep the manual cases the old button's project gave).
   - **The long file** (the screenshot's): 350–600 lines of believable code where both sides changed different places
     — insertions and deletions on each side, modifications, one or two conflicts — spread through the file so that
     with collapsing on (the default) the view still needs scrolling and the minimap shows a box.
   - **Problems:** one TypeScript error the merge itself causes (e.g. the colleague renamed something the user's new
     code still uses; a "Did you mean …?" message reads well) and one oxlint warning, outside conflicted lines. They may
     show as yamt opens the file, or after a few Apply clicks a user would make anyway: say which.
   - **Not overloaded:** an ordinary amount of change, nothing contrived, readable at a glance.
   - The TypeScript language server comes from `lsp-servers.sh` into the user's cache (once; the network the first
     time); print the PATH line to launch yamt with. Header comment: what the project holds and why (as
     `lsp-repo.sh`'s). Store each side's files as plain files under `scripts/demo/` (or another layout that keeps the
     code readable and editable; say why).
2. **`.vscode/tasks.json`:** "merge: new conflict project" (button "conflict") replaces `/tmp/yamt-conflict-project`
   with the demo project; "merge: open in yamt" (button "yamt") makes it if missing and opens it with the servers-path
   folder first on PATH, as "lsp: open in yamt" does; "merge: open in WebStorm" makes it if missing with the same script.
   Their `detail` texts describe the new project. The other tasks are unchanged.
3. **The screenshot** (you do not commit it): the real app on a private display through the app-session helper, real
   input only (no DOM edits, injected styles or scripted scroll positions in the final state), a 1600×1000 window at
   device scale 2 → a 3200×2000 PNG, dark theme, greyscale antialiasing, a scratch settings file and storage. One
   image holding:
   - the file list as a tree, the long file selected;
   - the default toolbar; the status area with the error and warning counts and oxfmt, oxlint, TypeScript running;
   - the long file scrolled so the view shows several kinds of change (an insertion, a removal bar, a modification, a
     conflict) and a collapsed wave;
   - the pointer resting on the TypeScript error, its tooltip shown;
   - Alt held: the minimap at the right edge, its box away from the top, problem marks on its left edge, change marks
     on its right edge.
     If two of these cannot coexist with real input (e.g. pressing Alt closes the tooltip), say which and how you tried,
     and give the best real alternative. Leave the chosen image at `/tmp/yamt-demo/screenshot.png`, other candidates

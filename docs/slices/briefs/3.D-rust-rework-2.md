## Findings (verbatim)

- **#536** (boundary, should) `src-tauri/AGENTS.md:1` — The module map still says `commands.rs (commands ≤ 15 lines delegating to session, IpcError, one Mutex<MergeSession>)` and never names ipc_error.rs, although IpcError and its mapping from session errors now live in src-tauri/src/ipc_error.rs. *Fix:* Drop IpcError from the commands.rs entry and add `ipc_error.rs` (`IpcError`, mapped from `yamt_session::Error`).
- **#537** (boundary, should) `crates/session/src/start.rs:45` — The MergeDriver docs describe the old attribute-only mapping. The enum doc still reads "The `merge` attribute (gitattributes(5) \"Built-in merge drivers\")" and Custom still reads "Any other driver: what it wrote cannot be known". But Custom now means only a configured `merge.<name>.driver`, an unconfigured name is Text, and Binary also comes from `merge.default=binary`. *Fix:* Reword the enum doc as 'the driver git used, resolved from the attribute and the merge config (merge_driver)', and Custom as 'a `merge.<name>.driver` from the config: what it wrote cannot be known'.
- **#538** (boundary, should) `src-tauri/src/ipc_error.rs:42` — Session NotAFile crosses as WriteFailed with a yamt-written English sentence in `message` (NOT_A_FILE). The same words are also in session lib.rs:46 `#[error("cannot write {path}: it is not a regular file")]`, so two copies can drift. The window cannot tell this refusal from an io failure, although failure wording belongs to ui/problemText.ts. *Fix:* Propose a structured `IpcError::NotAFile { path }` to the orchestrator before bindings are regenerated, so problemText words it. If WriteFailed is kept, define the phrase once in session and reuse it in both the `#[error]` and the IPC mapping.
- **#539** (boundary, should) `crates/session/src/seed.rs:24` — The doc on `base_end` ("Where the previous chunk's base lines end; the next chunk's start no earlier.") restates the field name, and its second half repeats the invariant already stated on after_previous_base. *Fix:* Rename the field `previous_base_end` and delete the doc comment.
- **#540** (boundary, nit) `crates/session/src/disk.rs:73` — Settlement mixes actions (Add, Remove, LeaveAsIs) with a result name (MarkersLeft), and LeaveAsIs/LeftAsIs differ from DiskResult by one word while MarkersLeft matches it exactly. *Fix:* Rename `Settlement::MarkersLeft` to `LeaveWithMarkers { conflicts }` so all four variants read as actions.
- **#541** (correctness, should) `crates/gitio/tests/what_git_wrote.rs:292` — `Repo::merge_config` and `attributes` read the developer's global config, but the conflict repos were merged without it. So `cargo test` fails on a machine whose ~/.gitconfig sets `merge.default=binary` (45 failures, among them every disk_is_truth test, e.g. `an_unchanged_disk_reports_nothing…` gets `MarkersLeft{2}`) or has mergiraf's recommended global driver plus attributes (45). A global `merge.<name>.driver` alone breaks `no_config == MergeConfig::default()`. *Fix:* Run the gitio/session test binaries with the user and system config isolated, e.g. export `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1 XDG_CONFIG_HOME=<empty dir>` in `just test` (and document it for bare `cargo test`). In the gitio test, assert only what the repo-local keys add (`config.default == binary`, `config.drivers.last() == mergiraf`), not equality with the default.
- **#542** (correctness, should) `crates/gitio/tests/what_git_wrote.rs:138` — `merge_file_returns_the_merge_with_one_or_two_conflicts` passes only because this machine's ~/.gitconfig sets `merge.conflictstyle=zdiff3`. With no global config (GIT_CONFIG_GLOBAL=/dev/null), git's merge style joins `A b c d E`/`X b c d Y` into one block and the `count == 2` assert fails. Any CI or fresh machine sees a red suite. The test dates from round 1. *Fix:* Use a two-block input that splits under every conflict style, e.g. hunks separated by four or more alnum lines like `a\nbb\ncc\ndd\nee\nf\n`, or set `merge.conflictStyle` in the conflict repo's config (`Setup::config`).
- **#543** (correctness, should) `crates/session/tests/start_from_disk.rs:283` — `a_configured_merge_driver_with_markers_opens_from_disk_at_the_first_list` still passes if the `config.drivers.contains(name)` lookup is deleted: `mergiraf` then falls back to Text, git's text merge of OURS/THEIRS differs from the driver's `local`/`remote` block, so the file is Changed and gives `MarkersLeft{1}` + Disk view anyway. No test proves that a configured name gives Custom. *Fix:* Make the driver write exactly git's text merge, e.g. `git merge-file -L ours -L base -L theirs %A %O %B; exit 1`. Then Custom (always Changed → MarkersLeft, Disk view) and Text (Untouched → Stages view) give different results, and keep the assertions as they are.
- **#544** (correctness, should) `crates/session/src/seed.rs:299` — #533 is only half-fixed. Remote's `dup`→`DUP` substitution keeps the ours view and local line for line the same length, so an identity ours→local mapping (and any off-by-N that is 0 here) still yields the asserted `(2,1)` ranges and the exact apply results. Only a content-search mapping is caught. *Fix:* Make remote's clean change insert a line before the block, e.g. remote `DUP\nnew\nmid\nother\nend\n` with the settled `new` line in the disk text. The ours line of the block then sits at view line 3 but at local line 2, and the identity mapping fails the range and apply asserts.

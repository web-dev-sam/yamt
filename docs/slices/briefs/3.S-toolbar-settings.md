## Behaviour (what the user sees)

### Arrows

1. Two icon-only buttons in `MergeToolbar.vue`, lucide `arrow-up` / `arrow-down`, titles and
   accessible names "Previous change" / "Next change", placed after "Mark resolved" and before the
   two apply-all buttons, same look as the other icon buttons, disabled while `summary === null`.
2. **A side has the keyboard** (its CodeMirror view `hasFocus`): Up/Down arrow = exactly that side's
   ArrowUp/ArrowDown key (`SideFocus` step: the next/previous change still waiting on that side;
   lowest/top-most stay put; from a side alone, screen-relative `stepAlone`; reveal per #590).
3. **No side has the keyboard** (the middle, a toolbar button, the file list, nothing): give the
   keyboard to the left side as a side alone, then step — exactly what Ctrl+wheel already does on a
   side that lacks the keyboard (`#wheel`: `#focusOn(side, alone(mark))` then `#step`). So Down focuses
   the first waiting change at or below the top of the left's visible area; the left has none waiting
   → the right (`stepAlone`'s fallback). Make the wheel and the arrows share one private method for
   "take the keyboard if needed, then step"; no second copy of that rule.
4. **Pressing an arrow with the pointer must not take the keyboard from the side**: prevent the
   button's `mousedown` default (focus) so the side keeps DOM focus and its outline; then case 2
   applies. Activating an arrow by keyboard (Tab to it, Enter/Space) is case 3 (the button has focus).
5. Read-only views have no toolbar, so no arrows; nothing to do there.

### Gear and settings view

6. An icon-only gear (lucide `settings`), title and accessible name "Settings", at the right end of
   every file's toolbar row: `MergeToolbar.vue` (push it right, e.g. `ml-auto`), the empty
   `<header>` that `MergeView.vue` shows for read-only files, and the empty `<header>` in
   `ChoiceView.vue`. One component renders the gear (VU15: a new `SettingsButton.vue` is
   pre-approved, reason "one gear for three file headers"); it calls the store's `openSettings`.
   Same size and hover look as the toolbar's icon buttons; never disabled.
7. The settings view (VU15: a new `SettingsView.vue` is pre-approved, reason "a screen of its own")
   renders in `App.vue`'s file grid cell (`col-start-1 row-start-1`) while `settingsOpen`. It fills
   the cell as one island panel (`rounded-island bg-panel`, like the merge panel), and inside it a
   horizontally centred column with a max width and padding (Tailwind, e.g. `mx-auto w-full
   max-w-3xl p-6`; pick values that look right next to the merge panel and say which). At the
   column's top left: a "Back" button — lucide `arrow-left` icon plus the word "Back", styled like
   "Mark resolved"'s neutral (bordered) state or the icon buttons' hover look, your choice, say
   which. Nothing else in the view. Give the panel `aria-label="Settings"`.
8. While `settingsOpen`, every MergeView/ChoiceView gets `shown = false` (`App.vue`:
   `path === active && !settingsOpen`), so its toolbar row and panes hide exactly as an inactive file
   does: they stay mounted (never `v-if` a MergeView: that destroys its editors and undo history),
   and `historyKeyInShownFile` already stops Ctrl+Z/Y because it checks `shown`.
9. Keyboard: opening settings moves DOM focus to "Back" (so no key — Enter, Space, Delete, arrows —
   reaches a hidden pane that still had focus). "Back" calls `closeSettings`, then returns DOM focus
   to the element that had it just before settings opened (normally the gear that was clicked), if
   it is still in the page and now visible; otherwise leave focus alone.
10. Picking a file in the file list while settings show closes settings and shows the picked file
    (also when it is the file already active). The app's own `open` calls (initial load, moving on
    after "Mark resolved") never change `settingsOpen`. Do not restore focus in this case: the list
    keeps it.
11. Back in the merge, the file is exactly as before: text, decisions, tints, undo history, each
    pane's scroll position, the side marks.

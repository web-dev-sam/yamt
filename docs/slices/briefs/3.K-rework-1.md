## Change — fix each finding (verbatim from the reviews)

1. **#599 (should)** `frontend/src/editor/internal/sideFocus.ts:190` — The capture-phase mousedown on
   scrollDOM also fires for presses on the scrollbar, so dragging a side's scrollbar retargets that
   side's mark to whatever change lies beside the thumb (or clears it to alone) although #54 rule 1
   only speaks of clicks in the pane and on a change block; the next Enter then decides a different
   change than the one the user had outlined. Fix: return early when `event.target ===
   view.scrollDOM` (scrollbar presses target the scroller itself; text, the empty area and the
   gutters do not).
2. **#600 (should)** `frontend/src/editor/internal/historyKey.ts:28` — `historyCommand` matches only
   `event.key`, so on a non-Latin layout (Ctrl+Z gives key 'я' on Russian) undo works in the middle —
   CodeMirror falls back to the keyCode — but does nothing from a side pane or anywhere else,
   contradicting #54 "on any keyboard layout". Fix: when `event.key` is not a single ASCII letter, fall
   back to `event.code` (`KeyZ`/`KeyY`), as CodeMirror's `runHandlers` does with keyCode; add a
   `historyKey.test.ts` row with key 'я', code 'KeyZ' (and one proving a Latin `key` wins over `code`,
   so a QWERTZ Ctrl+Z — key 'z', code 'KeyY' — still undoes).
3. **#601 (should)** `frontend/src/editor/index.ts:192` — After an icon click, a drag or a
   Ctrl/Cmd+click with the keyboard on a side, the outline moves on (settled) but the view never
   reveals it, so the outline can land off screen and the next Enter applies a change the user cannot
   see. #54 now says a newly focused change after a decision by any means while a side has the
   keyboard is revealed (null when already fully on screen). Fix: after `#decide` in the mouse path,
   reveal the mark of the side that holds DOM focus (through `SideFocus`; nothing when no side has
   it). Rule-1 clicks on a change still never scroll.
4. **#603 (nit)** `frontend/src/editor/internal/sideFocus.ts:106` — `decided()` hands the keyboard over
   whenever the focused side has nothing waiting, even when the decision was on the other side and the
   focused side was already empty (e.g. ArrowLeft onto a finished local, then a click on a remote icon
   moves the keyboard to remote), which breaks #589's "the keyboard stays where it was". Fix: hand
   over only when the focused side had a waiting change before the decision and has none after
   (compare before/after `#dispatch` in `#decide`); keep the rule pure and unit-tested in
   `handoverTo`.
5. **#604 (nit)** `frontend/src/editor/internal/sideFocus.ts:191` — A Ctrl/Cmd+click on a side that hits
   no waiting change is skipped by `#pressed`, but modClick does not consume it, so the browser focuses
   the side with its old mark still outlined instead of the side alone (rule 1). Fix: skip the
   mod-click in `#pressed` only when `changeAt` finds a waiting change; otherwise fall through and set
   the side alone.
6. **#593 (should)** `frontend/src/editor/internal/decorations.ts:62` — `focusLines` re-derives the
   zero-line edge rule (`line.from === from ? "above" : "below"`) that `bandDecorations` already has
   at `decorations.ts:27`, so the two copies can drift. It also emits a bare `chunk-focus-point` class
   that no CSS rule styles. Fix: one `pointEdge(line, from): "above" | "below"` used by both; give
   `.chunk-focus-point` the shared focus style or drop it, updating `decorations.test.ts`.
7. **#594 (should)** `frontend/src/editor/internal/geometry.ts:14` — `SIDE_PANE` adds a second way to
   map a side to its pane, while `drag.ts:38`, `gap.ts:19` and `strips.ts:200-202` still spell the
   same fact as `side === "local" ? …left : …right` ternaries. Fix: replace those ternaries with
   `views[SIDE_PANE[side]]` / `row[SIDE_PANE[side]]` so the mapping exists once.
8. **#595 (nit)** `frontend/src/editor/internal/sideMark.ts:11` — `alone(mark).remembered` uses a
   constructor as a getter. Fix: add `markedId(mark): Chunk["id"] | null` in `navigation.ts`, use it in
   `settled`, build `alone()` on top of it.
9. **#596 (nit)** `frontend/src/editor/internal/sideFocus.ts:126` — `#show` both sets the mark and moves
   DOM focus; elsewhere `show*` only pushes display state. Fix: rename to `#focusOn(side, mark)`.

Not for you (the verifier covers them): #597 Ctrl/Cmd+wheel seen in a real browser; #598 Ctrl+Z while a
"Mark resolved?" question is open.

  you see:

     outline stays on the same change (#599).

     the keyboard stays on the left (#603).

     side is focused with no change outlined (#604).

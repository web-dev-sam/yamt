# Slice 2.X — the git cross-check stops flaking, and the two cases where git is wrong are pinned

Board v0 wave 1, "engine" row (was row 12's RK13 note). The cross-check in
`crates/cli/tests/merge_file.rs` (RK13) asserts that when yamt and `git merge-file -p
--diff-algorithm=histogram` are both conflict-free, their merged texts are byte-equal. It fails
about once in 1 800 random cases, so `just check` flakes — not acceptable for a release.

Reproduced by the orchestrator (2026-10-10, git 2.56, `PROPTEST_CASES=20000`, failure after 1 768
cases). Both failures are the same thing: in a run of identical lines, git and yamt place one
side's change at different copies of the line (diff alignment is ambiguous there). git then applies
the two sides' changes at different copies; yamt sees them as the same change (`BothSame`). In both
cases **yamt's result is the right merge** and git's is not:

| case | base                     | local                         | remote                          | yamt (chunks → result)                                                                                                                       | git                                                                                                 |
| ---- | ------------------------ | ----------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| A    | `"\nx\r\ny\ny\ny\nx\nx"` | `"\nx\nx\r\nx\r\ny\ny\nx\nx"` | `"\nx\r\ny\ny\nx\nx"`           | LocalOnly `base[1+0] local[1+2]`, BothSame `base[4+1] local[6+0] remote[4+0]` → **local** (each branch dropped one of three `y`; two remain) | one `y` left: local deleted base line 3, remote base line 5 (`git diff --no-index --histogram -U0`) |
| B    | `"x\r\nz\nx\r\nx\r\n"`   | `"x\r\nz\nz\nx\r\nz\nx\r\n"`  | `"x\nx\r\nz\nz\nx\r\nz\nx\r\n"` | RemoteOnly `remote[0+1]`, BothSame `base[2+1] local[2+3] remote[3+3]` → **remote** (remote is local plus one first line)                     | 10 lines: git aligned remote as 4 lines inserted at the top, so `z`/`x\r` content appears twice     |

Owner direction (GUARDRAILS 2026-10-09): "I want to avoid AI writing the most complex engine just to
adhere to tests and not get the algorithm right." Decision (plan §2 #28): the engine is not changed
to copy git's tie-breaking; the oracle is narrowed to the cases where the two tools aligned each side
the same way — exactly where a bug in applying chunks would show.

## Target

Owned: `crates/cli/tests/merge_file.rs`.
Read-only: everything else — `crates/merge-core/**` (no engine change; if you find a real engine bug,
stop and report it in `deviations_from_brief` with the triple), `crates/cli/src/**`, `Cargo.toml`
files, `docs/**`, `.omp/**`. Needed elsewhere → stop, `deviations_from_brief`.
Non-goals: changing `compute_chunks`, `apply_non_conflicting`, imara-diff post-processing, the
triple generator's alphabet.

## Behaviour

1. **Example tests** (plain `#[test]`), named by what the user gets, e.g.
   `both_branches_dropping_one_of_three_equal_lines_keeps_two` (case A: result == local) and
   `remote_that_is_local_plus_a_line_merges_to_remote` (case B: result == remote). Each also runs
   `git merge-file` on the triple and asserts git's output **differs** from yamt's, so the test
   documents why the cross-check needs its precondition (if a future git agrees, the test says so).
   One short comment per test: git places the two sides' changes at different copies of a repeated
   line.
2. **Cross-check precondition**: in `cross_check`, when both are clean, compare how each tool aligned
   each side against base before comparing texts:
   - git's per-side alignment: `git diff --no-index --histogram --no-indent-heuristic -U0` of base
     against the side, in the same hermetic environment as the existing `git merge-file` call
     (RK19: no user/system config), hunk headers parsed into base/side line ranges;
   - yamt's per-side alignment: from `compute_chunks(.., &Options { gap: 0 })` — LocalOnly and
     BothSame chunks are local's changes, RemoteOnly and BothSame remote's (prove in a comment-free
     way, by the tests below, that this equals the per-side hunks for clean triples; if it does not,
     choose another way that does not touch `merge-core`'s public API and report it).
   - Same alignment on both sides → texts must be byte-equal (unchanged assertion). Different →
     a new `Agreement` variant (e.g. `AlignedDifferently`), no text assertion.
3. **Ceiling**: the deterministic sample test counts `AlignedDifferently` and asserts it stays at or
   below a named constant (pick it from the measured rate with headroom, e.g. ≤ 3 % of 512; state
   the measured count). The existing both-clean floor and yamt-clean/git-conflict ceiling stay.

## Tests / proofs

- `PROPTEST_CASES=20000 cargo nextest run -p yamt-cli --test merge_file` passes; paste the summary
  and the sample test's counts line (`--no-capture`).
- Cases A and B, fed through `cross_check`, come out `AlignedDifferently` (assert it in the example
  tests or show it once in the report).
- Failing-path proof: break `apply_non_conflicting`'s caller in the test (e.g. drop the last chunk
  before applying) → the proptest fails on an `Aligned`-equal case; paste the failure line; revert.
- `just mutants` will not mutate test files; this proof is the guard.

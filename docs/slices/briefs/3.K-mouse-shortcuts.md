## Behaviour (what the user sees)

"Waiting" = `isSideOpen` for that side. "Hit" = the hit test a plain press on a side already uses
(`navigation.ts` `changeAt`: the change's pixel band, or within `POINT_HIT_PX` of a zero-line
change's bar; decided sides never hit).

1. **Ctrl/Cmd+right-click on a side pane** that hits a waiting change ignores that side of it,
   exactly as its ignore icon would (`statusAfterIgnore`: a conflict loses only that side; a change
   that is not a conflict resolves whole). No context menu opens, the side's selection does not
   change, DOM focus does not move. One gesture = one ignore, on every engine: WebKitGTK and macOS
   fire `contextmenu` on press, Windows on release, after the `mousedown`/`mouseup` — never act
   twice, never leave the native menu open after acting. A Ctrl/Cmd+right-click that hits nothing,
   a plain right-click, and any right-click in a read-only view behave exactly as today.
2. **Ctrl/Cmd+click on a conflict's apply icon** (modifier read on release, like the click itself,
   #45) applies that side as a plain click would and, when the other side still waits, ignores the
   other side — in the same transaction. Result text and statuses equal "plain apply on this side,
   then plain ignore on the other side".
3. **Ctrl/Cmd+click on a conflict's ignore icon** ignores that side and, when the other side still
   waits, applies the other side — same transaction. Result equals "plain ignore on this side, then
   plain apply on the other side" (the other side's apply mode is then `replace`; a zero-line other
   side removes the block's lines, as its own apply would).
4. Other side not waiting (already applied or ignored), or a change that is not a conflict: the
   Ctrl/Cmd click behaves exactly as the plain click. Never touch a side that is no longer waiting.
5. **Drag** (#45) released with Ctrl/Cmd held: every covered conflict gets 2./3., every covered
   non-conflict the plain outcome, top to bottom, **one undo step** for the whole release (as today).
   Undo after any of 1.–5. restores the text and both sides' statuses in one Ctrl+Z.
6. **Hint:** while a conflict's other side still waits, its icons' hover text (`<title>`) gains a
   second line: apply → `Ctrl+click: also ignore the other side`, ignore →
   `Ctrl+click: also take the other side`; on macOS (the platform test `isModHeld` uses) `⌘+click`
   in place of `Ctrl+click`. The first line stays as it is ("Apply" / "Ignore"; "Apply after the
   other side" never has the hint, its other side was applied). The hint goes as soon as the other
   side is decided and comes back after undo — today `sameShape` only rebuilds a row when its
   `mode`/layout changes, so an ignored other side (mode stays `replace`) would keep a stale title.
   If WebKit shows the two lines on one line, report it with what it shows.
7. **Keyboard focus** (#54, #589, #603): every decision above goes through the path icon clicks and
   Ctrl/Cmd+click use today (`#act`): the keyboard stays where it was; on a side that has it, the
   outline moves on by the after-decision rule, and the keyboard is handed to the other side only
   when that decision emptied the focused side. A side whose remembered change was decided by the
   other-side half moves its mark on by itself (`sideMark.ts` `settled`), check that it does.
8. **One hit test (#606, verbatim):** "Ctrl/Cmd+click within POINT_HIT_PX of a zero-line change's
   bar is skipped by #pressed (changeAt hits it) but not consumed by modClick (openBlockAt needs
   len > 0), so the side gets focus with its old mark." Fix: plain press, Ctrl/Cmd+click and
   Ctrl/Cmd+right-click all use `changeAt`; `openBlockAt` goes. A Ctrl/Cmd+click within 4 px of a
   zero-line change's bar now applies it, a Ctrl/Cmd+right-click there ignores it.

## Follow-ups (verbatim from the reviews, with the fix to make)

- **#614 (should)** `editor/internal/historyKey.ts:29` — "`/^\p{L}$/u` rejects combining vowel
  signs. On Hindi/Marathi InScript, physical KeyZ gives `key` 'ॆ' (U+0946, category Mn; checked with
  node: \p{L} false), so Ctrl+Z in a side pane no longer undoes." Fix: fall back to `code` for any
  single non-ASCII key (`/^\P{ASCII}$/u` or `[\p{L}\p{M}]`; pick one, say why in the name), add the
  row key 'ॆ' + code 'KeyZ' → "undo".
- **#616 (nit)** `editor/internal/historyKey.test.ts:79` — "The row `key 'f', code 'KeyY'` returns
  null with or without the fix, because 'f' is a Latin letter and wins". Fix: replace it with key
  '-' + code 'KeyY' → null.
- **#617 (should)** `ui/useMergeController.ts:70-73` — "with no controller yet (file still loading)
  a toolbar click or Ctrl+Z would throw; no test covers the guard." Fix: a
  `useMergeController.test.ts` case calling the handle's `applyAllNonConflicting`, `undo`, `redo`
  and `historyKey` before a controller exists: no throw, `historyKey` returns false.
- **#620 (nit)** `editor/internal/wheel.ts` — "One X11 mouse notch in WebKitGTK is deltaY 96
  (deltaMode 0) while WHEEL_STEP_PX is 100: slow notches step once each, but a fast spin within one
  burst steps about every second notch." Fix: `WHEEL_STEP_PX = 90` (under one X11 notch; at most one
  step per event already caps fast touchpads), and a test: three 96 px events inside one burst give
  three steps.
- **#605 (nit)** `editor/internal/sideFocus.ts` — "WebKit moves DOM focus to DIV.cm-scroller when
  a side's scrollbar is pressed; the mark stays but the side loses cm-focused, so no outline and keys
  do not reach the side until the next click." Fix: when focus lands on a side's `scrollDOM`, hand
  it to that side's `contentDOM` with `preventScroll: true`. The scrollbar drag must keep scrolling.
- **#613 (nit)** `editor/internal/navigation.ts:93` — rename type `AfterDecision` →
  `FocusAfterDecision`.

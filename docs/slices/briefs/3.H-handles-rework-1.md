# Slice 3.H-handles — fix round 1 (`PaneHandlesR1`): one divider component, two press fixes, the scroll timing settled

Board "Servers and panes" row 6. Round 1 is commit `d989b9a` (brief `briefs/3.H-handles.md`, notes
`.omp/run/notes/PaneHandles.md`); row 4's fix round `659fc8d` renamed `ColumnDragHandle` → `ColumnDragBinding` and added
`parseStored` (notes `.omp/run/notes/PaneSplitModelR1.md`). Three findings verbatim, then the timing question.

> **#1283** (block, boundary) `frontend/src/ui/ChoiceView.vue:124` — The pane divider's markup is written out four
> times: two copies in MergeView.vue (lines 226-234 and 255-263) and two in ChoiceView.vue (lines 124-131 and 135-142).
> Each copy repeats role="separator", aria-orientation, the accessible names "Local and Result widths" / "Result and
> Remote widths" and a ResizeDots bound to that side's handle. Both views already share their per-side header words
> through `sideHeaders.ts`, so this breaks that "one rule for both" pattern. Renaming a handle or adding a third view
> with dividers would mean editing every copy, and app-session and screen readers find the handles by these names.
> Fix: add one `PaneDivider.vue` with props `side: Side` and `handle: ColumnDragBinding` (row 4's renamed type). It
> renders the separator role, orientation, the label from a single `Readonly<Record<Side, string>>`,
> `v-on="handle.listeners"` and `<ResizeDots :state="handle.dots.value">`, and takes each view's grid or hit-box classes
> through attribute fallthrough. Use it for both MergeView header cells and both ChoiceView hit boxes, and give the VU15
> one-line reason (the divider shared by the two views).

> **#1284** (block, correctness) `frontend/src/ui/MergeView.vue:273` — A quick double-click on an apply or ignore icon,
> or on a strip wave join, resets the stored split to thirds. The first click applies the change, so its icon row goes
> away, or it opens one step of the run, so the join moves. The second press then lands on the svg root, which the band
> rule makes the target even where a band is painted. The browser sends the `dblclick` to that second target,
> `dividerHandle.accepts` sees the svg root, and `useColumnDrag.doubleClicked` (useColumnDrag.ts:114) calls
> `resetPaneSplit`. The same happens on the right strip wrapper (MergeView.vue:285).
> Fix: in `useColumnDrag`, remember whether each of the last two `pointerdown`s the handle saw was accepted, and reset on
> `dblclick` only when both were. Add a node test: a rejected pointerdown, then an accepted one, then `dblclick` gives no
> reset; two accepted ones still reset.

> **#1285** (promoted, correctness) `frontend/src/ui/useColumnDrag.ts:96` — [INFERENCE, not observed] During an icon
> drag (#45), `IconDrag.start` captures the pointer on the strip svg. Pointer Events then fire `pointerover` at the
> capture target, so `hovered` sees the svg root, accepts it, and the header dots brighten after 300 ms while the user
> covers icons. That breaks the design's rule 'over an icon the dots stay at rest'.
> Fix: in `hovered`, set `rest` whenever `event.buttons !== 0`, so only a pointer with no button held brightens the
> dots, and add a node case for it.
> Orchestrator: observe it first in WebKit (an icon drag over several icons, `--dy 330` as W3 did, reading the header
> dots' colour after 400 ms), then fix and observe again.

# Slice 1.E — brighter word highlights inside blocks

The owner: on a conflict it is hard to see what exactly changed compared to base; WebStorm draws
the parts of each side that differ from base in a brighter tint of the block's colour, so left and
right are easy to compare. Decision: plan §2 #30. Slice 1.D put the word changes on every domain
chunk (`chunk.words`); this slice draws them.

## Target

Owned: `frontend/src/editor/**`, `frontend/src/style.css`.
Read-only: everything else — `frontend/src/ipc/**` (use `Chunk["words"]` as it is), `ui/**`,
`connectors/**`, fixtures, configs, `docs/**`, `.omp/**`, Rust.
Non-goals: recomputing word changes after hand edits; fading the block tint; word marks on
inserted/deleted blocks (the engine sends none); keyboard navigation between changes; a setting to
turn word highlights off.

## Behaviour (what the user sees)

- Inside every open conflict (red) and modified (blue) block, the words that differ from base are
  drawn in a brighter tint of the block's colour, on the left pane (`words.local`), the right pane
  (`words.remote`) and the middle pane (`words.base`: the base text either side changed).
- A pane shows a block's word marks exactly when it shows that block's tint (same status rules as
  the line tint: resolved blocks lose both; undo brings both back).
- Middle pane: word marks are drawn only while the block's text there is still exactly its original
  base text. Applying a side, ignoring, or typing inside the block hides them; undo restores the
  text and the marks with it. Typing elsewhere (above the block) moves the marks with the block.
- Text stays readable on the brighter tint; syntax colours stay.

## Contract (fixed; you may add, never change)

- Data: `chunk.words` (`ipc/domain.ts`): `local: InlineRange<LocalLine>[]`, `base: InlineRange<BaseLine>[]`,
  `remote: InlineRange<RemoteLine>[]`; `InlineRange<L> = { line: L; start; len }` — `line` is 0-based in
  that text, `start`/`len` are UTF-16 columns within the line, never across a line break. A
  document position is `doc.line(range.line + 1).from + range.start` (CodeMirror positions are
  UTF-16 units; this holds for CRLF documents too, since a line's text excludes its break).
- Side panes: `Decoration.mark` per range, built from the side document and the side status
  mirror, gated like `sideDecorations`. Middle pane: positions derived from the chunk's current
  span in `chunkField` (CM9: no stored positions) plus each range's offset from the start of the
  chunk's base lines, gated on "open" and "current text of the span equals the chunk's base
  text" (take the base text from the file data, as `SideDocs` does for the sides). No new
  `StateField` holds positions; `chunkField` stays the single owner (vision 2).
- Colours only from palette tokens (VU17). Add exactly two to `@theme`:
  `--color-chunk-conflict-word` and `--color-chunk-modified-word`. Start from `#8f5247a6` and
  `#43698da6` (the block colours at higher opacity, drawn over the block tint); adjust only if the
  screenshot shows text hard to read or words not clearly brighter, and report the final values.
  One way to keep the mark's colour tied to its block: the tint classes in `theme.css` also set a
  `--chunk-word-tone` the mark's class reads — your choice.
- `MergeController`'s public surface stays as it is.

## Tests (`node` project, `EditorState` only)

- left/right: a conflict's word marks sit exactly on the changed words (assert the marked text),
  including a CRLF file and a line with `😀` before the change; a resolved block has none; undo
  restores them;
- middle: marks on the base words of an open conflict; gone after applying a side; back after undo;
  gone after typing inside the block; shifted correctly after typing a line above the block;
- the mark colour follows the block tone (conflict vs modified).

`editor/` is outside the mutation run: break each tested rule by hand once (e.g. drop the
"text equals base" gate, use the chunk's original instead of its current span, skip the status
gate on a side), paste the failure, restore.

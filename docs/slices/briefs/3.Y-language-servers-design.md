# 3.Y — design: language servers in the Result pane (board "Language servers and saving" row 1)

Agent: `designer` (read-only). Output: two or three file-level options plus a recommendation (your output
schema). You design; the orchestrator chooses. Afterwards the build runs as several implementer tasks, so the
recommendation must split the work into **disjoint** ownership lists (every file each build creates or
changes; which build owns a file two would touch, and the fixed contract the other then uses). A Rust host
and a window side are the expected minimum split; say if yours differs and why.

This design does **not** cover saving to disk (Ctrl+S writing the file, the unsaved dot, reset): that is a
separate design that waits for the owner's answers. It does cover Ctrl+S's formatting step (below), and must
leave a seam for it: "format, then save".

## What the owner wants (settled, #856 and the exploration before it)

1. A user sets up language servers; their problems (errors, warnings) show in the **Result pane** as you
   type: underline plus the message on hover. The side panes get nothing.
2. A **status area left of the settings gear** in the toolbar row (like VS Code's bottom bar): each server's
   name and state; from there the user can **start, stop, restart** it and **see its log**.
3. **Ctrl/Cmd+S formats** the Result with a server that offers formatting (e.g. oxfmt's), then saves. If no
   formatter is set up or formatting fails, it saves unformatted and the status area says why.
4. Servers named by the owner: oxlint, oxfmt, TypeScript, eslint. The user's own command is the fallback.
5. How servers get set up and whether they start on their own is an **open product question**; your design
   takes "a list of server specs from some config source" as input (name, command + args, file patterns,
   project root, start options) and must not depend on which source wins.

## Sourced facts (given; re-check only what is marked [INFERENCE])

CodeMirror's client, `@codemirror/lsp-client` 6.3.0 (npm, 2026-10-14; MIT, Marijn Haverbeke; repo moved to
code.haverbeke.berlin/codemirror/lsp-client):

- dependencies: `marked`, `@codemirror/lint`, `@codemirror/autocomplete`, `@codemirror/language`,
  `@codemirror/view`, `@codemirror/state`, `@lezer/highlight`, `vscode-languageserver-protocol`.
- `Transport = { send(message: string); subscribe(handler); unsubscribe(handler) }` — JSON messages only,
  no `Content-Length` headers; connecting, disconnects and errors are the transport's job.
- `new LSPClient({ rootUri, initializationOptions, workspace, timeout (default 3000 ms), notificationHandlers,
  unhandledNotification, extensions })`, `.connect(transport)`, `.disconnect()`, `.initializing`,
  `.serverCapabilities`, `.request(method, params)`, `.notification(...)`, `.sync()`,
  `.plugin(fileURI, languageID?)` (an editor extension; opens the file in the workspace).
- `Workspace` (abstract): `openFile`, `closeFile`, `syncFiles`, `updateFile`, `requestFile`, `displayFile`;
  default workspace: one editor per file, only files with an editor.
- `serverDiagnostics()` handles **push only**: `textDocument/publishDiagnostics` with `versionSupport`,
  dispatching `@codemirror/lint`'s `setDiagnostics` on that file's view (src/diagnostics.ts:30-37).
- `formatDocument` is a command (asks the server for `textDocument/formatting`).
- `languageServerExtensions()` bundles everything (completion, hover, signature help, rename, references,
  definition). yamt wants diagnostics and formatting only (plan §4: "no completion popups in a merge window").

Servers:

- oxlint `--lsp` (oxc `crates/oxc_language_server/README.md`): full text sync; workspace folders; diagnostics
  pushed, or pulled when the client supports pull **and** `workspace/diagnostic/refresh`;
  `initializationOptions: [{ workspaceUri, options: { run: "onType"|"onSave", configPath, typeAware, … } }]`;
  without them it asks `workspace/configuration`; it sends `client/registerCapability` to watch its config
  files. The oxlint CLI has no stdin input (oxc.rs CLI reference): only a language server can check the
  unsaved Result.
- oxfmt `--lsp` offers `textDocument/formatting` (same README; oxfmt CLI reference).
- TypeScript 7's native language server serves per-file diagnostics **only on request**
  (`textDocument/diagnostic`, pull); pushing is a proposal (microsoft/TypeScript#63928, open on 2026-10-05).
  CodeMirror's client only listens, so yamt must ask after changes for such servers.
- eslint's language server asks for a block of settings through `workspace/configuration` [INFERENCE: from
  other editors' setups; check its source or a known client config].

yamt today (scout `FormatLintFacts`, file:line in its output `agent://FormatLintFacts`):

- Nothing spawns a process except `gitio` (`crates/gitio/src/run.rs:28-140`: `Command` with cwd = repo root,
  stdin bytes on a thread, stdout/stderr on threads, 5 ms poll, kill + reap at a deadline; `BlobReader` is a
  long-lived child, `blob.rs:15-27`). Rust is synchronous ("no async", architecture §7); IPC commands are
  plain `fn`s over one `Mutex<MergeSession>` (`src-tauri/src/commands.rs:40-42`); Tauri runs non-async
  commands on the main thread.
- `src-tauri` may depend only on `yamt-session` and `yamt-settings` (`scripts/arch-check.sh:30-35`); the Rust
  crate list (architecture §7) is closed unless a decision row adds to it.
- The window knows each file's repo-relative `path` only; no IPC type carries the repo root's absolute path
  (`bindings.ts:6-20`). A server needs `file://` URIs of the real files and a root URI.
- Window permissions: only `core:event:allow-listen`, `core:window:allow-destroy`
  (`src-tauri/capabilities/main.json:6`); CSP `connect-src 'self' ipc: http://ipc.localhost`.
- The editor's dependency list is closed (plan §4 "Frontend dependencies", row #4 "core primitives only");
  `@codemirror/search` was added by its own row (#44). Adding the client and `@codemirror/lint` is a new row.
- Module rules: only `ipc/` talks to the app; `ui/` never imports `@codemirror/*` or `@tauri-apps/*`;
  `editor/` never imports Vue or `@tauri-apps/*`; `editor/` is reached only through `MergeController`
  (project map, PM2–PM5). Vue state never holds an `EditorView`, a position or document text.
- The Result pane is the only pane with history (`pane.ts:209`). Its language comes from the file name via
  `@codemirror/language-data` (`language.ts:8-34`, `languageCompartment`).
- Chunk positions in the Result (`chunkField.ts:33-84`): a single whole-document replace collapses every open
  block to empty and marks it ignored on both sides (CM8) — **formatting must be applied as many small edits**;
  minimal edits map sensibly (an edit crossing a block edge snaps that edge). The server's formatting edits
  are already small; a server that returns one whole-document edit needs diffing first [INFERENCE: which do].
- Opened files each keep a live controller (`MergeView` per opened file, inactive ones hidden, plan #51); a
  file's view is destroyed and rebuilt on reset and on a disk change (`useMergeController.ts:113-126`).
- What a waiting change shows in the Result: its base text, or raw marker lines for a block yamt could not
  place exactly (`seed.rs:97-100`). Other conflicted files keep git's markers on disk.

## What to design (open)

1. **Where the protocol is spoken**: the window (CodeMirror's client; Rust a framed byte pipe) vs Rust
   (Rust speaks the protocol; the window receives problems and edits) vs a split. Cost each in new
   dependencies (Rust and npm), lines, and what the owner must read to follow a message end to end.
2. **The Rust host**: which crate (a new one is a decision row and an `arch-check` change), process
   lifetime (start, stop, restart, crash, app exit kills children), the framing, threads vs async, how the
   window receives a stream (Tauri `Channel`, events), where each server's **log** lives and how big it may
   grow, the **state** each server can be in (stopped, starting, running, crashed, …) and who owns it
   (vision 2: one owner).
3. **Documents**: one client per server per repo; which URIs (the conflicted file's real path); which
   opened files are open on the server (only the shown one, or every opened Result, so imports between two
   conflicted files see each other's work); closing on file close/rebuild.
4. **Pull diagnostics** for servers that only answer requests (TypeScript 7): when to ask, how results land in
   the same lint state as pushed ones.
5. **Server→client requests** the client must answer (`workspace/configuration`, `client/registerCapability`,
   `window/workDoneProgress/create`, …): which CodeMirror's client already answers (read its source), which
   yamt must.
6. **Formatting on Ctrl+S**: the `MergeController` method, applying edits as one undo step without
   collapsing open blocks; a result that arrives after the user typed again; the seam to "then save".
7. **Problems in the Result**: the lint extension in the middle pane (theme in `theme.css`, dark/light),
   whether problems inside a waiting change are shown (default: shown), counts reported to the window for
   the status area through `MergeController` (no `EditorView` in Vue).
8. **The status area and log view** in `ui/`: components, store state, menu with Start/Stop/Restart/Show
   log; where the log is shown (default: in the files' grid cell like the settings view, with Back).
9. **Platforms**: Windows `.cmd` shims for `node_modules/.bin/*`, PATH when yamt is started from a desktop
   menu vs by `git mergetool` from a terminal (macOS especially).
10. Fixture mode (browser without the app): what the window does with no host.

## Part A — the wave is one unbroken line (owner #854, a defect)

Owner's words: "the connector line is 3px too low, I dont wanna just slap a transform onto it because I
dont know the reason and want it consistent accross devices".

**Cause (orchestrator, measured — `/tmp/uv/zoom-joins.png`, an 8× zoom of the final run's screenshot
`/tmp/uv/1-von.png` at three joins; look at it):** there is no vertical error. Both ends compute the
wave's centre line from the same numbers (`waveCenterY(LINE_HEIGHT_PX)` = 10 px below the line top in
the pane mask, `foldView.ts:116`, and in the strips, `strips.ts:117`, `gap.ts:99`). The error is
**horizontal phase**:

- A pane's wave is a CSS mask tile repeated from the pane's **left** edge (`.fold-wave`: absolute in the
  line-number gutter cell, `left: 0`, `width: 100cqi` of `.cm-scroller`, `mask-position: 0 6px`). The
  tile (`waveTile()`, `connectors/index.ts:35`) starts at its crest: `M0 1` (upper = 1, centre = 4,
  lower = 7 in an 8 px box). So every pane's wave **begins 3 px above its centre line** at its left edge.
- Every strip join (`waveJoinPath`, a port of WebStorm's `drawConnectorLine`) **starts and ends on the
  centre line**: it leaves the left pane heading down and arrives at the right pane from below.
- So where a join meets the next pane's left edge (the middle's left edge, the right pane's left edge),
  the pane's wave sits 3 px (`WAVE_HALF_HEIGHT_PX`) above the join's end: the join looks 3 px too low.
  At a pane's **right** edge the step is anywhere from 0 to 3 px with any slope, because it depends on
  the wave's width modulo 20 px — which changes with the window size, the file list shown or hidden
  (Ctrl+B, #61), the screen, and whether the pane's scrollbar takes room (an overlay scrollbar on
  WebKitGTK, a classic one on Windows' WebView2). That is the "not consistent across devices" part.

**WebStorm's rule** (`DiffLineSeparatorRenderer.java`, read 2026-10-14 from intellij-community master,
`platform/diff-impl/src/com/intellij/diff/util/`): the editor wave is not drawn from x = 0. `drawLine`
shifts the tile so its phase is fixed relative to the editor edge next to the divider:
`shiftX = -interval - gutterWidth % interval - interval + getStartPhase(...)` (not mirrored) and the
mirrored form for the left editor, whose gutter sits next to the divider; `getStartPhase` returns one
step, commented "cross divider at a 45' downwards angle, to allow a smaller 'shoulder'"; the gutter part
(`paint`) uses the same start phase, and `+ hScrollValue` keeps the wave still while scrolling
horizontally. With tile phase 5 the wave is on the centre line heading down, with phase 15 on the
centre line heading up — exactly where `drawConnectorLine` starts (centre, heading down) and ends
(centre, arriving from below). WebStorm's three-side layout puts the left editor's gutter next to the
left divider and the other two editors' gutters on their left, so WebStorm aligns three of the four
edges; the middle editor's right edge is left to chance. yamt puts every gutter on the left, and the
middle pane touches a strip on both sides.

**Required behaviour (settled):**

1. At each of the four pane–strip edges the pane's wave and the strip's join meet at the same point and
   the same direction: out of a pane's right edge on the centre line heading down, into a pane's left
   edge on the centre line heading up — for level joins and S-curves, 1 px and 2 px (hover) strokes.
2. True for any pane width (window resize, file list shown or hidden, split ratios), any device pixel
   ratio (1, 1.25, 1.5, 2), overlay or classic scrollbars, dark and light.
3. No constant offset, no transform: the phase follows from measured geometry or from layout facts that
   hold everywhere. Measured values are read when the layout changes, never per scroll frame (#51).
4. The wave stays still while a pane scrolls horizontally; the joins keep WebStorm's shapes
   (`waveJoinPath` as is, unless an option argues otherwise with evidence).
5. The middle pane has two strip edges; its tile period is 20 px and its width is arbitrary. Options
   must say how both edges are met (e.g. a period stretched to fit `n + ½` waves; the strip join
   absorbing the phase; a global phase across all panes; …) and what each costs visually and in code.
6. Where a classic scrollbar sits between a pane's text and the strip, say what the user sees between
   the wave's end and the join's start, and how the phase is taken at the right point.

## Part B — a toolbar button turns collapsing on and off (owner #855, a feature)

Owner's words: "make the collapsed lines a tool to use as a button from the top menu bar and add it to
the right-click menu option to hide and show the button. The button toggles the collapsing feature. If
user extends some lines to show more code and then toggles off->on its like resetting the
expanded/collapsed areas, it does not remember the last expanded state."

**Product rule (settled by the orchestrator as owner; copied from WebStorm where it has the feature):**

1. **Button.** A toggle in the merge toolbar titled "Collapse unchanged fragments" (WebStorm's
   `collapse.unchanged.fragments`, `TextDiffViewerUtil.ToggleExpandByDefaultAction`, in yamt's sentence
   case like the other titles), Lucide `chevrons-down-up` (nearest to WebStorm's
   `AllIcons.Actions.Collapseall`), placed after "Next change" and before the two apply-all buttons
   (`MergeThreesideViewer.createToolbarActions`: the toggle comes right before the apply-non-conflicting
   group; navigation first, #56). It shows a pressed look while collapsing is on (a WebStorm
   `ToggleAction`'s selected state), distinct from hover, from palette tokens only; `aria-pressed`. Same
   enabled/disabled rule as the other icon buttons.
2. **On by default** (#63: collapsed at every open).
3. **Off:** every hidden line of every opened file shows at once, in all three panes; no wave remains in
   any pane or strip (`FoldingModelSupport.expandAll(true)`).
4. **On:** every run of every opened file collapses back to its starting state — all its steps hidden,
   4 lines kept next to each change — whatever clicks had shown before (owner #855;
   `ToggleExpandByDefaultAction.setSelected` → `expandAll(false)` collapses every region). The runs are
   the ones the file has now (computed at open, moved with the middle's edits, #63); they are not
   recomputed.
5. **New files** open collapsed while it is on and fully shown while it is off. A file opened while it is
   off still has its runs, so turning it on collapses them.
6. **Remembered** across restarts in the window's own storage, like the toolbar's hidden buttons (#58:
   the owner chose the window's storage over the settings file); one choice for every file; unreadable or
   missing storage means on.
7. **Right-click menu** (#58): lists it in toolbar order (now seven items), shown at first. Hiding the
   button does not change whether collapsing is on.
8. **Cursor.** A cursor inside lines that a toggle hides moves to the start of the wave line hiding it; a
   selection with either end inside hidden lines is dropped, leaving only that cursor (IntelliJ
   `FoldingModelImpl.onFoldProcessingEnd`: a caret in a collapsed region `moveToOffset(region start)`,
   then `removeSelection()` when either selection end is inside one; verified by the orchestrator in
   intellij-community master). Collapsing must not be undone at once by #63's reveal rule.
9. **Scroll.** After a toggle the middle pane's top line stays where it is on screen (when that line gets
   hidden, the wave line hiding it takes its place) and the sides line up with the middle at once (the
   pointer is on the toolbar, so nothing jumps under it; #63's "re-align at the next scroll" was for clicks
   on the wave).
10. **Not in undo history**; no key (none asked); read-only and deleted-side views follow it like any view.

**Non-goals:** a key for it, a setting in the settings view, changing the 4 lines, an "expand all"
separate from the toggle, remembering shown runs.

# Slice 1.I — ignoring one side of a conflict keeps the other side; Lucide icons

Owner request (2026-10-10, findings #255–#256): "the x button removes the purple from both sides.
This is not how webstorm works, the x say ignore that change. So only the side that gets ignored
isnt applied, its still possible to apply the other change. Similar to how the arrows button works,
when I apply the left side I can still apply the right side (the icon should change slightly
though). Ignoring a side still keeps applying the other side possible." And: "change all icons to
use lucide. Use unplugin icons."

Reference behaviour (WebStorm, `intellij-community` `platform/diff-impl/src/com/intellij/diff/merge/`):
`MergeConflictModel.ignoreChange` resolves only the clicked side of a conflict (a non-conflict
resolves whole); `replaceChange` appends when the other side was applied before, otherwise
replaces, and resolves the whole conflict when the other side's lines are empty;
`ThreesideMergeHighlighters` hides a handled side's buttons and draws that side as resolved, the
middle as resolved only once both sides are; the remaining side's apply icon becomes an
"arrow down" variant after the other side was applied.

## Behaviour (what the user sees)

**Blocks changed on one side, or the same way on both sides:** unchanged — `»`/`«` or `×` on a
changed side resolves the whole block.

**Conflicts — each side is handled on its own:**

- `×` on a side ignores that side: the middle text does not change. That side's tint, word marks,
  removal bars, connector band and both its buttons disappear. The other side keeps its tint,
  marks, bars, band and buttons, and can still be applied or ignored. The middle stays purple and
  the conflict still counts as open.
- `»`/`«` on a side: if the other side was **applied** before, this side's lines are added after
  the current block (today's "apply both"). Otherwise (other side still open or ignored) the
  block's current middle range is replaced by this side's lines.
- If the other side's lines are empty (it deleted the whole block), applying this side resolves
  the whole conflict (WebStorm; adding nothing afterwards is no choice).
- An applied side looks like an ignored side: its tint, marks, bars, band and buttons disappear.
  (Today a half-applied conflict keeps its tint on both sides; that rule goes, and the tests
  pinning it change with it.)
- Both sides handled → resolved: the middle tint goes, the counts drop by one conflict.
- The remaining side's apply icon is the "add below" variant while the other side is applied;
  the normal arrow otherwise (other side open or ignored). Tooltip: "Apply" / "Apply after the
  other side".

**Everywhere:**

- The user deleting a whole open block in the middle pane still resolves it (CM8), now as every
  side ignored.
- One undo step per click; undo/redo restore text and every side's state together (CM2); the
  view-keeping steps of 1.S stay as they are (cursor move outside history, action, recorded
  selection).
- Bulk apply unchanged (non-conflicting open blocks only).
- Focus (finding #252): right after a file opens nothing has focus, so a strip click left focus on
  the page and Ctrl+Z did nothing. After any strip action the middle pane has focus (focus it
  when it doesn't), without scrolling — the cursor is already at the clicked block. Clicking a
  button must still not steal focus first (today's `keepEditorFocus`).

**Icons — every icon is Lucide via unplugin-icons, nothing hand-drawn or a text glyph:**

| place                                        | today | Lucide                              |
| -------------------------------------------- | ----- | ----------------------------------- |
| left strip apply                             | `»`   | `chevrons-right`                    |
| right strip apply                            | `«`   | `chevrons-left`                     |
| left strip apply after the other side        | `»`   | `corner-right-down`                 |
| right strip apply after the other side       | `«`   | `corner-left-down`                  |
| strip ignore                                 | `×`   | `x`                                 |
| toolbar apply non-conflicting from the left  | path  | `chevrons-right`                    |

Muted colour, full colour on hover (as today), stroke `currentColor`, sized to sit inside today's
16 px button within one line height; the text-only buttons ("Reset file", "Mark resolved") stay.

## Contract

- `status.ts`:
  ```ts
  export type SideStatus = "pending" | "applied" | "ignored";
  export type ChunkStatus = Readonly<Record<Side, SideStatus>>;
  ```
  Every status rule lives in `status.ts` (resolved, side still open, append-or-replace, status
  after apply, status after ignore); `apply`, `chunkField`, `decorations`, `strips` ask it and
  never compare status values themselves. A non-conflict action gives every side the block
  changed the action's value (`BothSame` apply → both `applied`); the unchanged side of a
  one-sided block stays `"pending"` and no rule reads it.
- `ChunkAction` in `strips.ts`: `{ kind: "apply"; chunk; side } | { kind: "ignore"; chunk; side }`
  (`dismiss` renamed to the word the UI uses). `dismissSteps` → `ignoreSteps({ target, chunk, side })`,
  `userEvent: "yamt.ignore"`. Clean cutover: no `dismiss`/`dismissed` left in code or tests.
- `editor/` stays framework-free (PM3): strip icons come from `~icons/lucide/<name>?raw` (the SVG
  markup as a string, inserted into the strip's SVG), never from a Vue component.
- `ui/` uses the Vue components `~icons/lucide/<name>`.
- `frontend/src/icons.d.ts` declares `~icons/*?raw` (`string`) **before** `~icons/*`
  (`FunctionalComponent<SVGAttributes>` from `vue`): TypeScript picks the first of two wildcard
  patterns with an equally long prefix (probed: the reverse order types the raw import as a
  component). One why-comment. No `unplugin-icons/types/*` in a tsconfig (they declare
  `~icons/*` twice with different types).
- `MergeController`'s public surface unchanged.

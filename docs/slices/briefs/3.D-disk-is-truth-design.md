# 3.D — design: a conflicted file changed on disk is the truth (board v0 row 13)

Agent: `designer` (read-only). Output: 2–3 file-level options plus a recommendation (your
output schema). You design; the orchestrator chooses; two implementers build it afterwards, one
for Rust (`crates/session`, `crates/gitio`, `src-tauri`) and one for the window
(`frontend/src/ipc`, `frontend/src/editor`, `frontend/src/ui`). Your design must split cleanly
along that line, with the IPC contract between them written out in full.

## The product rule (settled — `docs/plan.md` §2 #52; do not reopen)

The owner: "a conflicted file that changes on disk is the absolute truth; the edits of the user
are ignored". Their answers:

1. yamt remembers each conflicted file's content on disk as it last saw it: at start, and after
   each of its own writes (Mark resolved = `finish`; Take/Keep/Delete = `take`; Reset = `reset`).
2. It compares when the window gets focus (together with the existing re-read of `git ls-files -u`,
   plan §2 #49 — `refreshFiles` in `frontend/src/ui/store.ts`, `refresh_statuses` in
   `crates/session/src/session.rs`) and right before each of its own writes. A change found then
   wins: the write does not happen. No file watcher.
3. On a change: that file's unsaved yamt edits and its undo history are dropped. A closable
   notice names the file: "<path> changed on disk; your edits in yamt were dropped". It is
   information, not a failure.
4. No conflict markers left, or the file deleted → yamt stages it at once (`git add` / `git rm`)
   and the file's mark turns resolved. A later disk change to an already resolved file is staged
   the same way.
5. Markers left → the middle pane shows the disk text; each conflict still marked there becomes a
   normal yamt conflict (arrows and × per side); the side panes stay git's stages 2 and 3; every
   other part of the file counts as settled.

Rejected by the owner: leaving `git add` to the user; showing the markers as plain text without
arrows; dropping edits silently; a file watcher.

## Facts you need (measured here, not from memory)

- Today yamt never reads the worktree file. `MergeSession::open` reads the stages once
  (`read_content`); `finish` overwrites the file and runs `git add` (rollback on failure); `take`
  writes the chosen stage (`checkout-index`) or removes the file; `reset` restores the stages and
  runs `git checkout -m`, which rewrites the file with markers.
- The editor's middle pane starts as `data.base` (`frontend/src/editor/index.ts`, `#center` pane
  creation), and every chunk's middle position is its `base` range mapped through the user's edits
  (`frontend/src/editor/internal/chunkField.ts`). Statuses are per side:
  `pending | applied | ignored` (`frontend/src/editor/internal/status.ts`, plan §2 #33).
  `FileMergeData` (`crates/session/src/session.rs`) has no middle text today.
- Reloading a file's view already exists: `putOpened` in `store.ts` replaces the record with a new
  object, so a kept view rebuilds its editor (Reset uses it). Unsaved edits are tracked by
  `frontend/src/ui/closeGuard.ts`.
- git's real output, produced on this machine (git 2.56.0) from one base/ours/theirs triple, is in
  `.omp/run/markers/`: `style-merge.txt`, `style-diff3.txt`, `style-zdiff3.txt`,
  `marker-size-12.txt` (attribute `conflict-marker-size=12`), `crlf.txt` (CRLF file: the marker
  lines end in CRLF too), the inputs `base.txt`/`ours.txt`/`theirs.txt`, and the script that made
  them (`make.sh <out-dir>`; it builds throwaway repositories under `/tmp/yamt-markers/`).
  Observations:
  - The triple has a legit `=======` line in the settled text (line 2) on purpose.
  - **The owner's global `merge.conflictStyle` is `zdiff3`**, and so is their trial repository's.
  - `merge` style trims lines both sides share at a block's end (`shared-b` sits outside the
    block); `diff3` keeps them inside each side; `zdiff3` moves them out but keeps the full base
    section. So the text outside a block is not always base text, and a block's sections are not
    always whole yamt chunks.
  - Labels after `<<<<<<<` / `|||||||` / `>>>>>>>` vary (`HEAD`, a short commit id, a branch name);
    the base section exists only in `diff3`/`zdiff3`.
- yamt's own chunks (`yamt_merge_core::compute_chunks`) are not git's blocks: git auto-merges
  one-sided changes and aligns repeated lines differently (plan §2 #42). So a remaining git block
  may cover several yamt chunks, part of one, or a region yamt does not see as a conflict.
- Plan §1 names "re-parsing conflict markers" as the root flaw of other tools. Here the markers
  only say **which blocks are still open and where they are in the disk text**; the panes still
  come from the stages, so base stays known. Keep that distinction explicit.

## What each option must answer

1. **Memory and comparison.** What `MergeSession` stores per file (bytes, length + hash, a
   "missing" state for a deleted file, a symlink's target), how the compare runs on focus and
   before each write, and where the Rust side decides "changed → stage or reseed". Cost on a merge
   with hundreds of conflicted files.
2. **Reading markers.** All three styles; `conflict-marker-size` (how it is read: `git check-attr`,
   once per session or per compare); CRLF; a file whose settled text legitimately contains
   `=======` or `<<<<<<<` lines; labels; a block the user half-edited (e.g. deleted the `=======`
   line, or edited inside a section) — what yamt then shows, and why that is safe for the user.
3. **Mapping the remaining blocks onto chunks and the middle text.** What the middle pane starts
   with (disk text with each open block replaced by what?), which chunks exist (git's blocks,
   yamt's chunks, or a mix), where each chunk sits in the base/local/remote panes and in the middle,
   and how a block's sections are located in the stages when text repeats or a section is empty.
   After the user clicks "apply ours" on such a chunk, the middle must read exactly as if they had
   resolved that block by hand on disk — show this on `style-zdiff3.txt` and `style-merge.txt`.
4. **Files without markers.** Binary, symlink, submodule (plan §2 #36) and deleted-side text files
   (#47): any change stages them. How each is staged (`git add`, `git rm`, `update-index`), and
   what "the disk content" means for each.
5. **IPC.** What crosses (a new field on `FileMergeData`, a new type, a new command, a changed
   return type of `list_files`/`finish_file`/`take_side`/`reset_file`), with every type written
   in full. Follow `skill://ipc-contract` (generated bindings, brands, errors, `Outcome`). A
   before-write change is not an error.
6. **Window side.** Where the drop of edits and undo history happens (rebuild the view from new
   data), how the close guard forgets the dropped edits, where the notice lives
   (`ProblemBar.vue` and the "all files resolved" bar in `App.vue` exist; the notice is not a
   failure), and what happens to a changed file that is not opened.
7. **State ownership** (`docs/architecture.md` §5.1): "last seen on disk" and the decision
   belong to Rust's `MergeSession`; Vue holds none of it.
8. **Tests** that would catch a real bug, at session level with a scripted repo (the existing
   `crates/session/tests/*.rs` style): regenerate a file → staged, resolved; remove one of two
   blocks on disk → only the other is a conflict and the middle equals the disk text outside it;
   delete the file → `git rm`'d; Mark resolved after an unseen change → the disk wins and the file
   keeps the disk bytes; the marker parser on the three styles, marker size 12, CRLF, a settled
   `=======` line, a half-edited block. Plus what the window must prove.

## Also report (as `open_questions`, product consequences only)

- A file the user already fixed **before** opening yamt (e.g. a regenerated lock file, or git's
  `rerere` having replayed a recorded resolution into the file while leaving it unmerged): under
  rule 1 yamt remembers that content at start and shows its own merge of the stages, so Mark
  resolved overwrites the fix. Say what each option would cost to treat such a file like a disk
  change at start, so the orchestrator can ask the owner.
- Anything else where your options differ in what the user sees.

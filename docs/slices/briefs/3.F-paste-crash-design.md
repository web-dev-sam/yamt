# 3.F — design: pasting must never crash yamt (board "Paste crash" row 1)

Agent: `designer` (read-only). Output: two or three file-level options plus a recommendation (your output schema). You
design; the orchestrator chooses; then one or two builds (`rust-impl`, `web-impl`) implement it. Name every file each
build creates, changes or deletes and the fixed contract between builds (an IPC command written out in full, if any).
Tree: branch `feat/raw-compare` (the compare window is built and accepted there, not yet merged into main).

## Settled — do not reopen

`docs/slices/request-paste-crash.md`: the owner's request, **rules 1–4**, acceptance, non-goals, and the **cause**
(given, with its sources): WebKitGTK 2.54.0/2.54.1's `WebKit::Clipboard::formats` callback builds a span from GTK's
`(atoms = NULL, atomsCount = -1)` when the clipboard's format list cannot be read, and reads it. Fixed upstream on main
(bug 324466), in no release yet. The fix lives in yamt; nobody is asked to update their system.

## What each option must answer

1. **Every path into `Clipboard::formats`** in yamt's two windows, from the code and WebKit's source at
   `webkitgtk-2.54.1`: the paste keys (WebKitGTK's own key bindings: Ctrl+V, Shift+Insert, others?), the middle mouse
   button's selection paste (the PRIMARY selection, `Clipboard::Type::Primary`), WebKit's context menu if yamt shows it
   (check what the windows do with `contextmenu`), any `navigator.clipboard` use, and anything that asks for formats
   without a paste (an editor-state or "can paste" query). Say which paths reach the crash and which do not, citing the
   WebKit functions.
2. **When the list cannot be read**: a dead owner, a clipboard nobody ever owned, an owner that hangs (does GTK's
   1-second retrieval timeout end in the same -1 and so the same crash?), and the Wayland backend of GTK 3 (what
   `gtk_clipboard_request_targets` reports there with no offer). Confirm the -1 in the GTK 3.24 source.
3. **The guard**, for each option: where it sits (the shell's webview set-up in `src-tauri/src/window.rs`
   `open_and_wait`, a new module next to it, or the window's editor keymaps), which paths it covers, what the user sees
   (rule 2: nothing pasted, no notice; rule 3: a live clipboard pastes exactly as today — CodeMirror's own paste
   handling, the compare window's 8 MiB refusal, undo of a paste), and the race when the owner quits between the guard's
   check and WebKit's own request. Candidates to weigh, at least:
   - **A — the shell swallows a paste that would crash**: on Linux only, the shell connects to the webview widget's key
     and button events through the GTK bindings tauri already pulls in, asks GTK whether the clipboard (or PRIMARY)
     offers any format with a call that handles failure, and stops the event before WebKit sees it when none is offered;
     otherwise WebKit pastes as today. Signal order (does a handler connected to `key-press-event` run before the
     webview's class handler, and does stopping it stop WebKit's key binding?), input methods, and the cost of a
     blocking check on the main thread (a nested main loop) vs. an asynchronous one that replays the paste.
   - **B — the window owns paste on Linux**: the editors' keymaps take the paste keys, a new IPC command reads the text
     through GTK on the main thread, and the editor inserts it as a paste (`userEvent: "input.paste"`), so WebKit's
     paste never runs; what covers the middle button and the context menu; how the window knows it runs on Linux.
   - Anything else you find (a GTK or WebKit setting, a version check that turns the guard off once WebKitGTK carries
     the fix). Name clever routes (replacing a GTK function by symbol interposition, `LD_PRELOAD`) and reject them under
     vision 1 unless nothing else covers a path that crashes.
4. **Cost and rules**: Rust dependencies (the `gtk`/`webkit2gtk` crates are in `Cargo.lock` through tauri/wry: the
   same versions, no new crate — check with `cargo tree`; a Linux-only `[target.'cfg(target_os = "linux")'.dependencies]`
   section), `unsafe` (the workspace lints; `skill://rust-conventions`), macOS and Windows untouched (rule 4), the line
   caps in `skill://project-map`, the boundary rules (a new shell module named in the map; `docs/architecture.md`
   §3.5).
5. **Tests and checks**: what a unit test can pin without a display (a pure decision, e.g. "a format count below 1
   blocks"), and the real-app recipe the final check runs: a private Xvfb with `env -u WAYLAND_DISPLAY GDK_BACKEND=x11`
   (never the owner's desktop, finding #1560), `xclip` set then killed, Ctrl+V and Shift+Insert into the merge window's
   Result and a side pane and a compare column; a fresh display (never-owned clipboard); the middle button after the
   PRIMARY owner quit; live pastes (3 lines, 300 lines, over 8 MiB in a compare column, Ctrl+Z after); a Wayland
   session if a private compositor is available on this host (say which, or why not).

## Output

Two or three options as above, each with its files, the paths it covers, what it leaves uncovered (if any) and why
that is acceptable or not, its risks, and the build split. A recommendation citing the visions (`docs/architecture.md`
§0). Read-only: no edits, no app launches beyond reading code and upstream sources.

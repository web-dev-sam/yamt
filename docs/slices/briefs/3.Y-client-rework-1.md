## Findings to fix

### #892 (boundary, block; `frontend/src/lsp/internal/server.ts:43`)

**Problem:** A server's run phase is stored in six places that must change together: `Server.#state`, `#attempt` and `#halting` (server.ts:43-45), plus `Attempt.run`, `hasExited`, `docs` and `folder` (attempt.ts:11-14, public and mutable, `docs`/`folder` written by server.ts:133,185). As a result "running" is answered two ways: `state.kind === "running"` (index.ts `#startIfServing`, formatting.ts:109) and `docs !== null` (formatting.ts:95, index.ts `open`/`synced`, server.ts:261). The two agree only because statements in `#initialize`, `halt`, `#exited` and `#fail` run in a set order. Growth: every later lifecycle rule (the status area's Restart, starting again on focus under plan #70) has to keep all six in step, and readers have to know which of the two "running" checks to trust.

**Fix:** Hold the run as one sum type in `Server`, for example `#run: { kind: "idle"; rest: ServerState } | { kind: "launching"; attempt } | { kind: "initializing"; attempt; folder } | { kind: "running"; attempt; folder; docs } | { kind: "halting"; done: Promise<void> }`. Derive the `state` and `docs` getters from it, and make `Attempt` keep only host, connection and its two promises, with `run`/`hasExited` exposed as read-only getters.

### #893 (boundary, block; `frontend/src/lsp/internal/serverDocs.ts:20`)

**Problem:** serverDocs.ts has four jobs: document sync (`open`/`change`/`close`); the problem slot and its pull loop (`OnServer.resultId/items/pulling/again` at :20-28, `push` :107, `pullAll`/`#pull`/`#pulled` :126-185, clearing in `closeAll` :92); the formatting request (:99); and the run's `Capabilities` (:10, :40). Meanwhile problems.ts, which the brief named "push + pull into one slot", only maps a diagnostic. Someone looking for where problems are kept opens the wrong file. Growth: the next pull rule and the next per-document request both land in the file that the AGENTS reading path routes every message through.

**Fix:** Move the per-document problem state and push/pull handling into problems.ts (a `DocProblems` held by each `OnServer`, with `push`, `pull`, `pullIfAsked`, `clear`). Move `Capabilities` to handshake.ts and the `textDocument/formatting` request to formatting.ts, with `ServerDocs` exposing `uriOf(entry)`. serverDocs.ts then keeps only didOpen/didChange/didClose.

### #894 (boundary, should; `frontend/src/lsp/internal/server.ts:193`)

**Problem:** server.ts is at 287 of the 300-line cap and holds both the lifecycle (start/stop/restart/halt/launch/initialize/release) and the routing of one attempt's messages (`#connect` :193, `#answer` :205, `#notified` :212, `#onEvent` :221). Growth: the next lifecycle rule hits `max-lines` and forces a split under deadline pressure.

**Fix:** Move the message routing into attempt.ts: `Attempt` builds its `Connection` and routes `HostEvent`s and notifications, calling back into `Server` only for `exited` and `log`.

### #895 (boundary, should; `frontend/src/lsp/internal/state.ts:62`)

**Problem:** A time-out on initialize is logged twice, once by connection.ts:56 ("No answer to initialize within 30 s; cancelled") and again by `failText` ("No answer to initialize within 30 s; stopped"); index.test.ts:1457-1458 checks for both lines. `MS_PER_SECOND` and the seconds wording are copied in connection.ts:31 and state.ts:4. Growth: the status area's log view will show two lines for one event, and changing the wording takes two edits.

**Fix:** Make `failText`'s `timedOut` case say "Stopped: the server did not answer initialize" with no duration, remove state.ts's `MS_PER_SECOND` and the `initializeTimeoutMs` parameter, and update index.test.ts:1458.

### #896 (boundary, should; `frontend/src/lsp/index.ts:27`)

**Problem:** `readyContext` turns `ServerContext` into `HostContext` (the null-root message, `process_id` → `processId`) inside the facade, while `HostContext` is declared in handshake.ts:8. handshake.ts:4 imports `Capabilities` from serverDocs.ts, so the edge runs from the producer to a consumer. Growth: index.ts gathers handshake rules as the facade grows, and the next handshake change has to be made in two files.

**Fix:** Move `readyContext` into handshake.ts as `hostContext(host)` next to `HostContext`, and declare `Capabilities` in handshake.ts so that serverDocs/formatting import it from there.

### #897 (boundary, should; `frontend/src/lsp/index.ts:76`)

**Problem:** `#retired` only ever grows: a stopped server stays listed after its halt has finished (open_risks 5, not accepted). Growth: plan #70 re-runs detection on every window focus, so every changed spec (an install hint that clears, edited settings) keeps a `Server` and its closures for as long as the window is open.

**Fix:** When a retired server's `halt()` resolves, filter it out of `#retired` (`void server.halt().then(() => { this.#retired = this.#retired.filter((s) => s !== server); })`); `destroy` keeps awaiting the ones still in the list.

### #900 (correctness, block; `frontend/src/lsp/internal/server.ts:110`)

**Problem:** While a server is `stopping`, `start()` or `restart()` queues `#halting.then(() => this.#startWhenIdle())`, and that callback launches a new run without checking whether anything later cancelled it. Three cases follow. (a) Restart and then Stop inside the shutdown window (up to 2 s shutdown + 2 s host kill): the server ends up `running` with `userStopped` true, so the user's Stop is ignored. (b) A `setSpecs` that drops or changes the spec in that window: the retired `Server` still launches, which leaks a process nobody stops. That process opens every served document and keeps calling `showProblems` under the same server name as the replacement, so the editor's single slot for that name gets problems from an old spec's run. (c) `destroy()` in that window resolves first (the queued callback is registered before destroy's `Promise.all`), and the run starts after destroy.

**Fix:** Track whether a start is still wanted (e.g. a `#wantsStart` flag set by `start`/`restart`, cleared by `halt()` before `restart` sets it again). The deferred callback launches only if the flag is still set. Add tests: restart then stop with `ignoresStop`, restart then `setSpecs([])`, and restart then `destroy()`; each should end with `host.servers` unchanged and the state `stopped`.

### #901 (correctness, block; `frontend/src/lsp/internal/server.ts:239`)

**Problem:** `#exited` closes the connection only for the current attempt. If a run exits while `#release` waits on `shutdown`, the request is not ended: the stop stays `stopping` for the full 2 s, then logs the false line 'No answer to shutdown within 2 s; cancelled' after 'Exited with code 0', and sends `$/cancelRequest` and `exit` to a run that is already gone. The test `rule 9: a server that exits during shutdown is not stopped again` (index.test.ts:1669) advances 2000 ms, so it locks in this delay instead of catching it.

**Fix:** In `#exited`, call `attempt.connection.close()` for every attempt, not only the current one, so the pending shutdown settles `closed` at once. Change the test to `settle()` without advancing 2 s, and assert the state is `stopped`, there is no 'No answer to shutdown within' line, and no `exit` or `$/cancelRequest` was sent after the exit.

### #903 (correctness, nit; `frontend/src/lsp/internal/server.ts:186`)

**Problem:** `#setState({ kind: "running" })` notifies listeners before the served documents are opened. A listener that calls `open()` synchronously gets that document opened by `LanguageServers.open` and again by the `documents()` loop: two `didOpen`s for one URI. Nothing gets harder to grow today, because Vue's watchers run asynchronously.

**Fix:** Open the served documents before `#setState(running)`, or make `ServerDocs.open` return early when `#docs.has(entry)`.

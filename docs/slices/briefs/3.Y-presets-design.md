# 3.Y-presets — design: language-server presets for more languages (board "Language server presets" row 1)

Agent: `designer` (read-only). Output: two or three file-level options plus a recommendation (your output schema). You
design; the orchestrator chooses. The build then runs as several implementer tasks (at most two at once), so the
recommendation must split the work into **disjoint** ownership lists: every file each build creates or changes, which
build owns a file two would touch, and the fixed contract the other then uses. Size guide per build: one concern,
≤ ~25 files, ≤ ~1,500 changed lines.

## What the owner wants (#993, 2026-10-15, verbatim)

"add language server presets for different languages like: ts/vue/rust/go/python(ruff,...)/php(phpcs,...)/...(popular
options)"

Read as (board section "Language server presets — more languages"): yamt recognizes the usual tools of more languages
the way it already recognizes oxlint, oxfmt, TypeScript and eslint: found in the repository, listed in the
once-per-repository question, shown in the status area, problems underlined in the Result, the formatter run by
Ctrl/Cmd+S; a tool the project uses whose server is missing shows "not installed" with that ecosystem's own install
commands. "Popular options": you propose the list per language, with a reason per entry.

## Settled (do not reopen; `skill://decision-record`)

`docs/plan.md` §2 **#67**, **#70**, **#71** (read all three whole). In short: yamt's own client in `frontend/src/lsp/`
(framework-free), Rust (`crates/lsp-host`) is a pipe that never learns a server's name; detection is a pure TS function
over the host's two generic lookups (`findProgram`, `projectFiles`); one question per repository covers detected and
added servers; **yamt ships no server and never installs one**; no login-shell PATH ("not found" lists the folders
searched); a crashed server stays stopped; only a formatting spec formats, the first formatting spec for a file wins
(spec order); problems in the Result only. Rejected in #67: "a command whose report yamt parses (one parser per tool;
problems only after a save)" — reopening that is a product question, not your call.

## Sourced facts (given; re-check only what is marked [INFERENCE])

yamt today:

- `frontend/src/lsp/internal/presets.ts`: one table `PRESETS` of 4 entries; `Look` is a sum type: `projectProgram`
  (oxlint, oxfmt: the program found inside the project, `findProgram(...).place === "Project"`), `typescript`
  (config + the project's `typescript` package version → `tsc --lsp`, `tsgo`, or `typescript-language-server`),
  `eslint` (config + package → `vscode-eslint-language-server`). Each preset: `fileTypes`, `formats`, `settings`
  (answers `workspace/configuration`, sent in `didChangeConfiguration`), `initializationOptions(workspaceUri)`.
- `frontend/src/lsp/internal/detect.ts`: a file's project = nearest folder with a `package.json` up to the repository
  root; files with none are served by no preset; one `projectFiles` batch per project (`candidates`); global installs
  never count for oxlint/oxfmt/TypeScript itself ("this project uses it"); names made unique per project
  (`"oxlint (frontend)"`).
- `frontend/src/lsp/internal/spec.ts`: `ServerSpec` (name, command, project, fileTypes, formats, settings,
  initializationOptions, install); `InstallHint` is npm-shaped (`package`, `program`, `folder`,
  `manager: PackageManager | null` = npm/pnpm/yarn/yarnBerry/bun, `reason` typescript|eslint); `serves(spec, path)`
  by project prefix + extension. `packageManager.ts` reads the `packageManager` field or the nearest lock file.
- `frontend/src/ui/serverText.ts` `installText(hint)`: per-manager project and all-projects commands
  (`MANAGER_COMMANDS`), the reason sentence, "Or install it any other way that puts <program> on your PATH", the
  come-back line; shown by `ui/ServerMenu.vue` and the log.
- `frontend/src/lsp/internal/languageIds.ts`: py, rs, go, sh present; no php, pyi, rb, c/cpp, …
- `frontend/src/lsp/internal/handshake.ts`: `rootUri` and one workspace folder = the spec's project folder;
  `synchronization.didSave: false` — yamt never sends `didSave`. `answers.ts`: fixed table (configuration from the
  spec's settings, workspaceFolders, registerCapability null, refreshes, showMessageRequest null + logged,
  applyEdit). Unknown server notifications are logged (`attempt.ts`).
- `crates/lsp-host/src/program.rs` `find`: `node_modules/.bin` in the project and each parent up to the root
  (`place: Project`), then each `PATH` entry (`place: Path`); Windows `PATHEXT`.
- `frontend/src/lsp/internal/added.ts`: servers added by hand (Settings: command + file types; project = root).
- `scripts/lsp-repo.sh`: the smoke repository for the real-app check (oxlint, oxfmt, TypeScript, ruff as an added
  server).

## What to design (open)

1. **The preset list.** Per language (TS/JS beyond today's four, e.g. Biome; Vue; Rust; Go; Python: ruff plus a type
   checker — pyright, basedpyright, ty; PHP: Phpactor, Intelephense, Psalm, …; and the "popular options": propose
   which other languages, e.g. Ruby, C/C++, shell, with a cut-off rule). For each server, from its own docs or source
   (cite): command + args; the repository signal that means "this project uses it" (manifest, config file, the
   program inside the project, a config section inside `pyproject.toml`/`composer.json`); file types; formats or
   not; `settings` / `initializationOptions` it needs; push or pull problems; server→client requests beyond
   `answers.ts`; whether problems need `didSave` (rust-analyzer's `cargo check` runs on save; yamt's Ctrl/Cmd+S
   writes the file — should yamt send `didSave` after its own write?); overlaps (two servers reporting the same
   problem; two formatters for one file type → which wins, by table order).
2. **Projects beyond `package.json`.** Which folder is a server's project per ecosystem (Cargo workspace root vs the
   crate; `go.work`/`go.mod`; `pyproject.toml`/`setup.cfg`/…; `composer.json`), and how a file maps to it; heavy
   servers (rust-analyzer) must not start once per crate of one workspace. Keep detection one pure function and one
   table (vision 2), not one detector per language with copied walking code.
3. **Programs inside the project outside `node_modules`.** Python virtualenvs (`.venv/bin`, `venv/bin`; Windows
   `Scripts`), Composer `vendor/bin`; servers usually installed globally (rust-analyzer, gopls): when a PATH-only
   server counts (the project's manifest says it uses the language) vs project-only tools. Who decides the folders —
   the Rust host (a fixed list) or the window passing them — given "Rust never learns a server's name".
4. **Install hints per ecosystem.** rustup (`rustup component add rust-analyzer`), Go (`go install …@latest`),
   Python (the project's tool from its lock file — uv, Poetry, PDM, pip/pipx — for ruff/pyright/ty), Composer, npm
   family as today. `InstallHint` as a sum type per ecosystem (vision 4); the texts in `ui/serverText.ts`.
5. **Vue.** What yamt needs for problems in `.vue` files: Vue's server with a relay of `tsserver/request` to a
   TypeScript server that loaded `@vue/typescript-plugin`; or the TypeScript server with the plugin alone; TypeScript 7
   / `tsgo` projects (plugins?). Cost each in files and in what the owner must read to follow one message.
6. **phpcs.** The owner named it; it has no server. Cost each path so the owner's answer (asked in parallel) can be
   built at once: (a) leave phpcs out, PHP gets Phpactor (with PHPStan/Psalm/PHP-CS-Fixer through it) and/or
   Intelephense; (b) phpcs through a generic wrapper language server the user installs (which one, how yamt configures
   it per tool, which other CLI linters that would cover); (c) yamt runs command-line linters itself (reverses #67).
7. **Settings.** Whether the Settings "Language servers" section should offer the presets when adding a server by
   hand (pick "ruff" → command and file types filled) — cost only; the owner is asked.
8. **Slicing and checks.** Rust and window builds with disjoint files; the smoke repository grows a project per
   language; how the real-app check gets servers on a machine without them (install into a throwaway folder: `uv tool`,
   `go install` with `GOBIN`, npm into a temp prefix; PHP is absent here — say what can and cannot be shown).

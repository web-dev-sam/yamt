## Findings to fix

### #957 (boundary, block; `frontend/src/ui/servers.ts:36`)

**Problem:** `serving` re-checks `serverViews.value.some(view => view.state.kind === "running")` before calling `servers.serving(path)`, while `LanguageServers.serving` (lsp/index.ts:102-104) already holds the rule "served only while running". The rule now lives in two places, and the copy also hides its real job, which is to make the caller's computed track `onChange`. If lsp's rule ever changes (for example, counts while `starting`), the ui guard will quietly override it. Growth: a second place decides when a file counts as served.

**Fix:** Keep the read only as a dependency and leave the rule to lsp: `serving: (path) => { void serverViews.value; return servers.serving(path); }`, with one comment line saying that the read makes the caller re-evaluate on `onChange`.

### #958 (boundary, block; `frontend/src/ui/ServerMenu.vue:91`)

**Problem:** Clicking the open server's own button cannot close its menu. `pressedElsewhere` (capture `pointerdown`) closes the menu because the button is outside the panel, then the button's `click` runs `openMenu` (ServerStatus.vue:45) and opens it again. To the user, nothing happens, though the brief says a press elsewhere closes the menu. The implementer's open risk "no toggle" describes the same defect.

**Fix:** Have ServerStatus pass the opener element to ServerMenu and make `pressedElsewhere` ignore presses inside it. In `openMenu`, close instead of reopening when `menu.value?.name === name`.

### #959 (boundary, block; `frontend/src/ui/ServerStatus.vue:20`)

**Problem:** The running dot uses `bg-success-border`, a border token (#29583c on Islands Dark, #bbdbc2 on Islands Light). It is nearly invisible on the panel; the implementer's own screenshot 03-crop.png shows this. The problem and warning dots use bright signal tokens, so "Running", the state users check most, is the one they can hardly see. Growth: the next status signal will also reuse a border token as a fill.

**Fix:** Have the orchestrator grant `style.css` and add one success signal token to both palettes, next to `--color-problem-error`/`--color-problem-warning` (for example `--color-success-signal`). Use it for `running` here and keep `success-border` for borders.

### #960 (boundary, should; `frontend/src/ui/servers.ts:5`)

**Problem:** `Screen` is the window's navigation type, and the store creates its ref (store.ts:101). It is defined in servers.ts, while writes to `screen` are split between store.ts (`pick`, `openSettings`, `closeSettings`) and servers.ts (`showServerLog`, `closeServerLog`). `shownLog` is refreshed only by servers.ts's writes, so the store's writes leave it stale. Growth: the next screen kind (the setup question or a settings section) has to be added in the servers module, and finding "what can change `screen`" takes two files.

**Fix:** Move `Screen` into a type-only `ui/screen.ts` that store.ts and servers.ts both import. Make `closeServerLog` reuse the store's files transition, or clear `shownLog` in `readLog` whenever `screen` is not `serverLog`, so `shownLog` has one rule.

### #961 (boundary, should; `frontend/src/ui/serverText.ts:4`)

**Problem:** The problem-count type is rebuilt by indexed access in three places: serverText.ts:4 `NonNullable<MergeHandle["problems"]["value"]>`, ServerStatus.vue:16 and MergeToolbar.vue:32. Meanwhile `ProblemCounts` already exists as a named export of `editor/index.ts`, and useMergeController.ts imports it without re-exporting it. Row 6b's finding #934 (promoted) flagged this same "type made with indexed access instead of a named alias" pattern. Growth: every new reader of the counts has to decode the indexed-access shape.

**Fix:** Add `ProblemCounts` to useMergeController.ts's `export type { … }` list (a one-line grant, the file is read-only here) and use it in all three places.

### #962 (boundary, nit; `frontend/src/ui/ServerLogView.vue:74`)

**Problem:** The Back button's word is a literal in the template; every other word in the log view comes from serverText.ts. Growth: nothing beyond one stray word.

**Fix:** Export `BACK = "Back"` from serverText.ts and render `{{ BACK }}`.

### #963 (correctness, block; `frontend/src/ui/ServerLogView.vue:87`)

**Problem:** Behaviour 5 says the log stays put when the user has scrolled up. That breaks once a server's log reaches `LogBook`'s 2000-line cap (`lsp/internal/log.ts` `LOG_LINES`): each new line drops the first one. The rows are keyed by `index`, so Vue rewrites every row's text in place while `scrollTop` stays the same. The text the user is reading then moves up one row for every stderr or `window/logMessage` line. A busy server such as typescript-language-server reaches the cap in one session. No test covers following the end or staying put. The report's open_risks says neither was exercised live.

**Fix:** Key each row by a stable identity (lines dropped so far + index, or a WeakMap id per `LogLine` object). While `following` is false, record the top visible row and its offset in a `flush: "pre"` watch and put it back in the `flush: "post"` watch. Put the 'how many lines were dropped above' rule in a pure helper (find the old first `LogLine` by identity in the new array) and give it a node test that covers the cap.

### #964 (correctness, should; `frontend/src/ui/servers.ts:37`)

**Problem:** `serverViews.value.some(running)` is there only so that a `computed` re-runs on `onChange`, because `servers.serving` is not reactive. It looks like a second condition, though. The surviving mutant `.every(...)` would hide the counts whenever any other server is not running (for example oxlint running, oxfmt stopped), and no test notices: the serving test has one spec and calls `serving` outside any computed. As more servers are added, someone may 'simplify' this clause and quietly break when the counts appear.

**Fix:** In servers.test.ts, add a second, stopped spec to the serving test (this kills `.every`). Add a case where `computed(() => slice.serving(path))` turns true after Start (this kills dropping the reactive read). Make the read's purpose plain, e.g. a one-line comment that it subscribes to `onChange`.

### #965 (correctness, should; `frontend/src/ui/serverText.ts:119`)

**Problem:** In fixture mode every spec is `failed{noHost}`, and the menu offers Start and Restart for it. Neither does anything: `Server.#startWhenIdle` needs a host. So the demo page shows two buttons that do nothing next to 'Runs only in the app'. If this stays, every later screen that uses `serverActions` copies the dead buttons.

**Fix:** Return `[]` from `serverActions` for `failed` with `reason.kind === "noHost"`, and add that row to the 'rule 3' test.

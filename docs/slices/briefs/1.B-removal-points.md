# Slice 1.B — removal points drawn on the side panes

The owner: where a side removed text, "it could show a small zero character highlight with its
padding at the position where it got deleted — that is usually intuitive". Decision: plan §2 #31.
Slice 1.A put the places on every domain chunk: `chunk.words.local.removedAt` /
`chunk.words.remote.removedAt` (`InlinePoint<L> = { line, column }`, zero-width, UTF-16 column
within that line, at most the line's length). This slice draws them.

## Target

Owned: `frontend/src/editor/internal/{words,decorations}.ts`, their tests
`frontend/src/editor/internal/{words,decorations}.test.ts`, `frontend/src/editor/theme.css`.
Read-only: everything else — `ipc/**` (use `Chunk["words"]` as it is), `style.css` (no new
palette token unless the screenshot proves the existing word tokens unreadable as a bar; then
report it instead of adding one), `ui/**`, `connectors/**`, fixtures, configs, `docs/**`,
`.omp/**`, Rust.
Non-goals: points in the middle pane; hover text or tooltips; showing what was removed; keyboard
navigation.

## Behaviour (what the user sees)

- Each removal point of an open block is a thin bar in the block's word colour (the same colour as
  that block's brighter word marks: purple in a conflict, blue in a modified block), the height of
  the text line, about 2 px wide with a little breathing room: visible at a glance, never mistaken
  for the cursor (no blinking; the cursor is thinner and a different colour).
- A bar takes no text width: the characters after it stay exactly where they would be without it,
  so columns still line up with the other panes.
- A bar at column 0 sits at the start of the line's text area; a bar at the end of a line sits
  right after its last character (also on an empty line).
- Same gating as the word marks, on the side panes only: drawn exactly while the block's tint is
  drawn (resolved blocks lose both, undo restores both, a half-applied conflict keeps both).
- Selecting text over a bar keeps the selection visible; the bar does not block clicks or
  cursor placement.

## Contract

- One decoration source per pane stays the rule (marks exactly where the tint is): add the bars to
  what the side pane's existing tint filter feeds; no second filter, no new `StateField`.
- Use `Decoration.widget` (zero-width marks are not drawn by CodeMirror); widgets compare equal
  when their tone is equal (`eq`), so redraws don't rebuild DOM; `ignoreEvent` keeps clicks
  working.
- Colours only from palette tokens (VU17) through the tone classes in `theme.css`.

Ride-along (logged nit, do it): #213 `decorations.ts` imports `StateField` as a value but uses it
only as a type; import it as `type StateField` like the rest of the repo.

## Tests (`node` project, `EditorState` only)

- A conflict and a modified block with points: the side panes carry one widget per point at
  `doc.line(line + 1).from + column`, with the block's tone; none on the middle pane.
- A resolved block has none; undo brings them back; a half-applied conflict keeps them on both
  sides.
- Points at column 0, mid-line and line end of a CRLF document land on the right positions.

`editor/` is outside the mutation run: break each tested rule by hand once (off-by-one column,
skip the status gate, draw on the middle pane), paste the failing assertion, restore.

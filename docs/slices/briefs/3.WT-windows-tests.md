`17849b0`); `main` still has the same code, so 0.5.1 cannot be tagged until it passes. Test-only change: no product
file changes, no changelog line.

## Facts (given)

- The failure, verbatim from the owner's log:
  `FAIL yamt-compare::opening a_locked_open_writes_nothing` -
  `panicked at crates\compare\tests\opening.rs:18:43: called Result::unwrap() on an Err value: Os { code: 33, kind:
  Uncategorized, message: "The process cannot access the file because another process has locked a portion of the
  file." }`. 636 of 637 tests passed.
- `opening.rs:18:43` is the `.unwrap()` after `fs::read(entry.path())` in `files_in`. In
  `a_locked_open_writes_nothing` (`:143-155`) `files_in` runs while `first` holds the store's lock, and it reads every
  file in the folder, the `lock` file included.
- The lock is `File::try_lock` (`crates/compare/src/files.rs:27-44`). On Windows that is `LockFileEx`, a mandatory
  byte-range lock: reading the locked range through any other handle fails with `ERROR_LOCK_VIOLATION` (33), also
  from the same process. On Linux and macOS it is `flock(2)`, advisory, so the read works there.
- `DirEntry::metadata()` on Windows comes from the directory listing and opens no file (std docs: "cheap to call (no
  extra system calls needed)"), so a locked file's length can be read.
- The five warnings (owner's log; reproduced here with
  `cargo clippy --tests --target x86_64-pc-windows-msvc -p yamt-compare -p yamt-cli -p yamt-lsp-host -p yamt-gitio`,
  the target is installed): items used only by `#[cfg(unix)]` tests -
  `crates/cli/tests/commands.rs:3` `use std::ffi::OsStr;` (only user: `:95-100`, which already has its
  `use std::os::unix::ffi::OsStrExt;` inside the function);
  `crates/lsp-host/tests/run.rs:19-20` `OUTPUT_DRAIN`, `DRAIN_SLACK` (only user: `:230-244`);
  `crates/gitio/tests/operations.rs:6` `conflict_repo` and `:9` `Error` (only user: `:114-...`).

## Contract

Every test keeps its name and what it proves. `a_locked_open_writes_nothing` still fails if a locked open creates,
removes or changes any file in the folder, the `lock` file included (by name; its bytes are always empty and cannot be
read on Windows while held).

## Change

1. `opening.rs`: `files_in` (or the locked test's own snapshot) never reads the `lock` file's bytes; the comparison
   still sees every file name, the lock's included, and every other file's bytes (the lock's length through
   `DirEntry::metadata` is a fine stand-in). Pick the simplest shape a Rust beginner reads at once; one line saying
   why the lock's bytes are not read (the Windows fact above). The other tests that use `files_in` behave as before.
2. The three warning sites: move each unix-only item to where its only unix test uses it (inside the function, as
   `commands.rs:98` already does), or put `#[cfg(unix)]` on it - whichever reads better in that file. No `allow`.

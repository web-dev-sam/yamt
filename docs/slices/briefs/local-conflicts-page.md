# Slice LocalConflictsPage — the page shows yamt's own conflict results as they land (frontend; wires the window)

Feature: the merge-request list checks conflicts locally (request `docs/slices/request-local-conflict-check.md`
rules 3, 7, 8, Acceptance "WebKit fixture" and "Real app"; design `docs/slices/briefs/local-conflicts-design.md`
option A, §2.1 "Words and icon", §3 A "Refresh", "Closed page"). Runs after `LocalConflictsCheck` has landed and the
orchestrator has run `just bindings` (the generated `Readiness`, `CheckedRow`, `ListMessage` below are then in
`frontend/src/ipc/bindings.ts`). **This slice wires the window together**: its real-app run is the feature's first
end-to-end proof.

## Contract

Generated by `LocalConflictsCheck` (given): `Readiness` gains `{ kind: "mergesCleanly" }`; `CheckedRow = { iid:
MergeRequestIid; readiness: Readiness }`; `ListMessage = { kind: "page"; page: MergeRequestPage } | { kind: "end";
end: ListEnd } | { kind: "checked"; row: CheckedRow }`. Rust sends `checked` messages only after `end`, on the load's
own channel, in order (plan #131: channel messages keep their order), only for rows whose readiness changed; the
command answers after the last one.

Fixed (add-only):

```ts
// ipc/mergeRequestDomain.ts
export type CheckedRow = { readonly iid: MergeRequestIid; readonly readiness: Readiness };
export function toCheckedRow(raw: Generated.CheckedRow): CheckedRow; // iid branded as toRow does

// ipc/MergeRequestSource.ts — the one changed signature
/**
 * Every page reaches `onPage` before the returned promise settles, and none after. `onChecked` gets this load's
 * local results (rows yamt's own merge changed), after the promise settled, and never another load's.
 */
listMergeRequests(
  onPage: (page: MergeRequestPage) => void,
  onChecked: (row: CheckedRow) => void,
): Promise<SourceResult<ListEnd>>;

// mergeRequests/internal/readiness.ts
export type Readiness = /* today's five */ | { readonly kind: "mergesCleanly" };
export type ReadinessIcon = /* today's five */ | "circle-dashed-check";
// readinessText({ kind: "mergesCleanly" }) === "No conflicts (checked locally). GitLab has not checked the rest yet"
// readinessIcon({ kind: "mergesCleanly" }) === "circle-dashed-check"
```

`ui/MergeRequestReadiness.vue`: `LOOKS["circle-dashed-check"] = { icon: CircleDashedCheck, tone: "text-fg-muted" }`
(`~icons/lucide/circle-dashed-check`). `ipc/index.ts` exports `CheckedRow` beside the other merge-request types.

The slice's rule (`ui/mergeRequests.ts`, the one new writer of `rows` besides a load's pages): a load's checked row
replaces the `readiness` of the row with its iid among **that load's rows** — in its buffer while it is buffered and
not ended (a refresh over shown rows, `mergeRequests.ts:98-118`), in `rows` while the shown rows are that load's;
otherwise it is dropped (another load's rows are shown, or a buffered load failed and its rows were never shown). An
iid not among them is dropped. No report, no problem, no log line per row (rule 8). Closing the page changes nothing:
results still land in the slice's rows (architecture §5.1 l. 1075).

# Slice 3.R-removal-tooltip — the removed code in a tooltip on the bar

Board "Removal tooltip" row 2. Product rule: `docs/plan.md` §2 **#73** ("Window"); the bars themselves are #31 with the
owner's new size (4 px wide, 2 px room on each side, owner commit `3e465cb`). Row 1 is committed before you start: every
chunk side's `words[side].removals` is `readonly { at: InlinePoint; text: string }[]` (`ipc/domain.ts`), and
`editor/internal/words.ts` places one `RemovalPoint` bar per removal at `removal.at`. What `text` holds (plan #73
"Engine"): the removed base text with `\n` line breaks; removed whole lines before the bar's line end with `\n`, removed
whole lines at a chunk side's end (bar at the end of the line before) start with `\n`; never empty.

Facts (given; re-check only [INFERENCE]):

- Bars: `words.ts` `RemovalPoint` (a zero-width `span.chunk-removal`, `ignoreEvent()` false, `eq` by class name), built by
  `sideWordDecorations`, provided by `decorations.ts` `sideDecorations` from the side's status mirror: a side that is
  applied or ignored loses its bars in the same transaction; undo brings them back.
- Bar CSS: `editor/theme.css` lines 53–77 (`.chunk-removal` inline-block, width 0, `::after` 4 px wide at `left: -1px`).
  The owner's commit put the 2 px room on each side as the Tailwind class `px-0.5` on the widget's class name
  (`words.ts:13`); that fails 3 tests in `words.test.ts` (they pin the class list) and is the only Tailwind class in
  `editor/` TypeScript (#1056).
- `pnpm -C frontend fmt:check` fails on `src/editor/theme.css` (`.fold-wave-hover>.strip-wave-line`, no final newline)
  and `src/style.css` (no final newline), both from the same commit (#1056).
- Tooltips: only the Result pane has `tooltips({ parent: document.body })` (`paneViews.ts:75`, with the reason in its
  comment: under a transformed or contained ancestor CodeMirror lays tooltips out inside the pane). Problem tooltip
  styles: `theme.css` 262–282 (`--color-panel`, `--color-control-border`, radius 4 px). Browser-test precedent for a
  hover tooltip on top of the panes: `editor/problems.browser.test.ts` (`userEvent.hover`, `covers`).
- Code font: `pane.ts` `paneTheme` (`var(--font-mono)`, 13 px, `LINE_HEIGHT_PX`, ligatures off); syntax colours:
  `pane.ts` `paletteHighlight` (`HighlightStyle`), the file's grammar in `languageCompartment` (loaded on demand; may be
  absent). `@lezer/highlight` is an allowed dependency (`skill://cm6-rules` Dependencies).
- `@codemirror/view` 6.43.14 `hoverTooltip` (`dist/index.js` 10818–10843): over a widget it asks the source with the
  widget's position; over text it asks with `posAtCoords` when the pointer is within one character width of that
  position — so a plain `hoverTooltip` source answering "a bar at `pos`" also opens on the characters beside the bar.
  Options `hideOn(tr, tooltip)`, `hideOnChange`, `hoverTime` exist; `closeHoverTooltips` is an effect.
- `just app-session` (`frontend/scripts/app-session.ts`, `scripts/app-session/{args,drive}.ts`) has `click` (by
  accessible name), `press`, `type`, `scroll`, `read`, `shot`, `colours`; no command moves the pointer without clicking.

## Change

1. **The owner's bar, kept, in one place.** Remove `px-0.5` from the widget's class name and give `.chunk-removal`
   `padding-inline: 2px` in `theme.css` next to the bar's width: the bar renders exactly as in `3e465cb` (4 px box, the
   `::after` bar where it is now). Show it with a before/after measurement of the span's and the bar's rects in the
   browser test or the real app. The 3 failing `words.test.ts` tests pass again unchanged. `oxfmt` `theme.css` and
   `style.css`.
2. **The bar knows its text.** `RemovalPoint` carries the removal's `text`; `eq` compares tone and text (a reused DOM node
   must never show another removal's text). One place builds where bars sit (`sideWordDecorations`); the tooltip reads
   the text from the bar under the pointer, never recomputes positions from `chunk.words` (vision 2).
3. **The tooltip** on both side panes (plan #73 "Window"), behaviour:
   - opens when the pointer rests on a bar's own box (the 4 px span) for CodeMirror's usual hover delay; never when
     the pointer is on the characters beside it (see the `hoverTooltip` fact; the mechanism is yours — a source that
     checks the bar under the pointer, or a small plugin on the widget's DOM with `showTooltip`; report which and why);
   - shows the text as a code block: the panes' code font, size, line height and the pane's tab width; the file's syntax
     colours through `paletteHighlight` and the pane's grammar at hover time (`@lezer/highlight` `highlightCode` or
     `highlightTree`), plain when the pane has none; whitespace and line breaks kept;
   - leaves out the one line break joining the text to the bar's line: a leading `\n` when the bar sits at the end of
     its line, a trailing `\n` when it sits at column 0 (exactly one; a removed blank line inside stays);
   - a text with nothing visible after that (only spaces, tabs, line breaks) shows its whitespace as marks in the muted
     colour: `·` per space, `→` per tab, `↵` per line break — so the tooltip is never empty (the catalogue's `\t` and
     blank-line removals);
   - a long text: the box is bounded (a width and a height you choose, about 640 px by 20 lines; named constants or
     CSS values in one place) and scrolls inside;
   - the pointer may move from the bar into the tooltip (to scroll, select and copy) without it closing; it closes when
     the pointer leaves both, and when the bar goes (its side applied or ignored, by click, key or bulk apply);
   - placed in `document.body` like the Result's problems, so it shows above the panes and gap strips; styled like the
     problem tooltip (panel colour, control border, 4 px radius) in both themes, using only existing colour variables.
     Pure rules (which line break to leave out, whitespace marks) live in one small function with node tests.
4. **`app-session hover`**: a command that moves the pointer onto an element without clicking and leaves it there,
   its target given like `scroll`'s (accessible name or CSS selector, `--role`, `--nth`; bars have no accessible name);
   `args.test.ts` covers its parsing.

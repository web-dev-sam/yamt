## Fix (findings verbatim, with the orchestrator's decision)

1. **#828 [block, boundary] `folds.ts:126`** — "Brief Contract 3 and design option 1 say the side mirror
   holds only per-run counts. `sideFoldField` instead keeps a full `readonly Fold[]` in each side's state,
   which includes every level's `center` range copied from `foldRuns` and never mapped, so after the first
   edit in the middle each side pane holds a stale second copy of the middle's hidden positions (vision 2)."
   Fix: "Make `sideFoldField` a `StateField<readonly number[]>` (the counts set by `showSideFolds`, as
   `sideStatusField` does). Have the side's `foldView` derive its levels from the fixed `runs` and those
   counts through one helper that `shown` also uses, e.g. `innermost(levels, count)`. Then the 'keep the
   innermost N levels' slicing is written once and no side state carries a `center` range."
   With it **#829** (TS7): `pushFolds(field, sides, views)` takes two parameters of one type, so a swap
   compiles — distinct value types (or one object parameter) make it a type error. The strips' joins read
   each side's displayed wave: keep that reading correct through the new counts field (same helper).
2. **#830 [should → promoted] `pane.ts:277`** — the app builds documents through `paneDocs(data)`, while
   `CenterPane.doc` and `paneState`'s `doc: string | Text` branch remain only for tests, "so seven test
   files build panes by a different path than the app does". Fix: "Have `centerPane` return only the kind
   (e.g. `centerKind(middle, readOnly)`), make `paneState` take `doc: Text`, have tests build their
   documents with `paneDocs(data)`, and stop exporting `paneDoc`."
3. **#831 [should → promoted] `index.ts:57`** — `index.ts` near 300 lines with fold wiring spread over
   five imports, the `#folds` record, `Folding` and three extensions per pane. Fix: "Put the fold wiring in
   one factory in `folds.ts`/`foldView.ts`, e.g. `centerFolds({ field, sides, hovered, views })` and
   `sideFolds({ sides, pane, hovered, center })`, each returning an `Extension`, so `index.ts` adds one
   entry per pane." The frame's access to the fold fields (added by the strips slice) stays one place.
4. **#832 [should → promoted] `foldView.ts:18`** — the 1 px / 2 px strokes are private to `foldView.ts`;
   use `WAVE_STROKE_PX` / `WAVE_HOVER_STROKE_PX` from `connectors/index.ts` (the strips use the same).
5. **#834 [promoted, comment only] `foldView.ts:116`** — one CP1 line at the inline `Decoration.replace`
   saying why it is not `block: true` (CodeMirror's vertical motion skips block widgets, so the cursor
   could not stop on the wave line, plan #63). The doc edits are the orchestrator's.
6. **#836 [block, correctness] `foldView.ts:140`** — "In the middle pane, pressing Delete with the cursor at
   a wave's `from`, or Backspace at its `to`, deletes every hidden line of that run with one key. Because
   the whole replaced range `[from, to]` is atomic, `@codemirror/commands` `deleteBy` → `skipAtomic`
   (dist/index.js:1186-1215) widens a one-character delete to the whole range … The cursor starts there:
   the middle's first cursor is at 0, which is run 0's `from`." Decision (plan #63 amended): any `delete.*`
   user event from an empty cursor that would remove a displayed hidden range whole (Delete at `from`,
   Backspace at `to`, the word/line variants included) changes no text and shows that run's next step
   instead (a middle-pane `EditorState.transactionFilter`, as the reviewer proposes). A delete of a
   selection the user extended across the wave line stays a normal delete. Test: a `delete.forward`
   transaction over `[from, to]` from a cursor at `from` leaves the text unchanged and drops the run's
   outer level; the same for `delete.backward` at `to`; a selection delete across a wave still deletes.
7. **#837 [should → promoted] `folds.test.ts:268`** — the "non-empty selection within `[from, to]`" clause
   of `holds` has no test. Add `selectMatch({ from, to })` with both ends exactly on level 0's `from` and
   `to`, expecting the reveal.
8. **#838 [should → promoted] `folds.test.ts:288`** — the side/middle `revealKeep` test feeds identical
   input. Use a run whose left ranges differ from the centre's (run 2 of `twoChanges`: local has one extra
   line), feed a left selection inside the left range but outside the centre's, and assert the side's
   reveal gives the keep the middle gives for the matching centre position — through the side's real path
   (`sideFoldField` + its reveal on a side state), not only `revealKeep`.

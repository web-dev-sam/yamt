## Findings to fix

### #905 (boundary, block; `src-tauri/src/commands.rs:139`)

**Problem:** This patch takes `commands.rs` to 411 lines, over RS6's limit of 400 (no detector sees file length; the implementer's open risk). The file also takes on a second job: its `pub(crate) mod tests` is now the shared mock-window harness that `servers.rs` tests import (`Window`, `open_window`, `invoke`). Every new command group has to grow the file where session commands are registered and tested, and Save (3.Z) also touches this file.

**Fix:** Move the mock-window harness (`Window` with `app`/`webview`/`repo`, `file`, `open_window`, `open_window_on`, `Window::invoke`) into its own `#[cfg(test)] mod mock_window;` file in `src-tauri/src/`, used by both `commands::tests` and `servers::tests`. Keep `exit_on_close`/`unmerged` in `commands::tests`, which drops back below 400 lines and becomes private again.

### #906 (boundary, should; `src-tauri/src/commands.rs:42`)

**Problem:** `with_session` now builds and manages `Mutex<Host>` too, from `Mutex::new(host)` and not from `servers::HostState`. A reader looking for where the host is made finds a function named for the session, in the session-command module, which now imports `yamt_lsp_host::Host`. The design put this in `window.rs`. The next piece of managed state will land in a function whose name already lies.

**Fix:** Rename it to say it manages all app state (e.g. `with_state(builder, session)`), or let `servers.rs` own a `manage(builder, root) -> Builder` that `with_session` calls. Either way the `Mutex<Host>` is built as `HostState`, next to its type alias.

### #909 (correctness, block; `crates/lsp-host/src/run.rs:204`)

**Problem:** Survivor 204:20 (`delete !` in wait_for_stop) stops every server about 20 ms after it starts, and all tests still pass. They pass because every test sends its message within that 20 ms (the message is queued before `Close`), and the kill test's 2 s grace starts at about 20 ms anyway. No test shows that a run stays alive while idle until someone stops it.

**Fix:** Add a `tests/run.rs` case: start lsp-echo, sleep about 300 ms (well over EXIT_POLL), check `is_alive(pid)`, then send a message and expect its echo.

### #910 (correctness, block; `crates/lsp-host/src/run.rs:192`)

**Problem:** Nothing tests the output drain, so the `Exited comes once, last` contract (in the HostEvent doc and in bindings.ts) and its 1 s cap are unproven. Survivors 191:34 (`+`→`-`), 192:11 (delete `!`) and 192:74 (`==`/`>`) remove the drain, so `Log`/`Message` can arrive after `Exited`; the window then logs a crashed server's last stderr lines after "Exited with code N". Survivor 192:56 (`&&`→`||`) turns the cap into an endless wait whenever a grandchild still holds the pipes: `Exited` is never sent and `stop_all` never returns, so the app hangs on close. The poll this relies on (the implementer's deviation 'a server that exits while something else holds its stdout still produces Exited') is also untested.

**Fix:** Give lsp-echo two commands. (1) `burst N`: write N stderr lines (about 60 KB) and exit; assert all N `Log`s come before `Exited` via `exited_once`. (2) unix `orphan`: spawn a sleeping child that inherits stdout/stderr, then exit 3; assert `Exited{Some(3)}` arrives within OUTPUT_DRAIN plus slack.

### #911 (correctness, block; `crates/lsp-host/src/frame.rs:3`)

**Problem:** The tests use `MAX_MESSAGE_BYTES` only by name, so survivors 3:46 and 3:53 (`64+1024*1024` ≈ 1 MiB, `64*1024+1024` = 65 KiB) pass. With those values the host would stop any server that sends a message above that size, and completion lists, semantic tokens and workspace diagnostics routinely go above 65 KiB. Survivor 5:40 (8 KiB header cap → 1032 bytes) is the same unpinned-constant gap.

**Fix:** In `a_length_above_64_mib_is_too_large_and_64_mib_is_read`, write the lengths as literals (`Content-Length: 67108864` read, `67108865` → `TooLarge { bytes: 67108865 }`). In `a_header_line_without_end_is_broken_after_8_kib`, feed a literal 8192-byte header line that is accepted and an 8193-byte one that is refused.

### #912 (correctness, block; `src-tauri/src/servers.rs:42`)

**Problem:** Survivors 43:5 (`forward` → `()`), 54:5 (`send_to_server` → `()`) and 61:5 (`stop_server` → `()`) leave the app's only path between a run and the page unproven. With `forward` → `()`, no event ever reaches the window and every server stops at its first output; with the other two, messages are never delivered and `stop` never produces `Exited`. Behaviour 2's 'when a send fails the run stops itself' has no test, and no smoke exercises these commands (the window does not call them yet), so VF7 (c) does not apply.

**Fix:** Add a `servers.rs` test that calls `start_server(app.state(), command, Channel::new(closure collecting the bodies))` directly (Channel::new is public in tauri 2.12.1, ipc/channel.rs:378), with a unix framed echo such as `cat` on PATH. Then `send_to_server` → the echoed `Message` arrives, `stop_server` → one `Exited`. Add a second channel whose closure returns `Err`: the run's pid is gone after its next output.

### #913 (correctness, block; `src-tauri/src/commands.rs:43`)

**Problem:** Behaviour 2 says a reloaded page's runs stop themselves, but they do not. Tauri 2.12.1's `Channel::send` only fails when `webview.eval` fails (implementer's open risk; confirmed in ipc/channel.rs:413-449), and nothing in the app prevents reload: F5/Ctrl+R are not blocked in src-tauri or ui. After a reload the new page starts a second set of servers next to the orphaned ones, and these run until the window closes (double memory; servers that lock their workspace, such as rust-analyzer's cargo lock, block each other).

**Fix:** In `with_session`, register `Builder::on_page_load`; on `PageLoadEvent::Started`, signal every run without joining (a `Host::stop_every` that only sends `Stop`). The first load finds no runs; each reload ends the previous page's servers.

### #914 (correctness, should; `crates/lsp-host/src/run.rs:164`)

**Problem:** `read_log` returns `OutputClosed` at stderr EOF or on a read error, and that stops the whole run. A server that closes or redirects its stderr while still serving over stdout is therefore killed, although only stdout EOF (or the child's exit, already polled) means the server is gone. Nothing gets harder as the app grows beyond this case.

**Fix:** When stderr ends, end the stderr reader without a stop request (only `read_messages` sends `OutputClosed`). Add an lsp-echo `close-stderr` command whose run still echoes afterwards.

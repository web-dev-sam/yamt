# Slice 0.1 — merge-core: chunk types, `compute_chunks`, `apply_non_conflicting`, invariants

The merge engine's heart (plan §4 "Chunk model", architecture §3.1). Pure function from three
texts to a sorted list of classified chunks. Everything later — highlighting, connector bands,
scroll anchors, bulk apply, the PhpStorm comparison — reads these chunks.

## Contract (fixed; you may add private items, never change these)

```rust
// crates/merge-core/src/lib.rs re-exports exactly these public items (RS10)
pub struct BaseLine(pub u32);     // 0-based line index in the base text
pub struct LocalLine(pub u32);    // … in the local text
pub struct RemoteLine(pub u32);   // … in the remote text
pub struct LineRange<L> { pub start: L, pub len: u32 }
impl<L> LineRange<L> { pub fn end(&self) -> L; pub fn is_empty(&self) -> bool; }  // end = start + len (exclusive)
pub enum ChunkKind { LocalOnly, RemoteOnly, BothSame, Conflict }
pub struct ChunkId(pub u32);      // == index of the chunk in the returned Vec
pub struct Chunk {
    pub id: ChunkId,
    pub kind: ChunkKind,
    pub base: LineRange<BaseLine>,      // may be empty (pure insertion)
    pub local: LineRange<LocalLine>,
    pub remote: LineRange<RemoteLine>,
}
pub struct Options { pub gap: u32 }   // impl Default → gap: DEFAULT_GAP
pub const DEFAULT_GAP: u32 = 1;       // the only tuning constant (RS13); goldens in 0.3 tune it
pub fn compute_chunks(base: &str, local: &str, remote: &str, opts: &Options) -> Vec<Chunk>;
pub fn apply_non_conflicting(base: &str, local: &str, remote: &str, chunks: &[Chunk]) -> String;
```

Derives (decided here, recorded as plan §2 row 25):

- Line newtypes, `ChunkId`: `Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord, Hash`.
- `LineRange<L>`, `ChunkKind`, `Chunk`: `Clone, Copy` where possible, `Debug, PartialEq, Eq`.
- Every type that crosses to the frontend (`BaseLine`, `LocalLine`, `RemoteLine`, `LineRange`,
  `ChunkKind`, `ChunkId`, `Chunk`) also derives `serde::Serialize` and `specta::Type`. Default
  serde representation, no renames: newtypes serialize as a bare number, `ChunkKind` as
  `"LocalOnly"` etc., `LineRange` as `{ "start": n, "len": n }` — exactly the shape in
  architecture §4. Session and the app reuse these types instead of mirroring them (vision 2:
  one source of truth). `Options` derives neither.

Line model (architecture §3.1 step 1): a line is the text up to and including `\n`; split on
`\n` only, `\r` stays in the line, the last line may lack `\n`. `""` has 0 lines, `"a\n"` 1,
`"a\nb"` 2. So CRLF↔LF and a missing final newline are real differences, exactly as git sees
them. `imara-diff`'s `&str` token source already tokenizes this way.

## Change

1. **Types** as in the Contract. `LineRange::end()` needs `start + len` on three newtypes: one
   small private trait with three impls, or three concrete impls — no `macro_rules!` (RS3).
   Constructive ranges only: there is no `{ start, end }` constructor that can invert (vision 4).
2. **Diff**: `d1 = diff(base, local)`, `d2 = diff(base, remote)` with `imara-diff`,
   `Algorithm::Histogram`, then `Diff::postprocess_lines` (the library's readable hunk placement;
   vision 5 — the boring default; goldens in 0.3 may revisit). Each hunk becomes
   `{ base: Range, side: Range }`; both lists sorted by base start.
3. **Sweep** (architecture §3.1 step 3): merge the hunks of both sides, in base order, into
   regions. Open a region at the first hunk; absorb the next hunk while
   `next.base.start <= region.base.end + opts.gap`. Two empty insertions at the same base line
   always land in one region (this is the add/add conflict).
4. **Side ranges** (step 4): a region's local and remote ranges are the region's base endpoints
   mapped through that side's edit script — not the union of that side's hunks. A region only
   local touched still gets a correct (unchanged) remote range. This is what connectors and
   scroll anchors rely on.
5. **Kind** (step 5): hunks from one side only → `LocalOnly` / `RemoteOnly`; from both → compare
   the region's local text with its remote text: equal → `BothSame`, else `Conflict`.
6. **`apply_non_conflicting`**: walk base; outside chunks copy base lines; for each chunk emit
   `LocalOnly` → its local lines, `RemoteOnly` → remote lines, `BothSame` → local lines,
   `Conflict` → **its base lines** (the result pane starts from base, plan §2 #9). Output bytes
   are a concatenation of input line slices — never re-joined with a chosen separator.
7. **Tests** (RS11; file names yours):
   - Proptests (`proptest`, ≥ 256 cases each, strategies that make overlapping edits likely:
     derive local/remote from base by random insert/delete/replace of lines drawn from a small
     alphabet that includes `"x\n"`, `"x\r\n"`, `"\n"` and a last line without `\n`; also some
     fully independent triples). Each invariant is its own named test:
     1. chunks sorted by `base.start` and pairwise disjoint in base, local and remote space
        (RK14); `chunks[i].id == ChunkId(i)`.
     2. **reconstruction**: base with every chunk's base range replaced by that chunk's local
        lines `==` local, byte for byte; same for remote. (Catches every mapping off-by-one.)
     3. every `LocalOnly` chunk's remote text equals its base text; every `RemoteOnly` chunk's
        local text equals its base text; every `BothSame` chunk's local text equals its remote text.
     4. `local == base` ⇒ every chunk is `RemoteOnly`; `remote == base` ⇒ every chunk is
        `LocalOnly`; `local == remote` ⇒ no `Conflict`.
     5. `apply_non_conflicting`: `local == base` ⇒ result `== remote`; `remote == base` ⇒
        `== local`; `local == remote` ⇒ `== local`.
     6. add/add: `base == ""` and `local`, `remote` both non-empty ⇒ exactly one chunk, base range
        empty at line 0, kind `BothSame` if `local == remote` else `Conflict` (RK2; this corrects
        the looser wording in architecture §3.1).
     7. every chunk is a real change: `LocalOnly`/`BothSame` → local text ≠ base text;
        `RemoteOnly` → remote text ≠ base text; `Conflict` → local text ≠ remote text.
   - **Five synthetic triples**, hand-computed, each one test with the full expected
     `Vec<Chunk>` written as a Rust literal and the expected `apply_non_conflicting` text:
     1. a local-only edit and a remote-only edit far apart → `[LocalOnly, RemoteOnly]`;
     2. the same edit on both sides → `[BothSame]`;
     3. overlapping different edits → one `Conflict` whose three ranges differ in length;
     4. add/add (`base = ""`) → one `Conflict`, base range `{start: 0, len: 0}`;
     5. grouping boundary: a local and a remote edit separated by exactly `DEFAULT_GAP`
        unchanged lines → one chunk; separated by `DEFAULT_GAP + 1` → two chunks; plus one
        pure end-of-file insertion and one change that is only a missing final `\n`.
        The JSON `expected.json` form of goldens belongs to 0.3 (its `classify --json` produces
        it); here the expectation is the Rust literal.

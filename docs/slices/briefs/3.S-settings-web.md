### Keys

6. **Defaults** (today's keys; `DEFAULT_KEYS` is checked by a test citing each source):
   apply Enter, Space · ignore Backspace, Delete, x · next-change ArrowDown · previous-change
   ArrowUp · left-side ArrowLeft · right-side ArrowRight · undo Mod-z · redo Mod-Shift-z, Mod-y ·
   find Mod-f · find-next F3 · find-previous Shift-F3 · close-find Escape · indent Tab · outdent
   Shift-Tab. (Ctrl/Cmd+Shift+Y no longer redoes; the middle's Mod-[ / Mod-] and Mod-u / Alt-u
   stay as text-editing keys.)
7. **File form** (`parseKey`/`keyText`): modifiers in the order `Mod-`, `MacCtrl-`, `Alt-`,
   `Shift-`, then the name: one of Enter, Space, Tab, Escape, Backspace, Delete, Insert, Home,
   End, PageUp, PageDown, ArrowUp, ArrowDown, ArrowLeft, ArrowRight, F1–F12, or a single
   character (Latin letters lowercase). Anything else → `null`. Round-trips exactly.
8. **Labels** (`keyLabel`): Linux "Ctrl+Shift+Z", "Shift+F3", "Space", "↑"; macOS in Apple's
   order ⌃⌥⇧⌘ ("⇧⌘Z", "⌃⌥X"); a `macCtrl` key on Linux "⌃X (macOS)". Use the names WebStorm
   shows for keys (`KeymapUtil`/`KeyEvent` texts) where they differ from these, and say which.
9. **`keyOfEvent`**: a modifier alone → `null`; Linux: Ctrl → `mod`, Meta → `null`; macOS: Meta →
   `mod`, Ctrl → `macCtrl`; a non-Latin layout falls back to the physical key exactly as
   `historyKey.ts:22-33` does today (Ctrl+я → Mod-z; Dvorak ';' on KeyZ stays ';'); a shifted
   symbol carries no Shift ("?" not "Shift-/"); " " → Space.
10. **`bindingsOf`**: per action, the stored entry if present else the defaults; an unknown action
    id is ignored (Rust keeps it in the file); a malformed key text → that action keeps its
    defaults and a `"unreadable"` problem; `[]` → the action has no key; a key on two actions
    (a hand edit) → the first in `KEY_ACTIONS` order keeps it and a `"twice"` problem.
11. **Into the editor** (`setPreferences`, at creation through `MergeOptions.preferences`):
    compartments in each pane for the side keys (today `SIDE_KEYS`/`sideKeys`,
    `sideFocus.ts:42-65`), the find keys (`find.ts:269-284`; the box's `runScopeHandlers` at
    `:260` picks them up), and a `Prec.high` keymap in the middle for undo, redo, indent and
    outdent that beats `defaultKeymap` (Indent on Mod-i wins over selectParentSyntax). The
    middle's `historyKeymap` keeps only its selection undo/redo (Mod-u / Alt-u), so Mod-z does
    nothing there once Undo is bound elsewhere; `indentWithTab` is replaced by the bound keys.
    A CodeMirror key string per `Key` (`cmKey`, in `editor/internal/`): Shift+letter without
    Ctrl/Alt is the uppercase name ("X"), as CodeMirror matches it; a `macCtrl` key on Linux is
    not bound. The find bar's Close button title follows the close-find binding; its Enter /
    Shift+Enter titles stay. Window-wide undo/redo (`historyKey`) match the bound keys through
    `keyOfEvent`, with today's guards (text fields, already-handled events, Alt rules as today).
    A key removed from a side action is simply not bound: the browser's default acts there again.
12. `editor/index.ts` stays ≤ 300 lines: move `#loadLanguage` (`index.ts:96-112`) into
    `internal/language.ts`, or similar wiring, never by compressing lines.

### Settings data and store

13. **Sources.** `ipc/tauri.ts` maps the four generated commands; `ipc/domain.ts` turns
    `SettingsRead` into the domain shape (`defaultPath`). Fixture mode: `ipc/fixtureSettings.ts`, an
    in-memory store with the same rules as the file (path shown `/fixture/settings.json`;
    `Some`/`None` per action; a move to an unknown path "creates" it from `current`, a known one is
    used; relative paths refused with `NotAbsolute`).
14. **Store** (`ui/settings.ts` holds the settings actions so `store.ts` stays ≤ 300 lines; move
    `clearProblemAbout` into `problem.ts` if needed): `settings` starts `{ read: null, theme:
    startTheme, keys: bindingsOf({}) }`. `current` sent with every command =
    `{ theme, keys: <only actions whose bindings differ from DEFAULT_KEYS, as key texts> }`.
    - `loadSettings`: at mount and whenever the window gets focus, together with `refreshFiles`
      (`App.vue:32-38`). OK → settings from the reply; key problems → one settings problem. Failure
      → a settings problem, the settings in use stay.
    - `setTheme`, key edits, `moveSettings`: send, then apply the reply; failure (a broken file, a
      relative path, an unwritable folder) → a settings problem, nothing changes.
    - Key edits (pure rules in `ui/keymapEdit.ts`, mutation-tested): add a key the action already
      has → nothing; add/change to a key another action holds → ask the new question kind
      `"clash"` (the key, the action asking, the owner) through `asking`; "Move" sends both
      changes in one `setKeys` (the owner loses the key), "Cancel" sends nothing; change replaces
      in place; remove; remove all → `[]`; reset → `null`; a resulting list equal to the defaults
      is sent as `null`.
15. **Clash question** (`question.ts` + `QuestionDialog.vue`'s existing rendering): title
    "Key Already in Use", message naming the key and the owner, e.g. "Ctrl+F is already used by
    Find. Move it to Undo?", confirm "Move", cancel "Cancel" (WebStorm `KeymapPanel`
    `showConfirmationDialog`, `KeymapPanel.java:786-796` under `/tmp/ij-diff/…/keymap/impl/ui/`,
    without "Leave", #663).
16. **Problems.** `Problem` gains `{ action: "settings"; … }`; `problemText` words for
    `SettingsBroken` ("The settings file … has an error at line 3, column 7: … Fix it or choose
    another file."), `NotAbsolute`, `NoConfigFolder`, `ReadFailed`/`WriteFailed` on the settings
    file, and the two key problems.
17. The window's question guard: while the clash question is open, no key reaches a file (the
    existing `question === null` check covers it — confirm).

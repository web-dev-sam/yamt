## Facts measured by the orchestrator (2026-10-24, glab 1.124.0 from its release archive, not installed) — given

- `glab mr note draft create [<id> | <branch>] --file <path> [--line <n | a:b> | --old-line <n>] -m <text>`: "Add a
  comment to your pending review … visible only to you until you publish"; `--file` "targets the latest merge request
  diff version"; `--line` the new version, `--old-line` "the old/removed side", not both; prints the pending comment's
  id on success; EXPERIMENTAL. `glab mr note draft publish` and the merge request page publish them.
- `glab mr list --source-branch <name> -F json` (open merge requests by default), `glab mr view [<id> | <branch>] -F
  json`; `-R/--repo` picks another project; otherwise the project comes from the folder's `git remote`.
- `glab auth status` exits 1 when no token is found or the API refuses it (it prints which instance), 0 when logged in.
- GitLab's REST API (the stable route, through `glab api`): a merge request's `diff_refs { base_sha, start_sha,
  head_sha }` names the diff GitLab shows (base = the merge base, head = the source branch's commit); draft notes are
  `POST /projects/:id/merge_requests/:iid/draft_notes` with a `position` naming those three commits and `old_path`,
  `new_path`, `old_line`/`new_line` — check both on docs.gitlab.com (merge requests API, draft notes API, discussions
  API "create a new thread in the merge request diff", including what an unchanged line needs: both `old_line` and
  `new_line`).

## What each option must answer

1. **Where a thread is anchored**: file (old and new path), side and line — a removed line on the old side, an added
   one on the new side, an unchanged line (both lines, as GitLab's position needs) — as one sum type (vision 4), and how
   a click on a line number in either column produces it from A's columns' line spaces.
2. **Thread boxes inside the columns** (rules 1, 3): a block below the line in the column that was clicked, an equal
   empty gap in the other so both stay aligned; their text boxes take typing, selection, Ctrl/Cmd+Enter and Escape
   without the read-only editor stealing keys; heights that change while typing (and, in C, while an answer streams)
   keep both columns aligned and the strip's bands correct (A's frame and strip geometry); collapsed threads; the line
   number's mark with a count; the hover comment button on line numbers (GitLab's). CodeMirror block widgets
   (`Decoration.widget({ block: true })` from a state field, `skill://cm6-rules`; `estimatedHeight`, `requestMeasure`)
   vs. Vue components positioned over reserved gaps vs. another split — with how each keeps one source of truth for
   which threads exist (vision 2: the thread store; the editor only shows them; the project map's rule that Vue never
   holds an `EditorView`).
3. **The thread store**: who owns threads (Rust, beside A's per-pair folder and lock, written temp file + rename as
   `yamt-compare` writes `tabs.json`, vs. elsewhere), the file format and its version, what a broken or newer file
   does (never overwritten silently), when it is written (each change), the thread and message ids (brands), each
   message's text, author, time, its posting state (`not queued` → `queued` with its edited text → `pending on GitLab`
   with the draft's id and link, or `refused` with GitLab's reason), and (C) the session id. Counts per file for the
   list.
4. **"Post" and the queue** (rule 5): the edit box with the text, queue, unqueue; one message = one new GitLab
   discussion; posting text is GitLab Markdown as written.
5. **"Send to GitLab (n)"** (rule 6): glab's draft command per message vs. `glab api` against the draft-notes route
   with an explicit position (commits named, so a moved MR cannot misplace a comment) — choose with the experimental
   flag in mind; sequential vs. parallel sends; a refused message keeps its reason and stays queued, the others are
   sent; the link shown after sending; where glab runs (which crate: a git-adjacent subprocess layer with a deadline,
   as `yamt-gitio` runs git; PM1's crate edges), its working folder (the repository), the environment.
6. **Only when it lines up** (rule 7): glab found and logged in; an open merge request whose source branch is the right
   side's branch (the range as typed names it; a commit id or `HEAD~2` names no branch: then which MR, if any); that
   MR's `diff_refs` equal the two compared commits (`a...b`: left = base_sha, right = head_sha; `a..b`: say when it can
   line up). When it is checked (window start, focus, before Send), how long it may take (network), what the buttons
   show meanwhile, and every hover sentence ("glab is not installed", "glab is not logged in to <host>", "no open merge
   request from <branch>", "the merge request is at <id>, this window shows <id>").
7. **IPC** (`skill://ipc-contract`): every new command and type in Rust and in the generated TS shape, brands, error
   kinds; fixture mode's source (threads in memory, a scripted GitLab: lined up, not lined up, a refusal) so WebKit
   drives every acceptance line.
8. **Tests**: `editor/` is not mutated (VF7) — for each new node unit test name the plausible bug it catches and the
   one-line hand mutation that makes it fail. Rust and `ui/` are mutated; name the behaviour tests (the store's format
   and refusals, the lines-up rule as a pure function over recorded glab JSON, sending with one refusal). A fake glab
   on `PATH` for real-app steps (glab is not installed here; say what only a real GitLab can prove and how the owner
   checks it once). WebKit steps (`just webdriver`) and real-app steps (`just app-session`) for every acceptance line.
9. **Size and order**: builds with disjoint `Owned` globs, files and changed-line estimate each, which run side by side
   and which wait for which commit; the contract each build fixes for the next.
10. **Plan §2 rows**: one per new decision (thread anchor and boxes, the store, posting through glab, the lines-up
    rule), citing visions, in the style of #93–#97.

## Design (option 1 — two facts, two owners)

**Which side has the keyboard = the browser's focus.** CodeMirror sets `cm-focused` on the pane
holding it (`@codemirror/view` `hasFocus`); every outline is drawn only under `.cm-editor.cm-focused`,
so an outline can never show where keys do not go, and outlines vanish while another app has focus.

**What each side points at = a `SideMark` in a StateField of that side's own state** (module-level,
like `coveredField`, `internal/covered.ts:9-15`):

```ts
type SideMark =
  | { readonly kind: "alone"; readonly remembered: Chunk["id"] | null }
  | { readonly kind: "change"; readonly id: Chunk["id"] };
const setMark = StateEffect.define<SideMark>();
const sideMarks: Readonly<Record<Side, StateField<SideMark>>>; // create: alone, remembered null
```

`update`: the last `setMark` wins; otherwise a `showStatuses` value (`internal/sideStatus.ts`,
pushed by `index.ts:205-216`) gives `settled(mark, states, side)`: a mark whose change (or remembered
id) stopped waiting on that side moves by rule 5's first two clauses; a mark whose change still waits
stays (so undo reopening a change never moves the focus). No history. Chunk ids and side ranges never
change (side docs are immutable), so middle edits cannot invalidate a mark.

### Adjustments to the design (owner answers after it; binding)

- **A1 — after a mouse decision the keyboard stays where it was (#589).** `#act` = `#decide` +
  "focus the middle only when **neither side** has DOM focus" (today: whenever the middle lacks it).
  Icons and drag (`index.ts:79-81`) and Ctrl/Cmd+click (`:166-168`) keep calling `#act`; strip presses
  already keep focus (`strips.ts:185`), and the mod-click handler prevents the mousedown default. So
  with the keyboard on a side, an icon click leaves it there and the outline moves on (via `settled`);
  with the keyboard in the middle or nowhere, the middle gets it, as before.
- **A2 — handover after any user decision.** After `#decide` or `#act`, if a side holds DOM focus and
  has no waiting change left, the other side gets DOM focus with its mark `alone` (keeping its
  `remembered`) — no change focused there (owner's rule 5). Not after undo, redo or "apply all
  non-conflicting". Never to `hidden`.
- **A3 — Ctrl/Cmd+wheel step.** A `wheel` listener `{ passive: false }` on each side's `scrollDOM`;
  without the modifier (`isModClick`'s platform test) it returns at once and plain scrolling is
  untouched. With it: `preventDefault`, focus that side, then step (from a change: `stepFrom`; from
  alone: `fromScreen`). Steps: `deltaMode` LINE or PAGE → one step per event; PIXEL → the **first
  event of a burst steps at once**, then one more step per `WHEEL_STEP_PX` (start at 100) of
  same-direction |deltaY| in that burst; a burst ends after `WHEEL_IDLE_MS` (start at 250) without
  wheel events (use `event.timeStamp`, no timers) or on a direction flip; at most one step per event;
  events with |deltaX| > |deltaY| never step. So one mouse notch always moves one change, whatever its
  pixel size, and a touchpad flick moves a few.
- **A4 — read-only files.** With `readOnly`, clicks, arrows, Left/Right and Ctrl/Cmd+wheel move the
  outline; decide keys are consumed (`preventDefault`) and do nothing.
- **A5 — reveal.** Only the focused side's `scrollTop` is written (when `revealTop` is non-null);
  `ScrollSync` makes it the source and the others follow (`scrollSync.ts:73-84`, echo ignored
  `:77, 105-114`). No geometry per scroll frame (#51): a key press reads cached rows (`#layout()`),
  `scrollTop`, `clientHeight`, `documentPadding.top`, `defaultLineHeight`. Clicks never scroll.

### Rule 1 click

`SideFocus.#pressed`: capture-phase `mousedown` on the side `scrollDOM`; skip a mod-click in an
editable view (modClick applies it, and focus must stay where it was, A1); otherwise `changeAt` →
`setMark` (a change, or `alone` keeping `remembered` when the click hits no waiting change). The
browser's own focus handling gives the side DOM focus. Text selection with the mouse keeps working.

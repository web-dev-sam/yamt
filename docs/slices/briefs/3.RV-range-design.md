# 3.RV — design: `yamt --diff=<range>`, a read-only review of a git commit range (board "Review a commit range" row 1)

Agent: `designer` (read-only). Output: two or three file-level options plus a recommendation (your output schema). You
design; the orchestrator chooses; then builds run as a dependency graph — at most two implementers at once, Rust
(`rust-impl`) and window (`web-impl`) builds side by side where the files are disjoint. Name every file each build
creates, changes or deletes, and the fixed contract between builds (the IPC types and commands written out in full, the
`editor/` public surface written out in full). One build ≤ ~25 files, ≤ ~1,500 changed lines; split otherwise. Tree:
branch `feat/review-range` off main `bc69714`.

## The feature — settled, do not reopen

`docs/slices/request-review-range.md`: the owner's words, **delivery A, rules 1–6** (this design), the orchestrator
defaults, the sourced facts, the non-goals and the risks. Read it in full first; its facts carry a source and are given
(`skill://slice-protocol`); re-check only what it marks `[INFERENCE]`. Deliveries B (threads inside the columns, stored
per repository and commit pair, posted through glab) and C (an AI per thread in a temporary checkout of the right
side's commit) follow and are designed separately — **design A so they slot in without rework**: name, per option,
where B's thread boxes would go in the columns (a block between lines in one column and an equal gap in the other),
where B's per-pair storage would live, and where C's `--ai` flag would reach the window. Do not design B or C.

Orchestrator defaults for A (boring; take them unless an option shows a real cost): an empty side means `HEAD`, as git
reads `a..` and `..b`; a single name without dots (`--diff=main`) is a usage error (the working tree is a non-goal);
`a...b` with several merge bases takes the first, as `git diff a...b` does; the window's title names the range as
typed; the left header names the left side as typed (for `a...b`: "merge base of a and b") and its short id, the right
header `b` and its short id; closing the window exits 0 with no question; nothing is written anywhere for A.

## What each option must answer

1. **Arguments** (`src-tauri/src/args.rs`, a hand parser: `USAGE` 4–15, `DIFF_WITH_REPO` `:17`, `parse` `:27`,
   `--diff` boolean `:35`): `--diff` alone stays `Invocation::Compare` (plan §2 #93–#101 unchanged); `--diff=<range>`
   a new invocation carrying the range text and an optional `--repo`; malformed (`--diff=`, `--diff=a`, `--diff=a....b`)
   is exit 2 with one line. Which errors are found by the parser and which only after git answers (unknown name, not a
   repository: also a message, exit 2, no window — say where that message is printed and how the shell exits before
   any window, cf. `outcome::startup`'s refusals). The help text.
2. **Git reads and their crate** (vision 3: PM1 — `src-tauri` never depends on `gitio`/`merge-core` directly; `compare`
   depends on merge-core only): resolving both sides to commit ids once (`rev-parse --verify <name>^{commit}`,
   `merge-base` for three dots), listing changed files with git's rename detection (mark A/M/D/R, old and new path,
   `+n −m`, binary, mode-only, a submodule) in as few git runs as is boring (`diff --raw --numstat -z -M` or two runs;
   `--no-ext-diff --no-textconv`, the user's `diff.*` config that must not leak in), and reading both sides' texts of
   one file (`cat-file --batch`, already in `yamt-gitio`). Which crate owns the range (a new crate over gitio and
   merge-core, `yamt-compare` gaining gitio, or `yamt-session` gaining a second job) — a new crate is a plan §2 row and
   an architecture §7 entry; PM1's detector (`scripts/arch-check.sh`) changes with it. Large ranges: the list from one
   reply, texts per file on demand; what a 10,000-file range costs.
3. **The mode in the shell and the page**: how the page learns it is the range window before the first frame
   (`WindowKind` merge|compare in the start script's `data-window`; a third kind vs. the compare kind with a range),
   what never starts (`MergeSession`, language servers, the compare `TabStore` and its lock), the title, the close
   (exit 0). Fixture mode's equivalent (a query such as `?range=<case>`, fixtures under `tests/…` generated by `just
   fixtures` through `yamt-cli` as `tests/compare/` are) so WebKit can drive every acceptance line.
4. **The window's root**: a third root (`RangeApp.vue` + its store, fenced like PM7 and its `frontend/scripts/fences.ts`
   detector) vs. a range shape inside the compare root (`CompareApp.vue`, `ui/compareStore.ts`). Who owns the file list,
   the shown file and the loaded files (`skill://project-map` state table: Vue never holds an `EditorView`, a position
   or document text); one mounted view per visited file as `CompareApp` keeps visited tabs (plan §2 #51) or one view
   reloaded per file — memory with hundreds of visited files. The settings gear and settings view (`ui/settingsStore.ts`
   seam), find, the toolbar's change arrows.
5. **The changed-files list** (rule 3): reuse of the merge window's `FileList.vue` / `FileTree.vue` / `fileTree.ts` /
   `fileListMode.ts` / `usePanelWidth.ts` + `PanelWidthHandle` and `fileListKey.ts` (Ctrl/Cmd+B) — which of them
   import the merge store or merge-only types today, and how the range root gets the same list/tree switch, width and
   key without a second copy (vision 2) and without the merge root's marks (resolved, remembered, the operation tag).
   The row: a mark per status (as GitLab: added, modified, deleted, renamed), `+n −m`, the renamed file's old path, the
   file icon as the merge list shows it. The first file shown at start; a range with no changes (one sentence).
6. **The two read-only columns** (rule 4) over the compare window's editor: `CompareController` (`editor/compare.ts`,
   internals `editor/internal/compare*.ts`, plan §2 #96) today takes editable `TabTexts` with `settled`/`detected`/
   `refused` events, `columnLimit` and Format. A read-only shape — a second constructor or class sharing the internals,
   vs. an option on the one class (no flag bag: vision 4) — with its exact public surface, how differences arrive (one
   reply per file from Rust's `merge_core::compare`, never recomputed, since nothing is edited), language from the
   file name (the merge window's rule in `editor/internal/language.ts`), locked scroll, find, previous/next change,
   word marks, removal bars, bands. Where B's thread blocks and their aligned gaps would attach (a block widget per
   column from one state field, CodeMirror's `Decoration.widget({ block: true })` — `skill://cm6-rules`; the compare
   frame's row geometry `compareFrame.ts` and strip bands that must count those heights).
7. **Special files** (rule 5): added → empty left column; deleted → empty right column; renamed → header "old → new";
   binary, over 8 MiB (`MAX_COLUMN_BYTES`), only the mode changed, a submodule → one sentence instead of the columns;
   a text not valid UTF-8 (the merge window's rule, cite it). Where each is decided (Rust once, as a sum type crossing
   the IPC: vision 4) and its words (one words file).
8. **One window per repository and commit pair** (rule 6): a lock keyed by the repository and both commit ids
   (`File::try_lock`, as `yamt-compare`'s `files.rs`), its folder under the app's data folder (B will store threads
   beside it), the refusal message naming the open window, exit status; several range windows on different pairs and
   a `yamt --diff` window at once.
9. **IPC** (`skill://ipc-contract`): every new command and type in Rust and in the generated TS shape, domain brands
   (a commit id, a range file index or path), error kinds (`IpcError` additions), the fixture source's interface beside
   `CompareSource.ts`.
10. **Tests**: `editor/` is not mutated (VF7) — for each new node unit test name the plausible bug it catches and the
    one-line hand mutation that makes it fail. Rust and `ui/` are mutated (`just mutants`); name the behaviour tests
    (git reads against real temp repositories built in the test, renames, binary, mode-only, `...` with a merge base).
    WebKit steps (MiniBrowser through `just webdriver <port>`) and real-app steps (`just app-session`) for every
    acceptance line, against a smoke repository script (`scripts/…-repo.sh` beside `scripts/demo-repo.sh`, sourcing
    `scripts/git-sandbox.sh`).
11. **Size and order**: builds with disjoint `Owned` globs, files and changed-line estimate each, which run side by
    side and which wait for which commit; the contract each build fixes for the next.
12. **Plan §2 rows**: #93's and #94's amendments (DR4: the reopened text gets the new information, the old decision
    stays for `--diff` alone), #101 extended to `--diff[=<range>]`, and one row per new decision (mode, crate, listing,
    read-only columns, the pair lock), each citing visions, in the style of #93–#97.

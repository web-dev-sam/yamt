## Findings (verbatim) and decisions

### #236 block (correctness) and #238 block (boundary) — bars not visible at a glance

> #236: The brief asks for bars 'visible at a glance … with a little breathing room', but the bar
> sits on the character boundary with no gap at all (`left:-1px; width:2px`) and in the word-mark
> colour. Where it touches a word mark of the same colour it disappears: language-tools-conflict.png
> left line 363 col 0 is invisible next to the mark that starts at col 0 (contrast 1:1). On a band
> it is barely there: blue bar over blue band composites to about rgb(59,89,117) on rgb(43,58,72),
> about 1.6:1, and C27 line 83 'foo();' does not show at 1x (the 4x crop zoom-C27-left.png is still
> faint). Purple is about 1.56:1 on its band.
>
> #238: At 1x the bars are not visible at a glance. … The cause is that the bar uses the 65%-alpha
> word token, the same hue and brightness as the mark and only slightly brighter than the band.
> Fix: … adds two opaque bar tokens to style.css, one per tone, clearly lighter than the word
> tokens …

### #239 should (boundary) — no breathing room

> `left: -1px` with `width: 2px` centres the bar on the character boundary, so it overlaps each
> neighbouring glyph cell by 1px with no gap. In zoom-X2.png it touches the 'w' of 'watch', and
> nothing separates it from an adjacent mark of the same colour.
>
> Fix: Separate the bar from its neighbours with a 1px gap in `--color-editor` on each side, e.g.
> `box-shadow: -1px 0 0 var(--color-editor), 1px 0 0 var(--color-editor)` on the ::after. Confirm
> in the re-shoot that glyph edges stay intact.

**Decision (all three):**

- **Colour:** the bar no longer uses the word colour. Add two opaque tokens to `@theme` in
  `style.css` and point `.chunk-removal-{modified,conflict}::after` at them:
  - `--color-chunk-modified-removal: #6b9bfa` (JetBrains New UI palette "Blue9");
  - `--color-chunk-conflict-removal: #b589ec` ("Purple9").

  These are the lighter steps of the same hues, so a bar reads as "this block's colour, but
  brighter".

- **Breathing room:** keep the bar 2 px wide and add a 1 px gap in `--color-editor` on each side
  (`box-shadow`, as the finding proposes). It still takes no text width.
- **Plan §2 #31** already says "thin bright bars"; the original brief's sentence "in the block's
  word colour" is replaced by this decision.
- **Fallback:** if, at 1x, the bar still doesn't stand out on a modified band or next to a
  same-colour mark, report it with screenshots instead of inventing another look.

### #237 should (correctness) — the test label does not prove the DOM class

> `painted` builds the label `chunk-removal-${tone}` from `widget.tone` itself, so it looks like the
> DOM class but is not. If `RemovalPoint.toDOM` wrote a wrong class (a typo, or the `chunk-word-`
> prefix), no CSS rule would match and no bar would be drawn, yet every node test would still pass.

**Decision:** one source for the class.

- `RemovalPoint` exposes the class string it writes (e.g. a `className` getter that `toDOM` uses),
  and the test label reads that same value.
- `theme.css` selectors must match it; the smoke screenshot proves the CSS side.

### #241 nit (boundary) — `ignoreEvent` vs `pointer-events: none` — rides along

> Clicks are handled twice over. `ignoreEvent(): false` hands widget events to CodeMirror, while
> `pointer-events: none` (theme.css:55) means the widget never receives events.

**Decision:** keep `ignoreEvent(): false`, drop `pointer-events: none`, and repeat the
click-right-after-a-bar check in the smoke.

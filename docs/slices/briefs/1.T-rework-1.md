## Findings and decisions

1. [should, boundary, TS14] `indent.ts:19` — "The rule that 1-space steps (block-comment ` *`
   lines) don't count is written as two bare `> 1` checks, `width > 1` here and `step > 1` at line 23. A reader cannot tell from the code why 1 is excluded, or that both checks express the same
   rule." **Decision:** one named constant (e.g. `SMALLEST_INDENT_STEP = 2`) used by both checks.
2. [should, correctness] `indent.test.ts:64` — "Nothing pins the `width > 1` boundary in the
   tab-vs-space count. If it changed to `width > 0` or were dropped, every test would still pass,
   but a tab-indented file with top-level JSDoc blocks (whose `*` lines outnumber its tab-led
   lines) would switch to space indentation." **Decision:** add that case: tab-indented text with
   a top-level `/** … */` block that has more `*` lines than tab-led lines → `"\t"`.
3. [should, correctness] `indent.test.ts:56` — "Skipping blank and whitespace-only lines
   (indent.ts:10) is not pinned … a 2-space file with blank-separated statements at depth 4 would
   be guessed as 4 spaces, and every test would still pass." **Decision:** add the reviewer's
   2-space text with blank lines (one of them whitespace-only) between depth-4 statements → `"  "`.
4. [nit, boundary] `indent.ts:1` — "`DEFAULT_UNIT = "  "` is only read as `DEFAULT_UNIT.length`"
   **Decision:** declare the width (`DEFAULT_WIDTH = 2`).
5. [nit, boundary] `indent.ts:13` — "`LEADING_SPACE.exec(line)?.[0] ?? ""` keeps a fallback for a
   case that cannot happen … `LEADING_SPACE` also covers tabs." **Decision:** drop the regex
   (`startsWith("\t")`; width = `line.length - line.trimStart().length`).
6. [nit, correctness] `indent.ts:9` — "`\r?` in the split has no observable effect … The CRLF
   input in indent.test.ts:69 therefore proves nothing." **Decision:** split on `"\n"`, drop the
   `\r\n` from that test's input.

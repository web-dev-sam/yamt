# Slice 0.3' — 10 real golden conflicts from public projects + `scripts/golden-repo.sh`

The engine's acceptance test (plan §5 M0): "chunk boundaries match what PhpStorm shows on the
same conflict". The owner will open each case in PhpStorm and compare it with
`yamt-cli classify`. Owner decision (plan §2 #26): the cases come from **public open-source
projects** in the owner's languages — TypeScript, TSX and Vue — never from private code.

## Target

Owned: `tests/golden/**` except `tests/golden/*/expected.json` (generated later by the
orchestrator with `just golden-update`; a hook blocks writing it), `scripts/golden-repo.sh`.

Read-only: everything else, in particular `docs/**`, `.omp/**`, `crates/**`.

Work only in `/tmp` for clones and probes; git commands that change a repository must be
`git -C /tmp/…` (the bash guard blocks `git merge/commit/add` elsewhere).

Non-goals: Rust code, expected.json, choosing the grouping constant, judging the engine's output.

## What a case is (fixed)

```
tests/golden/<case>/
  base.<ext>     stage 1 (merge base) — exact bytes from git
  local.<ext>    stage 2 ("ours", the branch merged into)
  remote.<ext>   stage 3 ("theirs", the branch being merged)
  README.md
```

`<ext>` is the original file's extension (`ts`, `tsx`, `vue`); all three files of a case share
it. `<case>` is `<project>-<topic>` in kebab case, e.g. `vue-core-apiwatch-flush`. Bytes are
exactly the blobs git reports for the conflict — no reformatting, no trimming, no newline fixes.

`README.md` per case (fixed headings):

```markdown
# <case>

- Project: <owner/repo> (<license>, <link to LICENSE at that commit>)
- Merge commit: <sha> (<link>) — parents: ours <sha>, theirs <sha>; merge base <sha>
- File: <original path>
- Lines (base/local/remote): <n>/<n>/<n>
- Why this case: <one sentence: the shape it exercises>

## Compare in PhpStorm

    scripts/golden-repo.sh <case> /tmp/yamt-golden/<case>
    # then open /tmp/yamt-golden/<case> in PhpStorm → Git → Resolve Conflicts → Merge…

or, with the PhpStorm command-line launcher:

    phpstorm merge tests/golden/<case>/local.<ext> tests/golden/<case>/remote.<ext> tests/golden/<case>/base.<ext> /tmp/yamt-<case>-result.<ext>

## Compare with yamt

    cargo run -q -p yamt-cli -- classify tests/golden/<case>/base.<ext> tests/golden/<case>/local.<ext> tests/golden/<case>/remote.<ext>
```

Plus one `tests/golden/README.md`: what the directory is, the selection method you used (so
it can be repeated), and a table of the 10 cases (case, project, license, file, why).

## Change

1. **Find real conflicts.** Clone candidate projects into `/tmp` (a blobless clone,
   `--filter=blob:none`, keeps it small). Projects must be MIT, Apache-2.0 or BSD licensed; good
   sources are repos that merge long-lived branches back and forth, e.g. `vuejs/core`
   ("Merge branch 'main' into minor"), `vitejs/vite`, `vuejs/router`, `vueuse/vueuse`,
   `nuxt/nuxt`, `vuejs/language-tools`, `vuejs/pinia`, `TanStack/query` — any public project
   that fits is fine. For merge commits (`git rev-list --merges`), re-run the merge with
   `git merge-tree --write-tree` on the two parents; keep merges where a `.ts`, `.tsx` or `.vue`
   file conflicts; read the three stages' blobs.
2. **Select 10**, diverse, from at least 3 projects, with at least one `.vue` and one `.tsx`:
   - each file 40–1500 lines per side, at least 2 changed regions, at least one real conflict;
   - across the set include: a region both sides changed identically (common when a fix was
     cherry-picked to both branches), changes on the two sides only 1–3 unchanged lines apart
     (this is where the grouping distance matters), a large conflict next to small one-sided
     changes, a pure insertion at the same place on both sides, and if you find one, an add/add
     file (no base — then `base.<ext>` is an empty file) or a file without a final newline;
   - prefer cases a human can compare in a few minutes (not 40 regions).
3. **Write the cases** exactly as above (bytes untouched, README filled from git facts).
4. **`scripts/golden-repo.sh <case> <dir>`**: POSIX `sh` or `bash`, `set -eu`; refuses an existing
   non-empty `<dir>`; builds a repo in `<dir>` whose single file (at the case's original path)
   has base on `main`, local on branch `local`, remote on branch `remote`, then checks out
   `local` and merges `remote` so the conflict is left in the index and worktree. It isolates the
   user's git config (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, explicit
   `user.name`/`user.email`, `init.defaultBranch=main`, `commit.gpgsign=false`,
   `core.autocrlf=false`) and works on Linux and macOS. For an add/add case (empty base),
   `main` does not contain the file.

## Acceptance

- `ls tests/golden` shows 10 case directories + `README.md`; each case has exactly the four files.
- For every case, a re-extraction check you script in `/tmp`: the three files are
  byte-identical (`cmp`) to the blobs git produces for that merge (paste the 10 `ok` lines).
- `scripts/golden-repo.sh` run on 2 cases (one `.vue`) into `/tmp`: paste
  `git -C /tmp/… ls-files -u` (3 stages, or 2 for add/add) and the first conflict-marker lines of
  the worktree file. Running it again on the same dir fails with a clear message.
- A table in the report: case, project, license, file, lines b/l/r, shape it exercises.
- Delete your `/tmp` clones afterwards.

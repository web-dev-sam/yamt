## Findings to fix

### #918 (boundary, should; `frontend/src/editor/internal/serverDoc.ts:28`)

**Problem:** `#counts` keeps a second copy of counts that already come from lint's state (set at :36, compared and rewritten at :66-70), while `MergeController.#statusesChanged` (index.ts:150-161) reports the summary by comparing `startState` with `state`. The "tell the listener when a derived count changes" rule now has two forms. As the app grows, every count the status area adds must also be kept in step with this cache.

**Fix:** Drop `#counts` and compare `problemCounts(update.startState)` with `problemCounts(update.state)` in `updated`, the same way `#statusesChanged` does (principles §2 "derive, don't sync").

### #919 (boundary, should; `frontend/src/editor/internal/problems.ts:109`)

**Problem:** The rule for stale problem answers is now split across the boundary. lsp's `DocProblems.push` (lsp/internal/problems.ts:69-74) drops a version newer than the one sent. The editor drops an answer older than that server's last one (implementer decision 5) and builds its forgetting floor on that order (:39-45). Plan #70 says the lsp owns "one slot" per server for pushed and pulled problems. As the app grows, any change to staleness (for example, pulls keyed by resultId) has to land in two modules that cannot import each other.

**Fix:** Report the lsp addition the brief asked for: `DocProblems` drops an answer older than the last one it showed. Then remove the `version < last` check here and keep `answered` only for the forgetting floor, which can rely on that guarantee.

**This round (editor half):** the client now guarantees it never hands the editor an answer older than the last one it showed for that server (client fix round 2, committed before you start). Remove the editor's own `version < last` check and keep `answered` only for the forgetting floor.

### #920 (boundary, should; `frontend/src/editor/internal/problems.test.ts:12`)

**Problem:** The `DocVersion` brand rule (`Number.isSafeInteger(n) && n > 0`, lsp/internal/version.ts:3-5) is copied three times: here, in serverDoc.test.ts:71-79 and in problems.browser.test.ts:65-73. So the brand is created outside its owner (deviation 6). As the app grows, if lsp's version rule changes (for example, LSP-style versions from 0), these tests keep building versions the client never sends, and nothing fails.

**Fix:** Ask for `nextVersion` (or `isDocVersion`) to be exported from `lsp/index.ts` as a reported lsp addition, and import it in the three tests instead of the local guards.

**This round (editor half):** `lsp/index.ts` now exports `isDocVersion` (client fix round 2). Import it in the three tests instead of the local guards.

### #922 (correctness, block; `frontend/src/editor/internal/format.ts:26`)

**Problem:** A pure line diff turns a reindent into one edit that replaces every changed line, so an edit that reaches past an open block's edge breaks the block. If it covers the block and the line after it (for example a formatter reindenting a function around the block), both `from` and `to` are strictly inside the replaced range. `mapPos(-1)` maps both to the edit's start, the span collapses, and `chunkField` marks the block `ignored ignored` with no arrows, although every line of the block is still there. If the edit covers only line 199 and the block's first line, `from` moves to line 199, so the block grows, and applying a side then deletes line 199 from the Result. The node check `mapPos` of a span [12,21) through a reindent of lines 3–9 gave [6,6]. The acceptance test changes only lines 3 and 400, far from the block, so it cannot catch this.

**Fix:** Inside each `LineEdit`, pair old and new lines one to one. Replace each pair on its own, trimmed to the characters that differ, and insert or delete only the extra lines, so no single change straddles a line edge. Add a test that reindents lines 198–204 around the block and expects `pending pending`, the block's own text and the `replace` arrows. Optional: the same change keeps problems on reformatted lines (open risk 1).

### #923 (correctness, block; `frontend/src/editor/internal/format.ts:54`)

**Problem:** `state.toText(reply.result)` splits only on the pane's separator, so in a CRLF Result an LF answer from the formatter stays one 'line' full of `\n` characters. Node: `toText("a;\nb;\n")` with separator `\r\n` gives `["a;\nb;\n"]`, `lines: 1`. LF is the default line ending of prettier-style formatters [INFERENCE for oxfmt]. The result is a doc whose lines contain line breaks, one line number, every open block collapsed to ignored, and `resultText()` returning LF, so the CRLF file is rewritten to LF. The CRLF tests only feed results that are already CRLF.

**Fix:** Split the result on any line break (`Text.of(reply.result.split(/\r\n?|\n/))`, CodeMirror's default split) so the Result keeps its own separator. Add a CrLf test with an LF result: Result still CRLF, `doc.lines` equals the number of result lines, and a result that differs only in line endings is `unchanged`.

### #924 (correctness, block; `frontend/src/editor/internal/problems.ts:126`)

**Problem:** Every server answer dispatches `setDiagnostics`, even when the merged list is exactly what is already shown. Examples: a second server repeating its problems, or a pull answered `unchanged`, which the client re-shows. `@codemirror/lint`'s `hideTooltip` (lint dist/index.js:124) returns true for any `setDiagnosticsEffect`, and `hoverTooltip` applies `hideOn` to every transaction (view dist/index.js:10969). So a problem tooltip the user is reading closes when an answer arrives that changes nothing, and it stays closed until the pointer moves. This confirms open risk 2 for each server's answer after each edit.

**Fix:** When the merged diagnostics equal the shown ones (from, to, severity, message, source, compared through `forEachDiagnostic`), return only the `answered` effect without `setDiagnostics`. Add a test that a repeated identical answer carries no `setDiagnosticsEffect`.

### #925 (correctness, should; `frontend/src/ui/useMergeController.ts:112`)

**Problem:** Survivor: `onSummaryChange((next) => { summary.value = next; })` emptied. It is not equivalent: the toolbar summary would freeze at build time. No `just check` recipe kills it, and it is not wiring observed in a smoke. The fake's `onSummaryChange(): void {}` makes the path untestable. The `problems` twin added in this patch is tested. As the file grows, a later refactor of `reloaded` can drop the summary listener without any test noticing.

**Fix:** Have the fake keep the summary listener the way it keeps `countsListener`, and add a test that a reported summary reaches `handle.summary.value` after a rebuild.

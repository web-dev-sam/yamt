## Facts measured by the orchestrator (2026-10-24, omp 18.12.6, `omp acp` driven by a throwaway client) — given

- **Handshake**: `initialize { protocolVersion: 1, clientCapabilities: { fs: { readTextFile: false, writeTextFile:
  false }, terminal: false } }` → `protocolVersion 1`, `agentCapabilities { loadSession: true, promptCapabilities {
  image, embeddedContext }, sessionCapabilities { list, fork, resume, close } }`, `authMethods [{ id: "agent", "Use
  existing local credentials" }]` (no login step needed when omp is set up). One JSON-RPC 2.0 message per line on
  stdout; requests from the agent carry an `id` and need a reply.
- **`session/new { cwd: <absolute>, mcpServers: [] }`** → `sessionId` plus `configOptions` (mode default/plan, model).
- **`session/prompt`** → a stream of `session/update` notifications, then the reply `{ stopReason: "end_turn", usage }`
  (an edit plus a command took 8.6 s). Updates seen: `agent_thought_chunk` (thinking text), `tool_call` (status
  `pending`, `kind` read|edit|execute, `title`, `rawInput`, `locations[{ path }]`), `tool_call_update` (`in_progress`
  then `completed`, `content` holding text and, for an edit, `{ type: "diff", path: <absolute>, oldText: <whole file>,
  newText: <whole file> }`), `agent_message_chunk` (answer text), `usage_update`, `session_info_update`.
- **Permission requests** (`session/request_permission`, a request from the agent with options `allow_once`,
  `allow_always`, `reject_once`, `reject_always`): with omp's default configuration it asks before **every command**
  and before **deleting or moving** a file; plain edits and new files are never asked
  (`src/session/acp-permission-gate.ts:7-12`, `src/session/session-tools.ts:921-932`). `omp acp` honours
  `--approval-mode` (`src/cli-commands.ts:313` lists `acp` among the commands that take launch flags; `src/main.ts:1929`
  applies it); an explicit `yolo` stops every question.
- **`session/cancel { sessionId }`** (a notification) ends the running prompt: its reply `stopReason: "cancelled"`
  arrived 3 ms later, mid-command.
- **`session/load { sessionId, cwd, mcpServers }`** in a new process replays the whole conversation as updates
  (`user_message_chunk`, thinking, tool calls with their results, answer text, `available_commands_update`) in 0.45 s.
  With **any other `cwd`** — existing or not — it fails ("ACP session load was cancelled"); an unknown id fails ("ACP
  session not found"). **Two processes can load the same session at once**: omp does not lock it, so yamt's one window
  per repository and commit pair (A rule 6) is the only guard.
- omp reads the checkout's own project files (`AGENTS.md`, `.omp/`) as its project, since `cwd` is the checkout.

## What each option must answer

1. **`--ai`** (C rule 1): parsed in `src-tauri/src/args.rs` with every mode, never stored; how the window learns it
   before its first frame (the start script, as `data-window`/`data-theme`, or a reply), and how "no agent process and
   no checkout ever started without it" is guaranteed by structure (vision 4), not by checks scattered in the window.
2. **The agent pipe** (plan §2 #70: Rust only pipes bytes, the window speaks the protocol): generalise `yamt-lsp-host`
   (`frame.rs`: `Content-Length`, 64 MiB cap; `run.rs` threads; `program.rs` lookup incl. Windows PATHEXT and
   CREATE_NO_WINDOW; `lib.rs` `Host`) to a second framing (one message per line), vs. a sibling crate sharing nothing,
   vs. a shared run/program core with two framings. One agent process per window; started at the first "Ask AI" with
   the checkout as working folder; stopped at close and on a page reload; a crash reported once. The command setting is
   one string (`omp acp`): how it is split into program and arguments (no shell; quoting rule or none; Windows), and
   whether yamt appends anything (`--approval-mode`) or leaves that to the user's command. The IPC commands and the
   events channel (cf. `src-tauri/src/servers.rs`, a `Channel` per run, `RunId` branded in `ipc/domain.ts`).
3. **The window's agent client** (framework-free, beside `frontend/src/lsp/`; valibot over the subset yamt reads, as
   `lsp/` does): JSON-RPC ids, `initialize` once per process, `session/new` or `session/load` per thread (a replayed
   history rendered like a live one), `session/prompt`, `session/cancel`, the updates above folded into one turn model
   (thinking text, steps with status and output, edit diffs, answer text, stopped/failed), the agent's requests (a
   fixed table of answers, as `lsp/` has for server requests). **Permission answers**: the owner's rule is "not checkout
   anywhere else, but edits allowed" — commands run (C rule 5), a delete or move with a path outside the checkout is
   refused; say what is answered for each request kind, with or without the user seeing it. Parallel turns in several
   threads over one process. A session that `session/load` cannot find (`omp gc`) or refuses: one sentence (C rule 8).
4. **The temporary checkout** (C rules 5–6): of the right side's commit, one per repository and commit pair, at a path
   that is the same for every window on that pair (the load fact above) and survives a reboot (kept changes must not
   vanish: not the system temp folder). How it is made — `git worktree add --detach` (shares refs and objects; an entry
   in the user's worktree list; the AI's `git` commands then reach the user's branches) vs. `git clone --shared` /
   `--local --no-checkout` + checkout (own refs, objects borrowed) vs. extracting a tree — with what each costs on a
   large repository and what the AI can break in the user's repository. "Has changes": anything `git status
   --porcelain` reports (untracked files included) or a moved `HEAD` (the AI committed). Removal. Leftovers after a crash
   or kill: never removed when changed; a clean one removed — when and by whom (at the next range window's start, only
   when no open window holds its pair). Which crate owns it (`yamt-gitio` methods for the git runs; the owner of the
   per-pair folder that A's lock and B's threads also use — coordinate by naming the folder, `<data_dir>/yamt/…/<pair
   key>/`, and leave its exact key to A's design: write it as an input).
5. **The close question** (C rule 6): when the window is asked to close and the checkout has changes, "Keep the AI's
   changes?" naming the changed files and the folder; "Keep Changes" preferred (Enter) leaves it, "Discard Changes"
   removes it, Escape cancels the close. How the close is intercepted (`ipc/window.ts`, the only
   `@tauri-apps/api/window` importer, already guards the merge window's close; `ui/asking.ts` answers Yes, No or
   dismissed; `QuestionDialog`), what a running AI turn does at close (stopped first), and the shell's side (exit 0
   either way; the agent process stopped before the checkout is removed).
6. **Settings** (C rule 7): "Agent command" (default `omp acp`) and "First message" (a template, its default text
   written out) in the settings file (`crates/settings`: `lib.rs` types crossing the IPC, `file.rs` kept entries) and
   in the settings view (shown only with `--ai`); the placeholders `{{ RELATIVE_FILE_PATH_WITH_LINE }}`, `{{ MESSAGE }}`,
   `{{ RANGE }}`, `{{ OLD_COMMIT }}`, `{{ NEW_COMMIT }}` filled by one pure function (unknown placeholders left as
   typed, or refused when saved — choose).
7. **Markdown with highlighted code** (C rule 3): the answer text is the agent's, so rendering it must never run
   anything it contains (the window can reach the IPC). A dependency (a plan §2 row, vision 5; a sanitiser next to it)
   vs. yamt's own renderer of a fixed subset (paragraphs, emphasis, inline code, fenced code, lists, links, headings,
   block quotes, tables?) building DOM nodes, never HTML strings; code blocks coloured by the editor's one colour table
   (`editor/internal/syntax.ts`, plan §2 #102) through CodeMirror's language data — say how without a second colour
   rule. Links: opened how (or shown as text).
8. **The edit diffs in a thread** (follow-up answer: shown as a diff): `{ path, oldText, newText }` per edit, possibly
   whole files of several MiB; shown how (a small read-only two-column view through `merge_core::compare` as the
   compare window does, or unified lines), collapsed by default, its cost per turn.
9. **IPC** (`skill://ipc-contract`): every new command, type and event in Rust and in the generated TS shape, brands
   (a run id, a session id, the checkout path), error kinds (`IpcError` additions), the fixture-mode source (a scripted
   fake agent in the browser so WebKit can drive a turn, as `fixtureServers.ts` fakes language servers) and a test agent
   binary for Rust (as `lsp-echo`).
10. **Tests**: Rust and `ui/` are mutated (`just mutants`); name the behaviour tests (framing, a crashed agent, the
    checkout made / changed / clean / kept / removed / left over after a kill, the pair's folder reused). The client's
    turn model on recorded update streams (record a real one as a fixture: say how). WebKit steps for the turn view in
    fixture mode; real-app steps with `omp acp` against the smoke repository (a turn that edits a file, Stop, reopen
    and see the conversation again, close → Keep → reopen continues, close → Discard).
11. **Size and order**: builds with disjoint `Owned` globs, files and changed-line estimate each; which need A's
    commits (its crate, the pair key) and which run before them; the contract each build fixes for the next.
12. **Plan §2 rows**: one row per new decision (agent protocol and pipe, the checkout, the close question, the
    Markdown renderer, settings), each citing visions, in the style of #70 and #93–#97.

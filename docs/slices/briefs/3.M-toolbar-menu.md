hiding "Mark resolved", the status text or the gear; a menu on the gear-only headers of read-only and
choice files (they have no hideable buttons); closing on resize or scroll; sharing the choice between
the dev build and the installed app.

- `ui/store.ts`: state `hiddenButtons` (read-only to components, the `hidden` ref above) and action

  and holds it, the way it holds `asking` and `guard` (one pattern for helper state; VU9: the action
  lives in the store).

Storage (vision 2: one key, one value shape):

- key `"yamt.toolbar.hidden"` (one `const` in `toolbarButtons.ts`), value a JSON array of the hidden
  ids in `TOOLBAR_BUTTONS` order, e.g. `["undo","redo"]`; nothing hidden → `[]`.
- Reading: ids yamt does not know are dropped, duplicates collapse; a value that is not a JSON array of
  strings (or missing) → nothing hidden. Never throws.
- Writing on every toggle. A storage that throws on read or write (WebKit can) → the choice still
  applies for this run; log one warning through `log` from `../ipc` (snake_case event name, the error's
  message as a field, `skill://ts-conventions` logging rules), no problem bar.
- Use `@vueuse/core`'s `useStorage` with a serializer that does the reading rule above (VU12, vision 5:
  the dependency is already here and handles no-window and storage errors); if it cannot express a rule
  above, say which and write the smallest plain code instead.

## Behaviour (what the user sees)

### The buttons

1. `MergeToolbar.vue` renders the six icon buttons from `TOOLBAR_BUTTONS`, skipping hidden ones (not
   rendered at all, not merely invisible). Give each `IconButton` its `id`; key the button table by id
   (e.g. `Record<ToolbarButtonId, IconButton>`) so a missing or extra button is a type error
   (vision 4) and the order has one source (`TOOLBAR_BUTTONS`, vision 2). Titles, icons, the
   `keepsKeyboard` behaviour and the disabled-while-loading rule stay as they are.
2. Showing a hidden button puts it back in its own place (toolbar order), not at the end.
3. One choice for every opened file: hiding Undo removes it from every file's toolbar at once.
4. Hiding a button changes nothing else: Up/Down on a side, Ctrl/Cmd+Z/Shift+Z/Y, Enter/Backspace keep
   working.

### The menu

5. A right-click (`contextmenu`) anywhere on `MergeToolbar`'s header — on "Mark resolved", an icon
   button, the status text, the gear, or the empty bar — opens the menu and suppresses the browser's
   own menu there. The right-click itself never presses anything: no finish, no settings, no step.
   Right-clicking the bar while the menu is open moves it to the new pointer position.
6. New component `ui/ToolbarMenu.vue` (VU15 pre-approved, reason: "the toolbar's right-click menu:
   its own placement and closing rules"). It lists the six buttons in `TOOLBAR_BUTTONS` order, each by
   the button's own title (take the label from the button table; no second copy of the words), with a
   lucide `check` icon in front while the button shows and an empty space of the same width while it is
   hidden. Accessible: `role="menu"`, items `role="menuitemcheckbox"` with `aria-checked`.
7. Look: yamt's dark palette (owner #663) — a small rounded panel with a border and a shadow, items
   with the toolbar's hover look; existing tokens (`panel-inline`, `control-border`, `hover` or
   `row-hover`, `fg`). A new token only if none fits (see Target). Say what you chose.
8. Placement: the menu's top-left corner at the pointer, moved left and/or up just enough to stay fully
   inside the window (a right-click on the gear at the far right must not cut it off). Not clipped by
   the panels or hidden views (e.g. Vue's `<Teleport to="body">` with `position: fixed`; your call,
   say which). If you extract the placement as a pure function, unit-test it.
9. Choosing an item toggles that button through the store's `toggleButton` and closes the menu.
10. It closes, and nothing else changes, when:
    - Escape is pressed — and that Escape reaches nothing else (a side's find bar stays open);
    - any other key is pressed — the menu closes and the key then does what it does today;
    - the pointer presses anywhere outside the menu — the menu closes and the press then does what it
      does today (clicking the middle pane puts the caret there; clicking a file in the list opens it);
    - the window loses focus.
11. **The keyboard stays where it was** (#54, #589): if a side pane (or any element) has DOM focus
    before the right-click, it still has it while the menu is open, after choosing an item and after
    closing. So neither the right-click's press on the bar nor a press on a menu item may move focus
    (prevent the `mousedown` default there, as the arrow buttons do). The menu items need not be
    focusable.
12. Settings view, read-only and choice files: unchanged.

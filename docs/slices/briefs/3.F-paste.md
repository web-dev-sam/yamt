# Slice 3.F-paste — on Linux the window takes every paste (`ui/linuxPaste.ts`)

Board "Paste crash" row 3 (needs row 2's generated `commands.readClipboard`). Product rules: `docs/plan.md` §2 **#99**
— read it in full. Request: `docs/slices/request-paste-crash.md` (rules 1–4, acceptance). Design:
`.omp/run/notes/PasteCrashDesign.md` option B ("Window", "Delivery", "Which selection"), §1's table of paths.

Facts (given):

- WebKitGTK 2.54.0/2.54.1 crash the whole app when anything reads the pasteboard while GTK cannot list the clipboard's
  formats (an empty clipboard, an owner that quit or hangs; X11 and Wayland). Every WebKit paste — Ctrl+V,
  Shift+Insert, Shift+KP_Insert, key themes, Ctrl+Shift+V, the right-click menu's Paste and Paste As Plain Text, the
  middle button — first dispatches the DOM `paste` event and stops if it is cancelled, before reading the pasteboard
  (`Editor.cpp:1660-1666, 1676-1681` at `webkitgtk-2.54.1`). CodeMirror's `event.clipboardData.getData` and a field's
  default paste are the reads that crash.
- The middle button pastes on **release**, after the DOM `mouseup` and only when it was not prevented
  (`EventHandler.cpp:1325-1340, 2636-2638`); its `paste` event follows that `mouseup` in the same task [INFERENCE:
  confirm in the real app].
- CodeMirror's paste handler (`node_modules/@codemirror/view/dist/index.js:5167-5180`): `readOnly` → handled, nothing
  read; otherwise `doPaste(view, clipboardData.getData("text/plain") || …)` — no `isTrusted` check, so a paste event
  dispatched by the page with an in-memory `DataTransfer` takes the same path (multi-cursor and whole-line rules,
  `input.paste` undo; the compare window's 8 MiB refusal is a `transactionFilter`, `editor/internal/columnBytes.ts:63`).
  `new DataTransfer()` and `new ClipboardEvent("paste", { clipboardData })` exist at the tag (`DataTransfer.idl:33`,
  `ClipboardEvent.idl:31-38`). A field with no paste handler takes `document.execCommand("insertText", false, text)`
  with its native undo and `input` event.
- Fields with no paste handler today: the find bar, tab rename, the settings path, the server fields. The only
  clipboard use in the window is `navigator.clipboard.writeText` (`ui/ServerMenu.vue:128`), a write.
- `main.ts:22-55`: `IN_APP` (the Tauri source), `startCompare`/`startMerge` — both windows start here.
  `ipc/keys.ts:95-98` `isMac(platform)` (CodeMirror's `Mod` test); `ui/settings.ts:73-75` `showsAntialiasing` tests
  `platform.startsWith("Linux")` — the one Linux test today (plan §2 #60), WebKitGTK reports `navigator.platform`
  "Linux …".
- Row 2's command (generated): `commands.readClipboard(selection: ClipboardSelection): Promise<string | null>`,
  `ClipboardSelection = "clipboard" | "primary"`; `null` = unreadable or no text. A hung owner can make it answer
  minutes later.
- Fences live in `frontend/scripts/fences.ts` (+ test); the project map names every file (`skill://project-map`).

## Contract (fixed; you may add, never change)

```ts
// ipc/keys.ts — beside isMac; showsAntialiasing uses it (one Linux rule, vision 2)
export function isLinux(platform: string): boolean;

// ipc/index.ts (from ipc/tauri.ts) — the window's one way to read the clipboard
export type ClipboardSelection = "clipboard" | "primary";
export function readClipboard(selection: ClipboardSelection): Promise<string | null>;

// ui/linuxPaste.ts — installed once per window by main.ts when IN_APP && isLinux(navigator.platform)
export function takeLinuxPastes(
  target: Window,
  read: (selection: ClipboardSelection) => Promise<string | null>,
): void;
```

Behaviour of `takeLinuxPastes` (plan §2 #99):

1. A capture-phase `paste` listener on `target` cancels every **trusted** paste (`preventDefault` +
   `stopImmediatePropagation`) and never touches its `clipboardData`. Untrusted pastes (its own) pass untouched.
2. It reads `"primary"` when the paste follows a middle-button release in the same task, else `"clipboard"`.
3. When the text arrives: `null` or `""` → nothing. Otherwise, only if the paste's target is still the focused element
   (`document.activeElement` or inside it), it dispatches `new ClipboardEvent("paste", { clipboardData, bubbles: true,
   cancelable: true })` on that target with the text as `text/plain`; if nobody cancelled it and the target is an
   editable field, `document.execCommand("insertText", false, text)`.
4. No other module reads the clipboard: a fence in `scripts/fences.ts` refuses `navigator.clipboard.read`/`readText`
   and `clipboardData` reads outside `ui/linuxPaste.ts` (its failing path tested).

## Acceptance

- `pnpm -C frontend typecheck`, `lint`, `test` (node) pass; the fence test fails on a planted `clipboardData` read in
  another file (paste the line).
- Real app on a **private** Xvfb only (`env -u WAYLAND_DISPLAY GDK_BACKEND=x11`, through `just app-session start-app`
  on its private display; never the owner's desktop, finding #1560; a `--raw` session with a private `XDG_DATA_HOME`).
  Owners: `xclip … -loops 0 -quiet & pid=$!`, ended with `kill $pid` (never `pkill`). Paste the observed lines:
  1. live owner, Ctrl+V of 3 lines into the merge window's Result and into a compare column → the text, one Ctrl+Z
     removes it;
  2. owner killed, then Ctrl+V, Shift+Insert, Ctrl+Shift+V into the Result, a side pane, a compare column, the find
     field and tab rename → the process alive (`pgrep`), every text unchanged; then a live owner's paste lands;
  3. right-click → Paste in the Result with the owner killed → alive, unchanged;
  4. middle button into the Result with a live PRIMARY owner (`xclip -selection primary`) → that text (not the
     clipboard's); with that owner killed → alive, unchanged;
  5. `seq 300` and a payload over 8 MiB into a compare column → 300 lines; the 8 MiB notice, the column unchanged.

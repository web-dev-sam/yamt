# Slice 1.4 — applying changes: arrows, undo, bulk apply, toolbar, finish

The window shows the 10 real conflicts with coloured blocks, bands and locked scrolling. This
slice makes it a merge tool: the user applies each change from the left or right into the
middle pane, ignores it, undoes and redoes, applies every non-conflicting change from one side
in one click, and marks the file resolved. PhpStorm's merge window is the model (plan §2 #9:
the result starts from the base and every change needs an explicit action).

## Target

Owned: `frontend/src/editor/**`, `frontend/src/ui/**`.
Read-only: everything else, notably `frontend/src/ipc/**` (use the existing `ChunkSource`:
`finishFile`, `resetFile`), `frontend/src/connectors/**`, `frontend/src/style.css` (palette
tokens only; if you need a new colour, stop and report), `frontend/fixtures/**`, configs,
`docs/**`, `.omp/**`.
Non-goals: word-level highlights, "magic" resolution of conflicts (plan §2 #10), keyboard
shortcuts beyond CodeMirror's own undo/redo keys, a confirmation dialog, the Tauri app, the
warning banner, the `VITE_CHUNK_SOURCE` switch.

## Behaviour (what the user sees)

- Each change that still needs a decision shows, at its first line, on the edge of the side pane
  next to the gap: an arrow that applies it (`»` on the left pane, `«` on the right pane) and an
  `×` that ignores it. Arrows appear on the side(s) that changed: left for `LocalOnly`, right for
  `RemoteOnly`, both for `BothSame` and `Conflict`.
- Applying replaces the change's **current** range in the middle pane with that side's lines
  (architecture §6: even if the user edited inside it). The change is then resolved: its colours,
  its bands and its arrows disappear in all three panes. `BothSame` resolves from either arrow.
- A `Conflict` after one side is applied keeps the other side's arrow; applying it appends that
  side's lines after the first side's (architecture §6, "apply both"), then the conflict is
  resolved. `×` resolves a change or a half-applied conflict as it is.
- A change whose middle-pane lines the user deletes entirely counts as ignored (CM8).
- Undo/redo (keyboard in the middle pane, and the toolbar buttons) restore text **and** the
  change's state together (CM2): undoing an apply brings its colours, bands and arrows back.
- Toolbar "Apply non-conflicting changes from the left" applies every undecided `LocalOnly` and
  `BothSame` change at once; "…from the right" every `RemoteOnly` and `BothSame`. One click is one
  undo step (CM7, architecture §6).
- The toolbar shows what is left in the open file, e.g. "3 changes · 1 conflict" and "All changes
  processed" when none are left.
- "Mark resolved" sends the middle pane's text to `ChunkSource.finishFile` (the text keeps the
  file's line endings: CRLF files stay CRLF, CM5), and the file list shows that file as resolved.
  "Reset file" calls `resetFile` and reopens the file from its original data. Both act on the open
  file and stay on it.

## Contract (fixed; you may add, never change)

- `MergeController` (architecture §5.2) gains what the toolbar and the view need, e.g.
  `applyAllNonConflicting(side)`, `undo()`, `redo()`, `resultText()`, `summary()`, and a way to be
  told when the summary changes. Its constructor and `MergeHosts` stay as they are. Status lives
  in the center `StateField` (CM1/CM2), changed only by a `StateEffect` registered with
  `invertedEffects`. Status values are a discriminated union (TS2), e.g. `pending`,
  `applied-local`, `applied-remote`, `applied-both`, `dismissed`.
- Positions are never stored outside the field (CM9). Replacement text comes from
  `data.local` / `data.remote` sliced by the change's fixed side range, split into lines once per
  file (CM6). Every pane carries `EditorState.lineSeparator` for `eol === "CrLf"` (CM4);
  `resultText()` uses `state.sliceDoc()` (CM5).
- `ui/`: `useMergeController` stays the only place `ui/` imports `editor/` (VU11); the store never
  holds the controller, a position or document text (VU10). Where the toolbar lives so it can act
  on the open file's controller is your decision — report it (e.g. the toolbar rendered by
  `MergeView`, or events up to it). Store actions for finish/reset live in `store.ts` (VU9) and
  update the file list from what `finishFile` returns.

## Tests (`node` project, `EditorState` only for editor code)

- apply local / remote / both / dismiss: resulting text, status, and that a resolved change has no
  decorations or arrows; applying after the user edited inside the change replaces the current
  range;
- undo after apply restores text and status; redo re-applies; undo after bulk apply restores
  every change in one step;
- deleting a change's lines in the middle pane makes it ignored;
- summary counts across those transitions;
- `resultText()` of a CRLF file contains `\r\n` (build one with `createFixtureSource` and an
  in-memory record);
- store: finish updates the file list from `finishFile`'s result; reset reopens the original data;
  a failed finish or reset logs and keeps the current state (later open still wins).

`editor/` is outside the mutation run: break each tested rule by hand once, paste the failure,
restore. `ui/` is inside it.

# Slice 3.X-windows — a Windows build, and CI that builds and tests on three systems

Board "Crisp code text" row 2. yamt has shipped Linux and macOS builds only (`.github/workflows/release.yml`, plan §3
"Platform reality: three engines": Windows = WebView2, "later"). This slice makes the Rust workspace compile and its tests
pass on Windows, adds an NSIS installer to the bundle targets, adds a CI workflow on every push, and adds Windows to the
release matrix. Text crispness on Windows is a separate frontend slice; nothing here touches `frontend/src/**`.

## Target

Owned:

- `crates/gitio/**`, `crates/session/**`, `crates/conflict-repo/**`, `crates/cli/**`, `crates/settings/**` — only for
  portability (unix-only std APIs, git lookup, unix-only tests); no behaviour change on Linux/macOS;
- `src-tauri/src/**`, `src-tauri/tauri.conf.json`;
- `frontend/.env.tauri` (new, see Change 4);
- `.github/workflows/**`, `.gitattributes` (new), `deny.toml`, `scripts/third-party-licenses.sh`.

Read-only: everything else. Shared (report the exact diff in `deviations_from_brief`, the orchestrator applies it):
`justfile`, `Cargo.toml`, `Cargo.lock`, `frontend/package.json`. Generated (never edit, never run its generator):
`THIRD_PARTY_LICENSES.txt` (the orchestrator runs `just third-party-licenses` after your patch), `frontend/src/ipc/bindings.ts`.
Docs (`README.md`, `CHANGELOG.md`, `docs/**`) are the orchestrator's: put the facts it needs in your report.

Non-goals: code signing; Windows on ARM; an MSI; WebView2 offline installer; auto-update; making repositories with
`core.autocrlf=true` behave (written down as untested by the orchestrator); a Windows smoke of the window itself (no
Windows machine here; CI proves build and tests); any frontend source change.

## Contract

Fixed: every public Rust signature in the workspace; IPC types and commands; `merge-core` untouched; the gate recipes'
behaviour on Linux. No new crate dependency (DR3) unless std cannot do it — then a deviation naming why.

Decisions (orchestrator as product owner, #779; record-worthy, keep them):

1. **Console subsystem stays** on Windows (no `windows_subsystem = "windows"`): yamt is started from a terminal in a
   repository and its exit status and stderr line (`yamt: n of m files still unresolved`) are part of the tool's contract
   (plan §2 #13, outcome.rs); a GUI-subsystem binary returns to the prompt at once and loses both. Cost: a console
   window opens beside yamt when started from the Start menu.
2. **NSIS, per-user install** (`bundle.targets` gains `"nsis"`; tauri's default `installMode` `currentUser`, WebView2
   bootstrapper download as tauri's default): no admin rights, one installer file; MSI needs WiX and an admin install.
3. **Git on Windows**: `git.exe` found on `PATH` (no execute bits on Windows); unix keeps today's rule (a file named `git`
   with an execute bit, absolute `PATH` entries only).
4. **No line-ending conversion in this repository** (`.gitattributes`: `* -text`): goldens, fixtures and test inputs are
   compared byte for byte; a Windows checkout must equal a Linux one.
5. **CI** (`.github/workflows/ci.yml`, new): on every push and pull request, cancel superseded runs of the same ref;
   matrix `ubuntu-22.04`, `macos-14`, `windows-2025`: Rust tests with the hermetic git environment of the justfile's
   `hermetic_git` (`cargo nextest run --workspace`, nextest installed by a pinned action), then the app build — Windows
   `cargo tauri build --bundles nsis` with the installer uploaded as a workflow artifact, Linux/macOS `cargo tauri build
   --no-bundle`. Same toolchain/node/pnpm/tauri-cli setup as `release.yml` (tauri-cli 2.12.1). Frontend unit tests
   (`pnpm -C frontend test`) on Ubuntu only. The full `just check` gate stays local (plan §2 #27 and the verifier's job).
6. **Release** (`release.yml`): `windows-2025` joins the matrix; its licence step runs under bash (Git Bash on the
   runner) like the others; `scripts/third-party-licenses.sh`'s `rust_targets` gains `x86_64-pc-windows-msvc` so the
   licence file lists the Windows-only crates (webview2-com, windows, …); `deny.toml` covers the same targets if it lists any.

## Change

1. gitio: `std::os::unix` uses (`attributes.rs:1`, `entry.rs:2`, `repo.rs:4-5`) made portable (e.g.
   `OsStr::as_encoded_bytes` / `OsStr::from_encoded_bytes_unchecked` is not allowed — `unsafe`; prefer
   `as_encoded_bytes` + `str::from_utf8`/`to_str` paths that already exist, or `cfg`-split helpers in one place);
   `find_git_on_path` (`repo.rs:253-268`) per decision 3, one function with the platform rule isolated (a `cfg` on the
   file-name and the "is executable" check), unit-tested on the platform it runs on.
2. session: `start.rs` `DirBuilderExt::mode(0o700)` only on unix (Windows: the user's temp dir is private by its ACL
   [INFERENCE]); `disk.rs:107-108` symlink target bytes without `OsStringExt::into_vec` (portable conversion; a
   non-UTF-8 link target on Windows cannot occur [INFERENCE]); unix-only tests (`all_or_nothing.rs:4`,
   `disk_is_truth.rs:4`, `start_from_disk.rs:4`, `every_kind/mod.rs:114` and any symlink/permission test) gated with
   `#[cfg(unix)]` on the smallest unit, each gate's reason in its name or one line.
3. conflict-repo (dev-only): symlink and `OsStrExt` uses behind `cfg(unix)` so gitio/session/cli/src-tauri tests compile on
   Windows; tests needing a symlink are unix-only.
4. src-tauri: `appimage.rs` is Linux-only (`cfg(target_os = "linux")` on the module and its call, the other systems use the
   `--repo` argument as given); `tauri.conf.json`: `"nsis"` in `bundle.targets`; `beforeDevCommand`/`beforeBuildCommand`
   without the POSIX `VAR=value cmd` prefix (cmd.exe rejects it): Vite's mode file `frontend/.env.tauri` holding
   `VITE_CHUNK_SOURCE=tauri`, the commands `pnpm dev --mode tauri --port 5173 --strictPort` and `pnpm build --mode tauri`
   (check how pnpm appends arguments to `vue-tsc -b && vite build`; if it does not reach `vite build`, report the
   `package.json` diff you need). The built app must still use the real source, not fixtures.
5. Workflows per decisions 5 and 6; `.gitattributes` per decision 4; `deny.toml` and the licence script per decision 6.
6. Look for anything else that would not compile or would misbehave on Windows in the owned crates (path joins of git's
   `/`-separated paths, `/tmp` literals in tests, `\n`-only assumptions on paths you read from git) and fix or gate it;
   list each in the report.

## Acceptance

1. `rustup target add x86_64-pc-windows-msvc`, then `cargo check --workspace --all-targets --target x86_64-pc-windows-msvc`
   and `cargo clippy --workspace --all-targets --target x86_64-pc-windows-msvc -- -D warnings` exit 0 — or, if a build
   script cannot run for that target on Linux (e.g. tauri-build's Windows resources), the same with that package
   excluded, the failing step quoted, and every other package clean.
2. Linux unchanged: `just clippy` and `just test` exit 0 (paste the summary lines).
3. A test of the git lookup rule on the platform it runs on (unix: a non-executable `git` is skipped, an executable one
   found; the Windows variant compiles under acceptance 1).
4. `cargo tauri build --debug --no-bundle` exits 0 on Linux and the app shows the smoke repository's 7 files from git
   (`just app-session start-app --fresh-repo …` + `shot --display`, or a `read` of the file list) — the mode file works.
5. Both workflow files parse (`python3 -c 'import yaml,sys; yaml.safe_load(open(sys.argv[1]))'`) and pass `actionlint` if
   you can fetch it into `/tmp` (say if not).
6. Report for the orchestrator: every file changed and why; the README facts for a Windows install (installer file name
   pattern, WebView2 note, Git for Windows needed); anything that stays untested on Windows.

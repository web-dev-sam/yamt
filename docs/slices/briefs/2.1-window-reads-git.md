# Slice 2.1 — the window reads the real merge, and shows what went wrong

Board v0 wave 2. Slice 2.0 made `yamt` a desktop app whose commands (`commands` in the generated
`frontend/src/ipc/bindings.ts`) list the conflicted files, load one, mark it resolved and reset
it. The window still reads fixture files. This slice switches the window to those commands when it
runs inside the app, forwards the window's log to the app's log, and shows failures (git refusing
to stage, an unknown file, a file the editor cannot show) in the window instead of only logging
them. After it, `just dev-app --repo <repo>` resolves a real merge end to end.

## Target

Owned: `frontend/src/ipc/**` except `bindings.ts` (GENERATED); `frontend/src/main.ts`;
`frontend/src/ui/store.ts`, `store.test.ts`, `App.vue`; new `frontend/src/ui/ProblemBar.vue`,
`problemText.ts`, `problemText.test.ts`; new `frontend/src/env.d.ts`; `frontend/src/style.css`
(two colour tokens, below).
Read-only: everything else — `editor/**`, `connectors/**`, `model/**`, `ui/MergeView.vue`,
`ui/MergeToolbar.vue`, `ui/useMergeController.ts`, `ui/FileList.vue`, configs, `docs/**`,
`.omp/**`, Rust. Needed elsewhere → stop, `deviations_from_brief`.
Non-goals: keeping each file's unfinished work across file switches, confirmations before "Mark
resolved" or quitting, the "everything resolved" top bar (next slice); buttons for files the editor
cannot show (plan §2 #36, wave 3); the length-limit override on `store.ts` (stays until next slice).

## Behaviour (what the user sees)

- In the app (`just dev-app --repo <repo>`, `cargo tauri build`): the file list shows the
  repository's conflicted files, in git's order, with their resolved marks; clicking one shows its
  three panes from git's stages; "Mark resolved" writes the middle pane's text and stages it (the
  row gets its mark); "Reset file" puts the conflict back in git and reloads the three panes from
  the start. In a browser (`just dev-web`) everything stays as today (fixtures).
- The window's log lines (`log.info("file.loaded", …)`) also reach the app's log on stderr
  (target `frontend`), at the levels the logger already forwards.
- When an action fails, a bar appears at the top of the right-hand area (above the toolbar), in the
  JetBrains New UI dark error-banner colours (background Red1 `#402929`, border Red3 `#5e3838`, the
  normal text colour), with one plain sentence that names the file and what failed, e.g. "Could not
  mark src/a.ts as resolved: git add failed: …" or "src/logo.png cannot be shown in the editor: it
  is a binary file.", and a close (×, Lucide `x`) button. It disappears when closed or when the next
  action succeeds. Failures keep what was shown before (a failed open keeps the previous file; a
  failed "Mark resolved" keeps the file unresolved in the list). The failure is still logged.
- Which failures: the four kinds the app sends (`IpcError`: `Git`, `UnknownPath`, `Unsupported`
  with its reason, `WriteFailed`) and anything unexpected (the call itself rejected), each worded
  for a person, e.g. `Unsupported` reasons: binary file, not UTF-8 text, larger than 8 MiB, deleted
  in your branch / in theirs, a symbolic link, a submodule.

## Contract

```ts
// ipc/domain.ts — one source per fact: the failure IS the generated IpcError
export type SourceFailure = Generated.IpcError;
export type SourceResult<T> =
  | { readonly ok: true; readonly value: T }
  | { readonly ok: false; readonly failure: SourceFailure };

// ipc/ChunkSource.ts
export interface ChunkSource {
  listFiles(): Promise<FileEntry[]>;
  loadFile(path: string): Promise<SourceResult<FileMergeData>>;
  finishFile(path: string, text: string): Promise<SourceResult<FileEntry[]>>;
  resetFile(path: string): Promise<SourceResult<FileEntry[]>>; // was FileMergeData (plan §2 #41)
}
```

- `ipc/tauri.ts`: `createTauriSource(): ChunkSource` over the generated `commands` (their
  `{ status: "ok" | "error" }` results mapped to `SourceResult`; `loadFile` data through
  `toDomain`). No logic beyond the mapping (IPC5's spirit on this side).
- The fixture source keeps its behaviour behind the new shapes: an unknown path is an
  `UnknownPath` failure; `resetFile` returns the list with that file unresolved again.
- `ipc/index.ts` creates the one app logger: with `forward` = `commands.log` when the window runs
  in the app, without it otherwise (IPC8). `main.ts` picks the source the same way.
- "Runs in the app" = `import.meta.env.VITE_CHUNK_SOURCE === "tauri"` (architecture §4, IPC7); the
  app's dev and build commands set it (2.0, `tauri.conf.json`). `env.d.ts` types it as
  `"tauri" | undefined`; nothing else reads it.
- The store gains `problem: Readonly<ShallowRef<Problem | null>>` and `dismissProblem()`.
  `Problem` names the action (`list`, `open`, `finish`, `reset`), the path where there is one, and
  the cause (`SourceFailure`, or `{ kind: "Unexpected"; message }` for a rejected call). After
  `reset` succeeds the store reloads the active file (`loadFile`), so the panes start over.
- `problemText(problem): string` is the only place failures become words; exhaustive `switch` on the
  cause kind and the `Unsupported` reason (TS3). `ProblemBar.vue` only renders it.
- New colour tokens in `style.css` `@theme` (VU17): `--color-problem` `#402929`,
  `--color-problem-border` `#5e3838`.
- LogValue note (2.0 report): the generated `LogValue` allows `null`, the app rejects it, and a
  `NaN` number serialises as `null`: the forward must not send non-finite numbers (drop or stringify
  them; say which).

## Tests

Behaviour, not wiring (`store.test.ts` with its fake source; `problemText.test.ts`; the fixture
source's own tests):

- open failure → `problem` is set with action `open`, the path and the cause; `data` keeps the
  previous file; a later successful open clears it.
- finish failure → the list is unchanged (file still unresolved) and `problem` names the path;
  `dismissProblem` clears it.
- reset → the list comes from the reset result and the active file's data is reloaded (a new
  object, so the editor rebuilds), including when the source returns equal data.
- a rejected call (the source throws) → an `Unexpected` problem, no unhandled rejection.
- `problemText`: every cause kind and every `Unsupported` reason gives a sentence containing the
  file's path (and git's own message for `Git`); compare by `toContain`, never whole strings.
- fixture source: unknown path → `UnknownPath`; reset → that entry `Unresolved` again.

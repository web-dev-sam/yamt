## Findings (verbatim) and what to do

1. [should, boundary, principles-2] `editor/internal/words.ts:18` — "The rule 'a pane shows a
   block's word marks exactly when it shows its tint' exists as two independent copies. One is the
   side gate `!sideChanged(chunk, side) || isResolved(chunk, status)` at words.ts:18, mirroring
   decorations.ts:41; the other is the centre `isResolved` gate at words.ts:33, mirroring
   decorations.ts:53. A future change to the tint gate would silently leave the word marks on the
   old rule." Fix: "Fold sideMarks/centerMarks into decorations.ts so that each pane's single
   `EditorView.decorations.compute` filters chunks once and emits both bands and word marks.
   Alternatively, extract one predicate […] and call it from all four sites."
   **Decision**: either is fine; the rule must exist once. Report which.
2. [should, correctness, CM1] `editor/internal/words.test.ts:193` — "Every middle-pane 'text
   changed' case changes the block's length […] So a gate that only compares `span.to - span.from`
   with the original length (losing the sliceString compare at words.ts:39) passes all five tests,
   while marks would stay on a same-length edit such as replacing 'old' with 'new'." Fix: "Add a
   case to the 'typing inside' test that replaces 'old' with 'new' (same length) and asserts the
   conflict's middle mark is gone, then paste that mutation's failure as a hand proof."
3. [should, correctness, CM3] `editor/theme.css:41` — "The 0.65-alpha word mark is painted above
   CodeMirror's selection layer (drawSelection draws it behind the content at z-index -1 and makes
   native ::selection transparent), so a selection inside a word mark changes the background by
   only about (1,7,20) RGB. Selected text in the marked words, which is exactly what a user copies
   from a side pane (CM3 keeps selection and copy), is effectively invisible."
   **Decision**: selected text must be clearly visible everywhere — on plain lines, on block tints
   and on word marks — while text stays readable (JetBrains draws the selection over diff
   colours). The fix is yours (e.g. the selection layer drawn above the content with a
   partly transparent selection colour built with `color-mix(… var(--color-selection) …)`, which
   the palette check allows; no colour literals). Prove it with WebKit screenshots of a selection
   across a word mark and across a plain line in a side pane and in the middle pane; report the
   computed colours.
4. [nit, boundary] `editor/internal/words.ts:10` — "The field is called `originalDoc`, while its
   only reader […] calls it `base`." Fix: "Rename the field to `baseText` (or `originalBase`)."

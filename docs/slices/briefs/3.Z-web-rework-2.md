## Block

### #956 (correctness, block; `frontend/src/editor/internal/apply.ts:59`)

**Problem:** Deviation 5 has a user-visible bug when the user deletes the line break above a waiting conflict (Backspace at the start of its first line, giving "ab\nz\n" with span [1,3)) and then applies Local. `wholeLines` replaces [1,3) with "\nL\n". The applied span is then mapped to [1,4): `from` is mapped with assoc -1 and `to` with +1, so the span starts at the end of line "a" and holds the text "\nL\n". Two things follow. The centre band (decorations.ts:30, the conflict is still unresolved) and the strip rows (geometry.ts `rangeSpan`) now include line "a". And a Save of that half-decided conflict gets `shownLines` = ["", "L"], so the file is written as "a\n<<<<<<< ours\n\nL\n=======\nR1\nR2\n>>>>>>> theirs\nz\n". That blank line is not in the Result. Before this patch the apply joined the lines ("aL"), but the span stayed on that one line and the decided section was written correctly. The new apply.test case checks only the pane text, and the fileText cases only cover apply-then-join, so no test sees this.

**Fix:** Start the applied span on the line the apply inserted when `from` was mid-line. For example, when `wholeLines` adds the leading break, `applyChange`'s step should place the span with `from + 1` (or map the start with assoc 1 past that break). Add tests for join-before-then-apply: in apply.test, the span's text is "L\n"; in fileText.test, `written` equals the single marker block with no blank line.

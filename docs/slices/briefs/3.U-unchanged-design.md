## The product rule (settled — `docs/plan.md` §2 #63; do not reopen)

Copied from WebStorm 2026.2 (sources below). Owner's words (#827): "a big squiggle line that can be
clicked to show a bit more … spans across all 3 columns … when clicked shows a bit more code on all 3
views … so the user sees all changes/conflicts at once without scrolling much".

1. **Runs.** When a file's controller is built, each pane's runs of lines outside the changes are
   computed from all of `FileMergeData.chunks` (any kind, any status): before the first chunk,
   between two consecutive chunks, after the last. Run `k` in pane `p` is
   `[end of chunk k-1 in p, start of chunk k in p)`; the first starts at the file's top, the last
   ends at the file's end. Pane ranges: `chunk.local` (left), `chunk.middle` (centre), `chunk.remote`
   (right). Runs need not have the same length in every pane (the middle may come from the disk,
   plan §2 #53).
2. **Steps.** Each run has up to three nested hidden ranges, levels 0, 1, 2, keeping `C·2^level`
   lines (C = 4) next to each change and none at the file's edges. WebStorm (`FoldingBuilderBase`):
   ```
   for level in 0..2: shift = [4, 8, 16][level]
     for each pane i: start_i = clamp(runStart_i + shift, 0, lines_i)   // runStart = -∞ for the first run
                      end_i   = clamp(runEnd_i   - shift, 0, lines_i)   // runEnd = +∞ for the last run
                      range_i = end_i - start_i >= 2 ? [start_i, end_i) : none
     level exists when any pane has a range
   ```
   yamt's own addition: a level whose ranges equal the level outside it in every pane is dropped (a
   click that changes nothing). One level's ranges in the three panes are **one block**: shown or
   hidden together.
3. **What shows.** All levels start hidden. In each pane, a run shows its outermost hidden level as
   **one line of the normal line height** (20 px) carrying the wave, with no line number; deeper
   levels are invisible inside it. A pane where the outermost hidden level has no range shows the
   next hidden level that has one, if any.
4. **Click.** A press-and-release (primary button) on any part of a run's wave — in a pane (gutter
   or text area) or in a strip — shows that run's outermost hidden level in all three panes at once
   (`FoldedBlock.setExpanded(true)` on every editor's region). Three clicks show a whole run. The
   keyboard stays where it was (no focus change, no cursor move, no side mark, plan §2 #54 — as the
   strip icons, `preventDefault` on the press).
5. **Hover.** The pointer over any part of one run's wave draws that run's wave with a 2 px stroke
   instead of 1 px in all three panes and both strips, and shows the hand pointer
   (`updateHoveredBlock` sets one hovered block for every editor and repaints).
6. **Wave.** WebStorm's `DiffLineSeparatorRenderer`: period 20 px made of four quadratic segments
   (step 5 px = `diff.divider.width` 30 / 6; half-height 3 px; 1 px anti-aliasing gap; vertically
   centred in the line: offset `(lineHeight - 2·3 - 2·1) / 2`):
   ```
   moveTo(0, upper)                       upper = 1, center = 4, lower = 7  (px in a 8 px box)
   quadTo(step - step/2, upper,  step,   center)
   quadTo(2step - step/2, lower, 2step,  lower)
   quadTo(3step - step/2, lower, 3step,  center)
   quadTo(4step - step/2, upper, 4step,  upper)      repeated every 4·step along x
   ```
   Drawn across the line-number gutter and the text area, not moving with horizontal scroll.
   Colour WebStorm's `DIFF_SEPARATOR_WAVE`: #555555 dark (Darcula, parent of Islands Dark), #d0d0d0
   light (Default, parent of Light) — one new token in both palettes of `frontend/src/style.css`
   (VU17: colours only from there).
7. **Wave in a strip** (`ThreesideTextDiffViewerEx.MyFoldingModel`: `MyPaintable(0,1)`,
   `MyPaintable(1,2)`; `DiffDividerDrawUtil.paintSeparators`): for each run, the first level (outer →
   inner) hidden with a range in **both** adjacent panes is joined across the strip from the left
   pane's wave line `y1` to the right pane's `y2` (`DiffLineSeparatorRenderer.drawConnectorLine`, x1 =
   0, x2 = strip width, y += offset + half-height + 1):
   ```
   if |y2-y1| / width < 0.2:
     if width > 5·step: six quadTo half-waves: (x1+.5s, y1+h)→(x1+s, y1+h); (x1+1.5s, y1+h)→(x1+2s, midY);
                        (x1+2.5s, midY-h)→(midX, midY-h); (x2-2.5s, midY-h)→(x2-2s, midY);
                        (x2-1.5s, y2+h)→(x2-s, y2+h); (x2-.5s, y2+h)→(x2, y2)
     else: quadTo(midX, midY+2h, x2, y2)
   elif y1 > y2: curveTo(x1+s/8, y1+h/8, x1+s/8, y1+h/2, x1+s/2, y1+h/2); curveTo(x2-2s, y1+h/2, x2-2s, y2+4h, x2, y2)
   else:          curveTo(x1+2s, y1+4h, x1+2s, y2+h/2, x2-s/2, y2+h/2); curveTo(x2-s/8, y2+h/2, x2-s/8, y2+h/8, x2, y2)
   ```
   (s = step 5, h = 3; the strip SVG is the 2.5rem column minus 1 px borders ≈ 38 px wide.)
8. **Edits.** The middle's hidden ranges move with its text (a change elsewhere maps them); applying,
   ignoring, undo and redo never hide or show lines (WebStorm installs once per rediff,
   `MergeThreesideViewer.apply`); folding is never in the undo history. A hidden middle range that a
   user edit shrinks below 2 lines is shown.
9. **Hidden lines reached.** A selection placed on hidden lines in any pane (a find match, `selectAll`,
   a selection extended by keys) shows every level whose range holds the selection head in that pane —
   in all three panes (IntelliJ opens a fold the caret enters; `MyFoldingListener` mirrors the region
   state to the other editors). Plain arrow-key motion passes over a hidden range without showing it.
10. **Scope.** Fresh at every controller build (open, reset, a disk-change rebuild); nothing stored.
    Read-only views (plan §2 #47) fold the same. A side hidden by the deleted-side view
    (`data.deleted`) has an empty document: no ranges there, no strip wave beside it.

## Facts in the tree (HEAD `72e68d1`)

- `editor/index.ts` (294 lines; oxlint `max-lines` 300, `max-lines-per-function` 40) builds the three
  panes in `#createViews`, holds the `Layout` cache (`chunkRows` + `anchorsOf`) dropped by
  `rowsChanged(update, field)` (`internal/geometry.ts`), and paints once per animation frame in
  `#requestFrame` (`syncFindSpace`, `ScrollSync.sync(anchors)`, `pushCovered`, `Strips.paint`). The
  `#repaint` listener requests a frame on `docChanged`, `geometryChanged` and the find panel opening.
- Lines are 20 px in every pane (`internal/pane.ts:80`); `pane.ts` adds `lineNumbers()` (`:246`) and
  the gutter styles (`:90`); identical metrics in all panes are what keep them aligned (CM4).
- Scroll sync (`internal/scrollSync.ts`, CM12, RK4) interpolates linearly between chunk anchors
  (`lineBlockAt` tops/bottoms) — architecture §6 already names `Decoration.replace({block: true})`
  for collapsed regions and says `lineBlockAt` accounts for them.
- Strips (`internal/strips.ts`, `internal/gap.ts`): two persistent `<svg>`s (`hosts.strips`), bands
  as paths from `connectors/bandPath`, icon rows kept and moved per frame (plan §2 #51: no geometry
  work per scroll frame); `drag.ts` takes pointer capture on the strips for icon presses and drags;
  every strip press calls `preventDefault` so the keyboard stays (CM10).
- Side panes: `sideFocus.ts` handles presses (marks a change, focuses the side; scrollbar presses
  excluded), `modClick.ts` Ctrl/Cmd+click and +right-click on a change (`changeAt`); both go through
  `navigation.ts`'s hit test on chunk rows.
- Find: `internal/find.ts` + `findMatch.ts` on `@codemirror/search`, one bar per pane, selecting the
  current match.
- Middle: `chunkField.ts` maps chunk spans (CM1); actions are `Steps` (CM6/CM7); `history()` only in
  the middle; `invertedEffects` snapshot `placeSpans`.
- `connectors/index.ts` is pure path geometry (`bandPath`), unit-tested on numbers.

## What each option must answer

1. **Runs and steps as pure functions**: inputs (chunks' three line ranges, three line counts),
   output shape (run → levels → per-pane `[start, end)` or none), the dropped equal level, the file
   edges, a file with no chunks, a run of 0–1 lines, a pane with an empty document. Where it lives
   (`editor/internal/<name>.ts`), its types (line-space brands per pane: `LocalLine`, `MiddleLine`,
   `RemoteLine`, vision 4).
2. **State**: where "which levels are shown" lives (one owner, vision 2) and how all three panes and
   both strips read it; where each pane's hidden ranges live and how the middle's map through edits,
   undo and actions (CM1/CM9 style, no stored `number` positions outside a field); why folding stays
   out of history; what a transaction that shows a level looks like (one dispatch per pane? effects
   outside history).
3. **Rendering in a pane**: the CodeMirror construct (block replace decoration with a widget of one
   line height, `estimatedHeight`, `eq`), how the wave reaches across the gutter (line-number gutter
   marker for the widget, e.g. `lineNumberWidgetMarker`, or another way) and how the wave is drawn
   (inline SVG path, CSS mask, …) with the theme token; how hover state reaches the widgets without
   rebuilding decorations per mouse move.
4. **Rendering in the strips**: where the joins are computed (with the `Layout` cache, not per scroll
   frame), how they are kept/moved like the icon rows, the `drawConnectorLine` port as pure geometry
   (tested on numbers), hover thickness.
5. **Pointer**: one hover model across five surfaces (three panes, two strips); the click in a pane
   (which event, how it beats `sideFocus`'s press, `modClick`, CodeMirror's own selection press, text
   drag-select in the middle) and in a strip (beside `drag.ts`'s pointer capture and the icon rows);
   the keyboard staying put; the hand cursor.
6. **Cursor and find**: arrow keys passing over a hidden range (`EditorView.atomicRanges` or
   equivalent) in the middle and in sides; how rule 9 detects a selection on hidden lines (which
   transactions, which panes) and shows the levels in all panes without a loop.
7. **Alignment and scroll** (RK4, CM12): proof that rows stay aligned when runs differ in length per
   pane, whether the sync's anchors need the hidden ranges' edges, what `geometryChanged` does with
   the cache, and that no new layout read happens per scroll frame (#51).
8. **Interactions**: keyboard navigation and reveal (`viewport.ts`, `navigation.ts`'s on-screen
   rule), bulk apply's visible lines, find space above line 1, removal bars, drag over icons,
   `destroy()` (CM14), read-only and deleted-side views.
9. **File budget**: `index.ts` is at 294/300 lines — say what moves out (and where) so the build fits.
   Estimate files and changed lines (one build slice must stay ≤ ~25 files, ≤ ~1,500 lines).
10. **Tests**: `editor/` is not mutated here, so name the node unit tests that would fail for each
    rule's plausible bug (runs/steps, mapping, shown-state transitions, connector geometry, selection
    reveal), and the WebKit steps (real pointer moves, clicks and keys at visible positions on a
    golden fixture with far-apart changes) that prove it in the browser and the real app.

## Contract (fixed; you may add private items, never change these)

```rust
// merge-core/src/word.rs (serde::Serialize + specta::Type, like its neighbours)
/// Base text one side removed, and the place in that side where it would sit.
pub struct Removal<L> {
    /// The zero-width place (the same places `removed_at` held).
    pub at: InlinePoint<L>,
    /// The removed base text, every line break written `\n`; never empty.
    pub text: String,
}

pub struct SideWordChanges<L> {
    pub changed: Vec<InlineRange<L>>,
    /// Base text this side removed with nothing new in its place: sorted by place, at most one per place.
    pub removals: Vec<Removal<L>>,
}
```

`removed_at` leaves the contract. `word_changes`'s signature is unchanged.

Frontend domain (`ipc/domain.ts`), written exactly like this:

```ts
type Removal<L> = { readonly at: InlinePoint<L>; readonly text: string };

```

## Behaviour (what `text` holds)

1. **Inside a pair** (pure-removal token hunk): the removed base tokens, concatenated (`foo(a, b, c)` → `foo(a, c)`
   gives the text the tokens between the two kept places hold, e.g. `b, ` or ` b,` — whichever the existing point
   placement implies; pin it).
2. **Removed whole lines, bar at column 0 of the side line after them:** each removed base line without its own line
   break, followed by `\n` (`if (ok) {` removed → `if (ok) {\n`).
3. **Removed whole lines at the end of the chunk side, bar at the end of the side line before them:** `\n` before each
   removed base line (`}` removed at the end → `\n}`). A removed blank line gives `\n`, so `text` is never empty.
4. **Two removals at one place** (today's `dedup`): one removal whose text is the two texts concatenated in push order,
   which is base order: removed lines then a pair's leading removed tokens (`if (ok) {\n` + `\t` → `if (ok) {\n\t`, the
   catalogue's M2), or a pair's trailing removed tokens then removed lines at the chunk end (`;` + `\n}` → `;\n}`).
   [INFERENCE] these two are the only ways two pushes meet at one place; prove it to yourself in the code and say so.
5. CRLF: no `\r` from line ends ever appears in `text`; columns stay UTF-16; the same input always gives the same
   output.

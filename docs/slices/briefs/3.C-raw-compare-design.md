# 3.C — design: `yamt --raw`, a two-column compare of pasted text with tabs that survive a restart (board "Raw compare" row 1)

Agent: `designer` (read-only). Output: two or three file-level options plus a recommendation (your output schema). You
design; the orchestrator chooses; then builds run as a dependency graph — at most two implementers at once, Rust
(`rust-impl`) and window (`web-impl`) builds side by side where the files are disjoint. Name every file each build
creates, changes or deletes, and the fixed contract between builds (the IPC types and commands written out in full, the
`editor/` public surface written out in full). One build ≤ ~25 files, ≤ ~1,500 changed lines; split otherwise. Tree:
branch `feat/raw-compare` off main `8db7609`.

## The feature — settled, do not reopen

`docs/slices/request-raw-compare.md`: the owner's words, **rules 1–8**, the orchestrator defaults (names, closing,
headers, detection, size, toolbar, Ctrl/Cmd+B), the sourced facts, acceptance, non-goals and risks. Read it in full
first; its facts carry a source and are given (`skill://slice-protocol`); re-check only what it marks `[INFERENCE]`.

**The owner's answers** (request table, #1462; sent to the designer during its run): Format covers JSON and XML, built
in with the browser's own parsers (no formatter dependency); JSON keys keep their order (no sorting, no second action);
the strip shows bands only (no copy arrows).

## What each option must answer

1. **Mode**: how `--raw` is parsed (`args.rs` `Invocation`), what the shell does instead of `outcome::startup` (no
   git, no `MergeState` work; the close ending exit 0, no question), and how the page learns it is the compare window —
   a command, an initialisation script, or a URL — without a flash of the merge window. Fixture mode's equivalent (e.g.
   `?raw`) so WebKit can drive it. Which merge-only parts never start in this mode (language servers, focus refresh,
   listing, disk-change polling, close guard) and how that is guaranteed by structure (a second root component and
   store, vs. branches inside `App.vue`/`store.ts`: `store.ts` is at 297/300 lines).
2. **The differences' home** (vision 2, one diff rule): merge-core behind a new IPC command (confirm or refute that
   `compute_chunks(left, left, right)` + `word_changes` give a correct 2-way result in the existing chunk shape, from
   `crates/merge-core/src/compute.rs` and `word.rs`; or a small 2-way entry point in merge-core) vs. computing in the
   window. Live updates: when a recompute runs (pause length, a constant next to its only user), how a stale answer is
   dropped (a version per request), the cost on two 8 MiB columns (measure or cite imara-diff's), and what fixture mode
   does with no Rust behind it (WebKit must still show differences after typing, or the design says which acceptance
   lines are real-app only and why).
3. **The editor's two-column controller**: reuse of the merge view's internals (`paneViews`, `pane`, `decorations`,
   `words`/`removalTooltip`, `tone.paneTone`, `geometry`, `gap`, `strips`, `frame`, `scrollSync`, `find`, `historyKey`,
   the keymaps and `setPreferences`) for two editable panes and one strip — a second public class beside
   `MergeController` vs. a two-pane shape of `MergeController` — with exact public surface (constructor, `setText`/
   change events per column, `setLanguage`, `setDifferences` or its own recompute, `setPreferences`, `destroy`, what
   Format needs). How each internal that assumes three panes and two strips (`STRIP_PANES`, `PaneViews`, `Frame`,
   `chunkField` statuses, `paneTone`'s pane argument) is generalised or bypassed without a flag bag (vision 4) and
   without slowing the merge window (plan §2 #51). Which chunk colours mean what when both columns are editable and no
   status exists (no apply/ignore). `editor/index.ts` is at 286/300: where new code lives. Undo: Format as one step per
   column; undo by keyboard per column.
4. **Tabs and storage**: who owns the tab list, the shown tab and each tab's texts and language (vision 2: one writer;
   `skill://project-map` state table — the editor owns document text while shown, Vue never holds it); how a hidden
   tab's text is kept (a mounted hidden view per tab as the merge window keeps opened files, vs. one view whose
   documents are swapped; memory and switching cost with many tabs); where tabs are stored (a Rust-owned file in the
   user's data folder written with temp file + rename as the settings file is, one file vs. one per tab, vs.
   localStorage — the request notes its ~5 MB quota [INFERENCE: check WebKitGTK's]); when a save is written (rule 7:
   within about a second of the last change, only what changed); what a broken or newer-format stored file does (never
   overwritten silently, a problem shown); two `yamt --raw` windows at once (request risk: pick a rule and say how it
   is enforced); first start; the 8 MiB per column limit and where it is checked.
5. **Format and detection** as pure TypeScript modules with tests on strings: JSON (and XML for the default answer)
   with the browser's own parsers, indentation, a column that fails to parse (its message and line), line endings, a
   trailing newline, CRLF input; the edit applied as one change per column (whole-document replace vs. paired line edits
   as `format.ts` does — say which and why). Detection rules for "Auto" (request default), their order, which columns'
   text they read, when they re-run (a paste, a pause) and how "Auto · JSON" is shown. The drop-down's list from
   `@codemirror/language-data`'s `languages` (151) and how a choice reaches the panes (`languageCompartment`).
6. **The window's chrome**: the tab panel in the file list's cell (`App.vue`/`FileList.vue` reuse or a new component;
   header "+", rows with name, language, ×, rename by double-click), the toolbar (Format, the drop-down, change arrows
   if free, the gear), the column headers, the question on closing (`ui/asking.ts`), notices for Format failures and a
   refused paste (`NoticeBar`/`ProblemBar` reuse), the settings view behind the gear, Ctrl/Cmd+B, the panel's width.
   Component and composable names per `skill://vue-conventions`.
7. **IPC** (`skill://ipc-contract`): every new command and type written out in Rust and in the generated TS shape,
   domain brands if any (a tab id), error kinds (`IpcError` additions), and which crate owns the stored tabs (a new
   crate vs. `yamt-settings`, which today holds only settings: vision 5 and the crate list in `docs/architecture.md` §7
   — a new crate is a decision row).
8. **Tests**: `editor/` is not mutated (VF7) — for each node unit test name the plausible bug it catches and the
   one-line hand mutation that makes it fail. Rust and `ui/` are mutated (`just mutants`); name the behaviour tests.
   WebKit steps (MiniBrowser through `just webdriver <port>`, dev server on its own port) and real-app steps
   (`just app-session`, real X input via `xdotool`) for every acceptance line, including `kill -9` a second after
   typing, and a typing-speed check in a large column.
9. **Size and order**: builds with disjoint `Owned` globs, files and changed-line estimate each, which run side by side
   and which wait for which commit; the contract each build fixes for the next.
10. **Plan §2 rows**: #5's replacement (DR4: the reopened row's "Rejected" column gets the new information) and one row
    per new decision (mode, diff home, controller shape, storage, Format/detection), each citing visions, in the style
    of #81/#85.

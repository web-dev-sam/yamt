## Blocks

1. **#790 (RK25) — symlink conflicts are resolved silently on Windows.** Git for Windows defaults to
   `core.symlinks=false`: a symlink conflict is written as a plain file holding ours' link target. `compare_stage`
   (`crates/session/src/start.rs:~284-295`) counts `OnDisk::File` against a `120000` stage as `Changed`, the file gets
   `Seen::GitOutput`, and the first refresh's settlement stages ours' link with `git add` without the user choosing.
   Fix: a plain file against a link stage is compared with the link blob's bytes (`OnDisk::File(bytes) if is_link =>
   same(&blobs.read(&entry.oid)?, bytes)`), so git's own output is recognised as untouched. Test (runs on Linux, not
   gated): a link conflict merged with `core.symlinks=false` (conflict-repo's config hook, `conflict_repo_with`) — after
   open and the first list, the file is untouched on disk, still unresolved in `git ls-files -u`, and shown as the
   link it is. If the fixture needs a link created by git rather than by `link_to`, script it so it compiles for
   Windows too (the stage is `120000` with core.symlinks=false; no real symlink is created) — then it runs on windows-2025.
2. **#791 (promoted, RK18) — gate only the link.** `NON_REGULAR_NEXT_TO_TEXT` (`crates/session/tests/open_and_load.rs:~249`,
   which removes RK18's `reset_of_a_submodule_conflict_keeps_its_stages_and_leaves_it_unresolved`), `describe.rs:31`
   (binary, non-UTF-8 and commit-id sides) and `disk_is_truth.rs:319` (binary and submodule staged by any change) are
   gated whole for one link element: put `#[cfg(unix)]` only on the link element and its assertion rows, as
   `every_kind/mod.rs` and `deleted_side.rs` already do.

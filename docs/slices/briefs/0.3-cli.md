# Slice 0.3 — cli: classify, scan, golden, fixture + the `git merge-file` cross-check

The headless front end of the engine (architecture §3.4). It is how the owner compares the
engine against PhpStorm (Gate C, plan §5 M0 acceptance), how golden cases are checked in
`just check`, and how M1 gets its fixture JSON. It also hosts RK13: where the engine finds no
conflict, its merge must equal git's own.

A parallel slice (0.3') collects 10 real golden cases into `tests/golden/`; you do not depend on
them. Test your golden tooling on synthetic case directories you create in a temp dir.

## Target

Owned: `crates/cli/**`, `crates/session/src/**`

Read-only: `docs/**`, `.omp/**`, `crates/merge-core/**`, `crates/gitio/**`,
`crates/conflict-repo/**`, `crates/session/tests/**`, `tests/golden/**`, `Cargo.toml`,
`Cargo.lock`, `justfile`.

Dependencies already added and locked by the orchestrator: cli → `yamt-session`,
`yamt-merge-core`, `serde_json`; dev: `proptest`, `tempfile`, `yamt-conflict-repo`. Nothing else (no argument-parsing
crate: four subcommands parse fine with `std::env::args`, vision 5). If you need another crate,
stop and report it.

Non-goals: Tauri, bindings export, the golden cases themselves (0.3'), changing chunk
semantics, `insta` (expected.json comparison is plain JSON equality).

## Contract (fixed; you may add private items, never change these)

```rust
// crates/session — one addition, re-exported from lib.rs; `load` must use it (one source, vision 2)
pub fn merge_data(path: &str, base: &str, local: &str, remote: &str) -> FileMergeData;
// eol from base (local when base is empty), language from `path`'s extension,
// chunks = compute_chunks(.., &Options::default())
```

```
yamt-cli classify <base> <local> <remote> [--gap N] [--json]
    table (default): one row per chunk, exactly
        <id> <Kind> base[<start>+<len>] local[<start>+<len>] remote[<start>+<len>]
      e.g. `4 Conflict base[57+4] local[62+4] remote[53+2]`; then a summary line with the count
      per kind. --json: the chunks as pretty JSON, the §4 `Chunk[]` shape, trailing newline.
yamt-cli scan [<repo>]          (default: current directory)
    MergeSession::open; one row per file: path, status, then either the unsupported reason or
    the chunk count per kind; last line `remaining: N`.
yamt-cli golden run [<dir>]     (default: tests/golden, relative to the current directory)
    every subdirectory with base.*, local.*, remote.* (same extension) is a case; compute the
    chunks with DEFAULT_GAP, serialise exactly like `classify --json`, compare bytes with
    <case>/expected.json; print `ok <case>` or `DIFF <case>` (+ a short first-difference hint);
    exit 1 on any DIFF, a missing expected.json, a malformed case, or zero cases.
yamt-cli golden update [<dir>]  rewrite every case's expected.json; print `wrote <case>`.
yamt-cli fixture <case-dir>     print `merge_data("<case-name>.<ext>", base, local, remote)` as
                                pretty JSON (FileMergeData, §4) on stdout.
```

Errors: one `Error` enum in the cli lib (RS7), printed as `yamt-cli: <message>` on stderr with
exit 2 for usage errors and 1 for failures (`anyhow` is not needed). `main.rs` ≤ 30 lines,
delegating to the lib (RS10).

## Change

1. `session::merge_data` as above; `MergeSession::load` calls it.
2. The five subcommands in `crates/cli/src/` (module per responsibility: args, classify output,
   golden, scan, fixture — your call on names, RS12).
3. **RK13 cross-check** `crates/cli/tests/merge_file.rs`: a proptest (≥ 256 cases; small line
   alphabet incl. `\r\n` lines and a last line without `\n`; local/remote derived from base by
   random edits, plus shared edits so both sides often touch the same region) — whenever
   `compute_chunks` yields no `Conflict`, `apply_non_conflicting(..)` must equal the stdout of
   `git merge-file -p <local> <base> <remote>` run on temp files (exit 0). Run git with
   `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `LC_ALL=C`. Count and report how many
   generated cases were conflict-free (the property must not pass vacuously: assert a minimum
   share, e.g. ≥ 25%). If the property fails, do **not** weaken it: report the shrunk
   counterexample with both outputs — that is a finding about the chunk model, not about the test.
4. Tests for the tooling (integration, in a temp dir): `golden update` then `golden run` → exit 0
   and `ok`; edit one expected.json → `golden run` exit 1 with `DIFF <case>`; a case missing
   `remote.*` → exit 1; zero cases → exit 1; `classify` table format on a fixed triple (exact
   text); `classify --json` round-trips through `serde_json` into the §4 shape; `fixture` output
   has `path`, texts, `eol`, `language` and `chunks`; `scan` on a repo built with
   `yamt_conflict_repo::conflict_repo` lists its files with chunk counts and `remaining`.

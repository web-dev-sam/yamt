## Next, in order

1. **Row 13 — design "a conflicted file changed on disk is the truth"** (owner #514, answers #515;
   plan §2 #52 has the full rule). Spawn `designer` (read-only) for 2–3 file-level options, choose
   one citing a vision, then write the briefs for row 13'. The rule in short:
   - yamt remembers each conflicted file's disk content as it last saw it: at start, and after its
     own writes (Mark resolved, Take, Keep, Delete, Reset);
   - it compares on window focus (together with #49's `ls-files -u` re-read) and right before each
     of its own writes; a change found before a write wins, and the write is skipped;
   - on a change: the file's unsaved edits and undo history are dropped, and a closable notice
     names the file ("<path> changed on disk; your edits in yamt were dropped");
   - no conflict markers left, or the file deleted → `git add` / `git rm` at once, mark resolved; a
     later disk change to a resolved file is staged the same way;
   - markers left → the middle pane shows the disk text; each block still marked is a normal yamt
     conflict (arrows/× per side, side panes from git's stages); everything else counts as done.

   Questions the design must answer (owner-facing ones are settled; these are technical):
   - **Reading git's markers.** Styles merge / diff3 / zdiff3; the `conflict-marker-size`
     attribute; CRLF; a file that legitimately contains `=======` lines; the labels git writes
     after `<<<<<<<` / `>>>>>>>`. Plan §1 names marker parsing as the root flaw of other tools.
     Here markers are read only to find the blocks still open; the three panes still come from
     git's stages, so base stays known. Keep that distinction explicit in the design.
   - **Mapping marker blocks onto yamt's chunks.** yamt's diff3 chunks are not git's blocks (git
     auto-merges one-sided changes; it aligns repeated lines differently, #42). Options include
     re-diffing the disk text against base, or anchoring each marker block's ours/theirs text in the
     side panes. Statuses: `applied`/`ignored`/pending per side (#33).
   - **IPC.** A new field on `FileMergeData` (e.g. the seeded middle text plus chunk statuses), or a
     new command (`skill://ipc-contract`; bindings are generated by `just bindings`).
   - **Files the editor cannot show** (binary, symlink, submodule; #36) and **deleted-side text
     files** (#47) have no markers, so any change there stages it.
   - **State ownership.** The per-file "last seen on disk" lives in Rust's `MergeSession` next to
     the stages; Vue holds none of it.
   - **Notice.** The window has `ProblemBar` and the "all files resolved" bar. The notice is
     information, not a failure.
   - **Tests.** Session integration tests with a scripted repo: regenerate a file → staged;
     partial marker removal → remaining blocks only; delete → `git rm`; Mark resolved after an
     unseen change → disk wins.
